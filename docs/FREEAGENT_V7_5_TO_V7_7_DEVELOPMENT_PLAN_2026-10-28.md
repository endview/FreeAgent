# FreeAgent v7.5–v7.7 后续版本开发计划

日期：2026-10-28；实施更新：2026-10-29。本地实现已推进至 v7.7.0-dev.1；证据见 [v7.7 实施记录](FREEAGENT_V7_7_IMPLEMENTATION_PROGRESS.md)。用户已确认先完成本地实现与模拟验收；真实平台和代表性 Provider 验收仍为 NOT_RUN，不能称为正式平台验收通过。下文保留原规划基线及验收条件。

产品规则以[统一对话空间与外部渠道接入方案](FREEAGENT_CONVERSATION_SPACES_AND_CHANNELS_PLAN_2026-10-27.md)为准；本文负责版本范围、实施顺序、交付物和验收。两份文档发生冲突时先同步修正文档，不在实现中悄悄改变已确认规则。

## 1. 当前基线与目标

本次核对的本地基线：`VERSION = v7.4.0-dev.1`，HEAD 为 `6b9e0ae`。现有实现包括 GUI/CLI attach、控制操作、持久上下文压缩、工具结果规范化、后台命令和有限时长服务。[v7.4 实施记录](FREEAGENT_V7_4_IMPLEMENTATION_PROGRESS.md)记载了已运行的测试及其源码范围；这些历史结果不能直接算作后续版本通过。

规划时，统一空间、人员权限、None 和 Telegram/Lark/QQ 适配处于文档阶段；此处保留原规划基线。当前本地实现和实际测试结果见文首实施记录，真实平台及远端 Release 不能据此推定通过或已更新。

产品目标：先让 FreeAgent 在电脑和 Telegram 中使用同一套对话与执行核心，再复用同一接入方式覆盖 Lark、QQ，最后改善多人同时使用时的等待。每一阶段都应交付可实际使用的结果。

## 2. 全程保持的约束

1. 一个 Owner、一套 TaskService、一套空间和对话记录；渠道适配器不自行运行工具，不创建自己的 Agent、任务表或执行器。
2. 操作权限只有空间和实际发起人两层，取较低一级：`None < Ask < Workspace < Full`。新空间和未设置人员均为 None，不能继承全局 Full。
3. None 可以聊天、进入群背景和查看已开放的公开对话信息；文件、命令、网络、Provider 原生搜索、MCP/扩展及控制改动由核心拒绝。正常保存聊天和调用聊天模型不算授予操作能力。
4. 当前发起人取自可信渠道事件。历史、引用、转发、昵称、摘要和模型输出不能提供身份或批准；普通群消息只记录，明确唤醒才启动回答。
5. 产品持久设置由 AI 提议时需要明确确认；工具继续遵守现有模式。GUI 卡片、CLI 提示、渠道按钮复用已有确认，不新增聊天确认码。
6. 使用新的独立数据格式，不做旧版本兼容或迁移。沿用既有消息、Run、Attempt、审批和命令记录，不预设新的 Task、Step、Checkpoint、Evidence 持久对象。
7. 不加入自动 RAG、隐式人格学习、后台知识治理、多租户、组织角色、插件市场或模块生命周期平台。
8. 停止不代表副作用消失，UNKNOWN 不自动重试。Full 的同用户宿主机边界、共享背景可能影响有权限者的模型判断，都如实保留。

## 4. v7.5-A：统一空间与权限基础

### 4.1 数据结构和核心操作

- 新增 `spaces`，对话必须有 `space_id`；初始化创建不可删除的“本地”空间，默认权限 None。
- 空间权限、人员权限、渠道游标复用现有 `meta`；消息来源、真实发送人、背景/触发用途复用并扩展现有消息记录。原始内容与执行证据仍可追查。
- 把权限级别选择从对话改到空间，避免新旧两套判断共存；工作区与资源范围继续沿用执行配置。
- 实现列出、新建、重命名、删除空间，以及对话移动、设默认和渠道当前对话选择。默认/当前对话必须属于该空间，修改应原子提交。
- 删除空间时对话回到“本地”；存在未结束 Run 的对话先处理 Run。移入外部空间前预览公开范围和权限变化，明确确认后执行。
- 新格式使用当前未占用的数据目录标识 `Harness-v7`、schema 9 和 `freeagent-harness-v9`；v7.5-B 的可空消息 Run 关联包含在本次格式中。旧数据、包和备份不能互相误读。
- 同步更新 `internal/apppaths`、启动器、便携包 manifest、构建/启动/验收脚本和文档中的格式标识，不能只改数据库常量。

### 4.2 None 与统一执行检查

- 新增 None 的解析、保存、显示和执行配置。由核心计算权限，适配器和模型只提供已验证的请求信息，不能直接指定生效级别。
- 预先实现空间与人员的两层计算及 Run 来源记录，B 阶段只接入真实渠道身份，不再改写核心规则。
- None 在工具选择与实际执行入口双重生效，覆盖文件、命令/服务、MCP、扩展、模型原生搜索和控制写入；不能让模型通过猜测命令 ID、其他对话 ID 读取结果。
- 延续 Ask 的实际免批规则，不把 Ask 改成所有调用都弹框；Workspace/Full 的执行语义保持明确。
- 权限增加只用于新 Run；下降/撤销影响下一次工具调用、继续及审批，旧 Run 不获得新授权。权限撤销与 Stop 不能被正在运行任务的普通配置锁阻挡。
- 撤权同时查找该空间或人员已启动的后台命令和服务，向相关进程请求停止。终止、进程树清理或记录落盘不能确认时保留 UNKNOWN 和占用；已经发生的副作用仍由原记录说明，不因撤权清空。撤权不等待普通配置修改所需的空闲窗口。
- 输入范围必须覆盖完整模型请求：历史、摘要、本机指令、已选记忆、Skills、扩展注入和原生工具。外部空间不隐式继承本机输入选择；移动到外部空间时清除这些本机引用并重建对应公开摘要。纯聊天不能通过关闭工具后继续携带未公开工具轨迹或私密摘要。
- 本机可以管理权限，也可以继续外部 Run，但继续时不转换原发起人、不扩大其权限上限。

### 4.3 GUI、CLI 与 AI 操作

- GUI 侧边栏按空间归类，保留置顶与时间顺序；“本地”保持简洁，外部单对话空间可一行打开。
- 空间详情显示空间权限；外部空间另显示已出现人员及其全局权限，明确“改这个人会影响其在其他已接入空间的资格，最终仍受各空间限制”。
- CLI 增加空间与人员操作，列出对话默认限定当前空间。接口语义与 GUI 共用核心，客户端只保存各自当前查看的对话。
- 可调整的设置通过既有控制目录提供 AI 提议入口，持久改动走已有预览/确认；敏感配置在本机确认。None 不得借控制入口自行修改权限。
- GUI/CLI/attach 覆盖创建、列表、默认、移动和重启恢复，不以只完成存储函数作为阶段完成。

### 4.4 完成标准

- 新目录中所有对话均有有效归属，空间默认 None；删除、移动、当前/默认选择及重启后状态一致。
- 16 种空间×人员权限组合全部符合取低规则；模拟恶意 Provider 返回未提供的工具调用仍不能操作。
- 测试跨对话命令 ID、背景引用、Provider 原生工具和控制改动等旁路；无授权时不能发生对应资源访问。
- GUI/CLI 与 AI 控制入口的预览、确认、取消和失效处理一致；Full 确认不被空间移动绕过。
- 新数据格式与便携包脚本同时更新，旧数据拒绝误用；本机桌面可正常启动和接续。

交付：可独立使用的空间版本及阶段验收记录。此时可以提供内部预览，但不能宣称 Telegram 已可用。

## 5. v7.5-B：Telegram 私聊与公共接入契约

### 5.1 最小适配器

- 在 Owner 中增加可选 Telegram 接入，长轮询接收消息；未启用时不连接网络，不自动启动额外守护进程。
- 首版只定义实际需要的共同输入与输出：稳定聊天身份、稳定人员身份、消息 ID/用途、文本、回复目标以及审批回调。不要先设计通用渠道生命周期平台。
- 渠道调用与 GUI/CLI 相同的受认证核心操作。外部传输的身份必须由适配器确认，不能接受用户正文提供的 `person_id` 或 `permission`。
- Bot Token 进入现有密钥存储；日志、异常、诊断和导出不泄露 Token。AI 可以引导配置，秘密值仍通过现有密钥入口输入。
- 设置页、CLI 和 AI 控制目录覆盖启用/停用、连接状态、配对和故障原因；停用阻止新消息触发，不能销毁既有执行记录或声称任务已经撤销。

### 5.2 配对和基本使用

- 本机生成一次性限时配对码，私聊兑换后建立空间和第一个对话；重复事件不重复创建。
- 配对只建立聊天绑定。新空间 None，未授权人员 None；同一 Telegram 用户不因换群或换 Bot 生成一套新权限。
- 默认单对话并持续使用第一个对话。只有显式开启多对话后提供列表、新建、切换和默认选择；整理操作遵守既定权限。
- 支持文本回答、限频编辑与分段，以及公开状态、停止、继续、放弃、压缩。显示当前空间、本人和有效权限，外部 `/mode` 只读。
- 本机能看到并接续同一对话；回复目标明确，不能把本机私聊或其他空间内容误发到 Telegram。

### 5.3 审批与故障行为

- Ask 中需要确认的操作显示按钮，复用待确认记录；核验点击者、空间/对话/Run、具体内容、当前权限和状态。
- 审批、继续、放弃只认原发起人或本机。重复、过期、错误用户及内容已经变化的按钮不执行。
- 请求键由渠道、Bot/应用、聊天和平台消息 ID 组成。接收去重、记录入库和 Run 创建必须有可恢复的关联；不能因网络重试创建第二个 Run。
- Owner 离线积压消息不补执行；断线恢复不重跑已启动操作。发送结果不确定时记录交付状态，不能为了重新发回复而重跑模型或工具。
- v7.5 仍只执行一个前台 Run；忙碌请求明确拒绝并提示重发，不排队。只在存在真实等待提示时发一次空闲通知。
- 连接断开不改变操作权限；停止后的副作用、命令实际状态和 UNKNOWN 使用既有记录判断。

### 5.4 完成标准与交付

自动化覆盖模拟 Telegram API、重复投递、断连、限流、回调伪造、权限撤销、Owner 重启和 GUI/CLI 接续。真实测试完成以下路径：

1. 全新便携包配置 Bot，配对后以 None 正常聊天，操作请求被拒绝。
2. 本机分别设置空间和人员权限，验证任意一侧 None/Ask 都限制实际执行。
3. Ask 操作在 Telegram 点击批准或拒绝；核对实际文件结果与执行记录，而非只看模型回复。
4. GUI 与 CLI attach 到同一对话，审批、停止与恢复不产生第二个 Owner 或第二次执行。
5. 重启、重复事件及断线后的旧请求不重放，公开回复的目标不串到其他空间。

交付：Telegram 私聊预览、设置与使用说明、阶段测试记录。真实 Bot 未运行时标记 NOT_RUN，此阶段不能标为“已完成真实接入验收”。

## 6. v7.5-C：Telegram 群聊共享背景

### 6.1 群聊体验

- 群配对建立群空间。群可操作与成员可操作是两层条件，群接入不自动给全员授予能力。
- 保存实际收到的普通文字消息，包括 None 成员的发言；未唤醒消息不创建 Run、不请求模型、不启动工具。
- 命令、@Bot 或回复 Bot 触发回答。None 成员可以进行纯聊天和总结；需要操作时才说明权限不足，不对闲聊反复发拒绝提示。
- Run 固定触发消息、发起人和本次背景范围，运行期间的新发言留给后续请求。背景中的“已批准”及引用的 Full 用户不改变权限。
- 复用持久压缩，但先筛选该群可见内容再生成摘要；不能复用夹带本机私密工具轨迹的摘要。摘要保留来源与背景性质，不视为新授权。
- 普通消息按收到时的当前对话归档；多对话切换只影响后续记录。回复及审批绑定原 Run 的目标，不跟随客户端当前选择漂移。
- 接入界面说明 Privacy Mode 与可见消息范围；无法获取的消息或历史不标为完整记录，未公开执行结果不进入群背景。

### 6.2 群内操作

- 同一群里设置 None、Ask、Full 人员，按两侧取低规则运行；全群共用当前对话，不按发言人拆出独立上下文。
- 人员 ID 来自真实事件；匿名身份按 None，伪造昵称、转发及回复对象不提供操作者身份。
- 群内按钮人人可能看见，但只有原发起人和本机能批准、继续或放弃。其他人不能把 None 的请求变成自己的 Full 执行。
- Stop 保留现有规定的可操作人范围；直接停止、等待审批和权限撤销都不依赖模型判断。
- 群内正在执行时照常保存其他普通发言，明确请求仍按忙碌规则回复；空闲后不会把聊天背景中的旧要求自动执行。

### 6.3 v7.5 发布完成标准

- 至少两个可控真实账号在专用测试群完成多身份测试，通过切换授权覆盖 None/Ask/Workspace/Full；单账号只能证明单身份路径。
- 验证 None 的信息能被之后的回答引用，但其操作请求、伪造批准和工具 ID 猜测都不能直接越权。
- 真实审批、拒绝、错误账号点击、内容改变、权限撤销和重复回调均与本地证据一致。
- 压缩、重启及会话切换后仍能区分公开背景与未公开轨迹；不自动获取群中链接或附件。
- 默认 Privacy Mode 与可接收普通发言的配置分别实测；只根据实际收到的消息声明上下文覆盖范围。
- 完成 A/B/C 集成回归、Windows 原生竞态检查、WebView2 操作检查及最终干净便携包验收。
- 共享上下文的注入样例作为行为观察与权限回归，不能用有限样例通过来声称 Full 不受间接注入影响。

交付：v7.5 空间与 Telegram 版本、便携包、GUI/CLI/渠道使用说明、功能和平台验收矩阵。只完成 B 时不得把群聊标为已交付。

## 7. v7.5.1：Lark/飞书接入

目标是复用 v7.5 的核心契约，只补渠道差异。

- 优先使用官方应用长连接；实现事件身份解析、稳定聊天/人员键、消息收发、卡片回调及去重。
- 正确处理租户、应用和人员 ID 的有效范围，不把不同作用域下的相同字符串当作同一人；不要求 Telegram 用户与飞书用户自动合并。
- 支持私聊、群聊文字、明确唤醒、共享可见背景、单/多对话及按钮/卡片审批。
- 申请满足所交付场景的官方权限；群普通消息是否可见，根据应用权限和真实事件验证，不能由 Telegram 的测试推断。
- 卡片点击者、事件签名/鉴权、回调去重和动作失效由适配器与核心共同校验；卡片更新失败不重跑操作。
- 设置、配对、权限和状态继续在同一 GUI/CLI/AI 控制入口管理，不出现第二套人员或审批表。

完成标准：官方测试应用、私聊和群聊各完成一次真实闭环；两名成员验证权限与审批；重连、事件重复和跨租户键冲突有自动化覆盖。缺少应用权限或测试环境只阻塞 Lark 的真实验收，不能假报通过。

v7.5.1 不顺带增加审批流平台、组织目录同步、跨平台账号合并或复杂群管理。

## 8. v7.6：QQ 官方机器人接入

### 8.1 先确认平台能力

实施前用届时官方文档及已开通应用核对：

- 支持的私聊、群聊或频道类型，稳定聊天及人员 ID 的范围。
- 接收机制、回调鉴权方式及是否需要公网入口。
- 普通群消息是否投递、主动消息与被动回复的窗口及次数限制。
- 是否支持可核验点击者的交互按钮，长任务完成后是否还能发送结果。

把结果记录为能力表；无法验证的项目为 NOT_RUN 或 UNKNOWN，不按其他框架的非官方适配行为推断官方支持。

### 8.2 按能力交付

- 使用官方接入方式复用空间、两层权限、消息路由、去重与执行核心。
- 支持实际开放的文字聊天类型；平台只投递唤醒消息时，就只保存这些消息并显示“上下文仅覆盖已收到的消息”。
- 支持可信交互按钮时复用审批；不支持时，待审批操作保留给本机 GUI/CLI 确认，并在 QQ 提示，不能用聊天确认码或无确认执行代替。
- 消息编辑不可用时发送有界进度和最终回复；完成后发送窗口失效时保留结果并在下一次合法查询返回，不能重跑任务以获得回复窗口。
- 对当前应用未开放的聊天类型明确 NOT_SUPPORTED，不增加非官方个人账号协议，不为跨过平台限制建设公网托管平台。

完成标准：至少一种声明支持的聊天类型完成真实接入、两层权限、操作/审批、状态查询与失败恢复；所有其他类型逐项列出状态。若只交付一种类型，发布说明必须直接写清，不能称为 QQ 全场景接入。

## 9. v7.7：同一工作区内跨对话并行

### 9.1 用户结果与范围

同一工作区内，GUI/CLI 的对话与外部渠道的另一个对话可以同时运行，建议默认最多两个前台 Run。同一对话仍只允许一个未结束 Run。跨工作区并行、消息队列和自动重试不在本版范围。

等待确认、停止或 UNKNOWN 的 Run 继续占用自身对话的未结束位置；是否占实际执行名额按执行状态判断，不能因为用户迟迟未批准就占住所有模型执行名额。后台命令与有限服务继续使用 v7.3/v7.4 的 Owner 级名额，不因开启第二个对话而翻倍。

### 9.2 核心改动

1. 把 `TaskService` 的单个取消函数、`activeChat`、ChatUI 单个 `active` 和单份事件回调改为按 Run/对话索引的有界运行状态；仍放在现有组件内。
2. 将 Run 执行互斥从 Owner 全局缩小到对话；配置提交、备份恢复与工作区切换保留全局独占边界，错误信息列出具体阻塞对象。
3. Stop 和权限撤销保留独立的短路径，不等待整个运行完成；避免配置锁、对话锁及事件回调形成反向等待。
4. 审批、模型事件、工具输出和渠道回复始终按 Run 路由；GUI 查看其他对话不改变后台任务的接收人和权限。
5. 父子任务累计预算、模型调用预算和命令/服务限制统一计数，不能把每个新前台 Run 当作绕过 Owner 上限的入口。
6. 复用 v7.4 已有沙箱授权兼容规则。共享 AppContainer 身份不能临时扩大其他运行进程的授权；不兼容配置继续明确 busy，不自动降级到宿主机。
7. 文件工具除核验修改前状态，还要在同一 Owner 内共享短时修改锁，覆盖最终哈希重查至发布/删除；不能把“检查哈希，再替换”当作原子比较与提交。批量操作逐项记录，多个工具实例和路径别名不能绕过同一锁；用可控交错验证两个 Run 修改同一文件时只允许一个基于旧哈希成功。命令或外部程序直接改文件仍无通用冲突保护。

### 9.3 验收与效率记录

- 两个不同对话真实重叠运行，同一对话的第二个请求被拒绝；第三个前台 Run 遵守名额限制。
- 停止 A 不停止 B；撤销 A 发起人的权限不影响 B 的合法工具调用；事件、审批和回复不串线。
- A 等待审批时 B 可继续工作；A 的批准仍绑定原动作和权限，不因 B 提高配置而变宽。
- 并行运行与备份、工作区切换、授权变更、服务启动/停止、Owner 退出及 UNKNOWN 恢复组合测试通过。
- 测量串行/并行的实际起止时间、重叠区间、请求拒绝耗时、内存与输出界限。报告测量环境和数字，不预先承诺“两倍提速”。
- 通过 Windows 原生竞态检查和 Linux race；实际沙箱配置不兼容时，正确拒绝也是契约验收，不能硬凑同时执行。

交付：同一工作区两对话并行的可用版本、实测效率数据和现有限制。若平台接入仍存在身份/审批串线问题，先修复这些问题，再开放并行。

## 10. 实施顺序与变更落点

| 顺序 | 主要变更位置 | 应先完成的可验证结果 |
|---|---|---|
| 1 | `store.go`、`permissions.go`、`execution_profile.go`、`apppaths` 与包脚本 | 空间归属、None、两层计算及新格式一致 |
| 2 | `taskservice.go`、工具执行入口、`control.go`、`command_sessions.go` | 身份进入既有 Run，直接调用也不能越权 |
| 3 | `internal/chatui`、`cmd/freeagent` 和 attach | GUI/CLI/AI 使用相同操作，无第二套业务状态 |
| 4 | Owner 装配和可选渠道适配代码 | Telegram 私聊真实收发及审批闭环 |
| 5 | `context.go`、`context_summary.go`、`context_compaction.go` 与消息投影 | 群背景可用，压缩不混入非公开结果或授权 |
| 6 | 新增 Lark、QQ 的薄适配器 | 平台差异封装在渠道层，核心规则复用 |
| 7 | `TaskService`/Store/ChatUI 运行状态及现有命令监督 | 并行运行正确，预算、权限、停止与输出不串线 |

每段采用“核心契约与负面测试 → 入口接入 → 实际操作验收 → 阶段记录”的顺序。先修复影响本段正确性的失败，再进入依赖它的阶段；不因某个外部凭据不足而放弃独立的本地工作。

## 11. 测试与发布规则

### 11.1 按改动选择检查

沿用仓库现有命令，以下是后续开发时要运行的检查，不是本次已经运行的结果：

```powershell
pnpm --dir internal/chatui test
pnpm --dir internal/chatui build
go mod verify
go vet ./...
go test -count=1 -timeout=5m -skip 'Live|RealProvider' ./...
go test -race -count=1 -timeout=10m -skip 'Live|RealProvider' ./...
./scripts/update-notices.ps1 -Check
```

- 功能阶段先运行相关测试；合并或发布候选运行完整相关门禁。测试通过后不在无新改动、无新问题的情况下反复重跑。
- ChatUI 改动同时运行 JS 测试、生产构建和原生 WebView2 检查；新数据格式必须实际走一次全新便携包首次启动。
- Windows race 必须实际在可用 C 工具链下运行，不能用 Linux race 或普通 Go 测试替代。未具备环境时记录 NOT_RUN 与所需条件。
- `scripts/test-portable.ps1` 与 `scripts/test-desktop-startup.ps1` 分别按脚本要求使用构建包和全新解压目录；不拿已经初始化过的包冒充首次启动测试。
- 权限与渠道路由主要使用确定性模拟 Provider 验证。v7.5 群聊/摘要涉及模型理解，补充一个实际可用 Provider 的代表性聊天与摘要验收；不顺带重测所有厂商。
- None 的 Chat/Responses/Anthropic 等请求构造覆盖所有现有适配器，尤其检查不会注入原生搜索、残留工具或未公开历史。这些构造测试不等于各厂商端点实测通过。
- 发布包记录源码版本、数据格式、SHA256、实际检查结果及已知限制，不能包含测试 Token、用户数据或测试群内容。

### 11.2 结果必须分开记录

| 状态 | 含义 |
|---|---|
| 已实现 | 代码存在，尚不等于验收通过 |
| PASS | 该版本和该场景实际运行并通过 |
| FAIL | 已运行但不符合要求，需要调查和修复 |
| NOT_RUN | 尚未实际运行；列出缺少的环境或执行步骤 |
| UNKNOWN | 已执行但结果或副作用证据不足，保留不确定状态 |
| BLOCKED | 必须由用户提供权限、凭据或外部平台改变条件后才能继续该项 |
| NOT_SUPPORTED | 当前明确不支持的能力，界面和发布说明同时披露 |

自动化测试可以 PASS，同时证明某种中断正确保留了运行时 UNKNOWN；两者不能混为一谈。每个版本的实施记录应列出源码、实测命令/环境、失败修复、平台支持矩阵和真实 Provider 未验收项。

## 13. 本轮之后的候选项

以下只保留为候选，不占用 v7.5–v7.7 的交付范围：

- 附件、图片和文件回传：先明确大小上限、可见范围、缓存清理和渠道实际能力，再进入单独计划。
- 每个对话按自己的工作区并行：需要重新审查现有全局配置、沙箱授权及资源冲突，不随空间功能自动开启。
- IPv6、长时持续运行、签名发布与额外 Provider：按实际用户需求补充相应验收；不能与当前渠道接入混成一次大重构。

本轮优先顺序固定为：当前发布收尾 → 统一空间与 None → Telegram 私聊 → Telegram 群聊 → Lark → QQ → 跨对话并行。平台阻塞可以调整无依赖工作的先后，不能改变权限与确认边界。
