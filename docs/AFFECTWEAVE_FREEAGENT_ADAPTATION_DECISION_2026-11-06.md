# AffectWeave 接入决策：整体 Go 重写，独立适配 FreeAgent

日期：2026-11-06。状态：方案修订；AffectWeave 产品实现未开始。

## 1. 结论

**采用整体 Go 重写，由 AffectWeave 仓库实现并交付独立 Go 扩展，主动适配 FreeAgent。** 人物规则、上下文编译、状态持久化和宿主适配全部进入同一套 Go 生产实现；FreeAgent 负责通用宿主契约及自己的管理界面。

选择 Go 的依据是统一长期维护、开发工具和双平台发行方式。`freeagent-ext/1` 仍是语言无关的 stdio JSON-RPC 协议，其他扩展继续可以使用 Python 或 Node。AffectWeave 的语言选择不改变 FreeAgent 的扩展边界，也不把人物业务编入默认 Core。

整体重写会增加前期实现和行为验证工作；只有完成切换后保持一套生产引擎，才能取得预期的维护收益。状态语义、PG、确认和真实交付仍需独立设计和验收。当前没有性能实测，因此不以“必然更快、更省内存或总成本更低”作为已证实结论。

## 2. 与保留 Python 方案比较

| 比较项 | 整体 Go 重写（采用） | 保留 Python 并适配 |
| --- | --- | --- |
| 前期工作 | 重写业务实现，迁写测试，并核对规则差异 | 复用更多源码，重点改造宿主契约与 PG |
| 后续开发 | 与 FreeAgent 统一语言、构建、测试和并发工具；人物业务仍在独立仓库 | 保留两种语言及各自依赖、发行工具 |
| 发行 | Windows/Debian 独立可执行文件，不需要用户安装 Go/Python | 可选包需要固定 Python 解释器与依赖 |
| 维护收益条件 | Go 成为唯一生产引擎，旧 Python 不再同步开发功能 | Python 是唯一人物引擎，仍需维护解释器和依赖发行 |
| Core 接入 | 仍须补实际缺失的输入、提案、交付和恢复接口 | 需要相同的宿主接口，语言不能替代这些工作 |
| 业务风险 | 要防止规则漏迁、数值/时间语义变化和错误简化 | 要防止原 Demo 的即时写回、JSON 回答格式渗入宿主 |
| 性能 | 启动、内存和并发开销有优化空间，实际收益待测 | 进程复用也能控制开销，实际差距待测 |

这里优先长期统一维护，接受一次性的重写和对照验证成本。不会同时维护两种语言的正式产品，也不为了支持旧 Demo 恢复 SQLite、旧 API 或数据迁移层。

本次没有运行 AffectWeave 基准或构建发行包，因此不提供虚构的工期、包体积、内存和性能差值。

## 3. 谁负责改什么

| 位置 | 应承担的内容 |
| --- | --- |
| AffectWeave 仓库 | Go 人物规则、ContextCompiler、FreeAgent 协议适配、PG 仓库、版本/幂等、持久提案、依赖锁定、测试及可选二进制包 |
| FreeAgent Core | 已采用输入与可信身份、有界上下文、现有模型/工具调用、控制确认、真实执行/投递事实的受限接口 |
| FreeAgent 前端 | v8.1 预留位置中的 AffectWeave 管理页和本轮能力选择；不加载扩展提供的任意脚本 |
| 两端共同验收 | 一组固定版本和合成场景：输入采用、重试、审批、工具、流式、取消、交付、重启、配套恢复 |

AffectWeave 的 Go 业务代码和适配代码在同一仓库演进，通过进程协议与 Core 连接，不导入 FreeAgent 的私有实现或直接链接人物模块进 Core。接口文档在 FreeAgent 维护，AffectWeave 声明所需协议和实际验过的宿主版本。

旧 Python Demo 固定到参考提交，保留源码出处、许可证、规则说明及合成输入/预期输出。迁写阶段可以离线生成对照样本；成品正常运行和发布测试不依赖启动 Python 引擎。原源码不必删除，但不再承担同步功能开发、生产回退或运行时兼容。

“整体”覆盖人物基线、情绪/中期状态、关系、人物经历、人物未决事项、上下文编译和全部生产入口。复用的是规则与测试意图，不是逐文件照搬；不迁写旧 SQLite 后端、Demo 专用包装及其不符合 FreeAgent 的即时写回行为。

## 4. 必须改造，不能靠包装隐藏的部分

1. **上下文读取与状态推进分开。** 原 `prepare_turn` 会修改聚合状态。重复预览、模型重试和同轮工具后补上下文不能再次推进人物；只对 Core 已采用的输入登记一次，并复用冻结版本。当前 `context.prepare` 尚未提供完整稳定输入/空间身份，不能用 invocation 或文本哈希代替消息身份。
2. **回答与持久提案分开。** 不强制 Core 把正常流式回答改成 Demo 的单个 JSON。人物分析按显式启用的预算调用 Host 模型；模型建议的长期变化先形成提案，再复用 Core 确认。
3. **执行结束与实际交付分开。** `turn.finished` 不证明 TG 发出、GUI 呈现或用户已读。扩展使用真实回执，支持部分交付、取消和 UNKNOWN，不能为补证据重新发送回答。
4. **PG 与事务内幂等。** 使用扩展自己的逻辑库和受限角色，可共用 PG 实例。状态更新和原控制操作结果在同一事务保存；ACK 丢失查原结果，不换新 ID 重做。不访问 Core 私表，也不引入双数据库产品后端。
5. **可信身份与作用范围。** 角色/关系/经历绑定 Core 提供的空间、参与者和事件身份，昵称或模型文本不能授权跨空间读取。
6. **生命周期与失败处理。** Go 进程按宿主要求启动、复用、取消和停止。RPC 收发与业务执行不能互相阻塞，调用使用有界并发和取消上下文；状态冲突、进程退出、未决写回须有明确结果。不为此另建调度框架。

迁写测试固定输入、时间和随机种子，离散状态/身份/版本结果严格比较，数值字段明确精度和容差。对照预期不能直接认可旧实现中的错误；因确认、交付或身份规则而有意改变的行为单列差异和新预期。完成这组 Go 回归后不要求长期运行两套引擎作比较。

## 5. 发行方式与已知约束

目标是 Windows 和 Debian 12 **独立可选 Go 二进制包**，包含 manifest、程序、必要静态资源、许可证和说明。用户不需要 Go、Python 或 Node；默认 Core 不启动该进程。工具链与 FreeAgent 基线对齐，固定模块依赖，优先采用不需要 CGO 的依赖；最终包实际检查系统动态库需求，不能只靠交叉编译认定兼容。

A1 验证最小 Go 进程通过现有握手和调用契约，`run.command` 指向包内入口；构建两个目标平台的样包并核对大小和目录安装。移动目录、空格/中文路径、退出清理和数据保留必须实测。若需要安装/卸载脚本，仅处理该扩展，不建设通用插件安装器或常驻管理服务。

源码核查仍需保留两项事实：

- 现有 `extensions.import` 是小目录复制入口，限制 **8 MiB、256 个文件**，不允许符号链接。Go 二进制也可能超限，改用 Go 不会自动消除这个约束。优先验证目录发行；若必须改导入能力，只增加有界安装能力，不取消通用限制。
- Python SDK 接受 `tools/call` 和 MCP 风格结果，而当前 Core 发出 `tool.call`，期望字符串 `content` 与 `is_error`。该缺口已实测，继续作为通用 Kit 修复项；Go 入口直接遵循当前 Core 契约，不依赖 Python SDK 修复才可开发。

FreeAgent 扩展指南增加经实测的 Go 最小样例和构建/协议调试步骤，不提前建设通用 Go SDK、代码生成器或模块生命周期平台。原有 Python/Node 文档服务其他扩展，保持语言无关的协议边界。

## 6. 收敛后的实施顺序

| 阶段 | 交付与退出条件 |
| --- | --- |
| v8.0.1 文档/接入准备 | 扩展开发指南；修正 SDK 工具契约差异并加入宿主联测，不扩大为新 SDK 框架 |
| A1 | 固定 Python 参考提交，列全量功能/规则映射和有意差异；冻结输入、提案、回执和恢复契约；Go 最小入口、样包和取消/并发探测通过 |
| A2 | 在 AffectWeave 仓库完成 Go 人物业务、上下文编译、协议入口和 PG 仓库；规则对照、重复输入、版本冲突和身份隔离通过 |
| A3 | 接入上下文、正常回答、确认和真实交付；完成 UNKNOWN/丢 ACK 恢复，不重复副作用 |
| A4 | 完整管理入口、包含 Go 样例的扩展开发指南、安装/排障文档和双平台 Go 可选包；保留用户数据完成更新/停用/恢复 |
| A5 | 真实多轮宿主验收，达到统一计划的完整成品范围后发布 AffectWeave FreeAgent 1.0 |

## 7. 验证记录与当前状态

此前基于 FreeAgent v8.0.0-dev.1，Windows 隔离目录中通过了 `ext new` 三类模板、三类 `ext check`、生成模板的上下文/工作流 mock，以及 SDK prompt-router、triage-cluster 的 mock；Python SDK 自带 2 项单元测试通过。SDK 工具分支差异另行实测确认，尚未修复。这些是现有扩展入口的证据，不是 Go 重写的验收结果。

AffectWeave Go 实现、Go 样例、PG 接入、真实模型、双平台发行和新宿主能力尚未完成。本次只调整实施方案并核对文档一致性，按统一计划的既定顺序开发，没有更新线上服务。
