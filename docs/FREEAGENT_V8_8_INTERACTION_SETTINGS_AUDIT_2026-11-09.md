# v8.8 设置保存、对话控制与上下文恢复核查

日期：2026-11-09。范围：v8.8.0-dev.1、Hytron 当前运行实例、React 设置界面与 Core 控制操作。

2026-11-11：本文件列出的 30 项已完成本地修复，第二轮复查另修复 14 组问题（31～44），收尾补齐确认读取、草稿重载和接续选项三组边界（45～47），已生成便携开发包。原核查与诊断证据保留，最新实现和验收状态见 [修复记录](FREEAGENT_V8_8_INTERACTION_REPAIR_2026-11-11.md)；下文“未修复”描述的是当时核查快照。代码尚未发布到 Hytron。

## 1. 结论

用户反馈成立。主要缺口在“找到设置 → 修改 → 确认 → 保存 → 回读 → 当前任务恢复”的完整路径，不能用“已有配置字段/接口”当作完成验收。

4,096 是摘要正文的 UTF-8 **字节**上限，不是模型生成的 token 上限。代码允许将其设置为 1～16,384；0 表示关闭自动压缩。目前全局设置确实能保存，但对话上下文面板没有保存入口，已有摘要会使面板继续显示旧上限；改变配置后，受限任务的继续与手动压缩还可能同时被拒绝。

另一个已实测的严重问题：保存模型窗口后，再保存同一模型的思考/能力草稿，会把窗口覆盖回旧值，界面却继续显示新值。

本次交付为核查结果及修正建议。未实施产品修复、发布或部署。下面明确区分实际复现、代码证据和有意保留的管理限制。

## 3. 优先问题

### P1-01：对话中的摘要输入框没有持久保存动作

**浏览器实际复现。** 打开“上下文管理”，把摘要上限改为 12,288，只有“手动压缩 / 重新生成摘要 / 清除摘要”；关闭重开恢复原值，服务端配置未变。该输入仅作为下一次手动压缩的参数。

全局“设置 → 工作台 → 上下文”存在“保存设置”，隔离浏览器和登录后的公网 API 均已成功保存 8,192。两个界面使用近似名称，却没有说明一个是临时参数、另一个是持久策略，也没有相互跳转。

位置：`internal/chatui/frontend/features/conversations/ContextPanel.tsx:20,71,156,182`；`internal/chatui/frontend/features/settings/RuntimeSettings.tsx:166,622,693`。

**修正：** 在对话面板显示当前 Core 默认值与本次压缩值，提供明确的“保存默认设置”和“仅本次压缩”。全局设置直接链接到同一字段；保存使用现有 `runtime.set_limits`，不要另建一份会话配置。自动压缩开关、触发比例和辅助思考设置也提供准确跳转。

### P1-02：保存成功后，旧摘要展示与受限任务恢复没有衔接

**隔离 Core + PostgreSQL 实际复现。**

1. 创建上限为 1,024 的旧摘要，将全局上限保存为 8,192；`ContextState.byte_limit` 仍为 1,024，因为读取时优先使用旧摘要的 `ByteLimit`。
2. 创建一个因上下文过长进入 limited 的任务，再通过正式控制确认保存新上限；“继续”和“手动压缩”均返回 `ErrConfigChanged`。这里不只是静默沿用旧值，而是旧任务快照与新配置比较失败。

位置：`internal/harness/context_summary.go:281`；`internal/harness/context_compaction.go:420`；`internal/harness/model_selection.go:390,470`；`internal/harness/service.go:579`。

**修正：** 分开返回/显示“旧摘要生成上限”“当前默认策略”“本次压缩目标”。出现受限任务时，提供使用已保存新配置进行压缩或新建后续执行的明确动作，复用现有维护请求/接续机制；保留旧 Run 快照与已执行证据，不能通过删除配置校验或重跑已完成工具来恢复。仍有 UNKNOWN、未决写入或审批时，先处理对应状态。

### P1-03：模型窗口和能力表单分开保存，后保存会覆盖先保存

**Chromium + 真实隔离 Core 实际复现。**

1. 模型窗口设为 131,072，点击“保存窗口”，服务端回读为 131,072。
2. 不离开页面，修改该模型“压缩 / 扩展分析思考”，预览并确认能力声明。
3. 后一份完整 `capabilities` 草稿携带旧窗口 0，服务端窗口被覆盖为 0。
4. 页面输入框依然显示 131,072，没有反映实际保存值。

`tokens` 与 `caps` 是两份独立状态。`useFormDraft` 只在首次挂载读取初值；保存窗口后的重新取数不会同步现存 `caps`，后续完整模型替换也未绑定编辑时版本。

位置：`internal/chatui/frontend/features/settings/Providers.tsx:596,600,627,657,884`；`internal/chatui/frontend/features/settings/shared.tsx:64`；`internal/harness/control.go:2830`。

**修正：** 模型窗口/能力使用同一份保存基线；每次只提交用户改动的字段，思考开关优先复用已有窄更新操作。提交携带编辑时版本；确认后同步服务器回读值。外部更新只自动刷新干净表单，有未保存草稿时显示冲突，不能清空草稿或静默覆盖。

### P1-04：AI 改设置依赖本身已经塞满的上下文

**线上记录 + 代码证据。** 控制工具存在，但一轮在模型能调用 `control_plan_change` 前已因压缩失败结束。再让模型“把摘要调大”仍需要先通过相同预算检查，形成使用上的死路。

`control_read_state` 无查询范围，自动带入当前扩展的整份状态。设置读取返回约 49 KB，其中约 44 KB 是扩展状态；TG 分支又把 `config.models` 等所需字段删掉。全操作目录还被重复放入工具描述。对于修改一个摘要数字，这些内容过大且不对题。

位置：`internal/harness/control_tools.go:64,96,119,137`；`internal/harness/context_prepare.go:47`。

**修正：** 设置故障必须有不需要先调用模型的直接操作入口。现有控制读取增加按领域选择与有界投影，只在明确请求扩展状态时读取它；模型设置返回授权范围内的当前模型、主回答/辅助思考及有效额度。目录按需提供具体操作 schema，避免每轮附送全目录。扩展详情仍由扩展负责，Core 只实现通用的选择与大小限制。

### P1-05：TG 能提设置变更，但没有可完成的确认路径

**代码明确限制。** 产品设置提案进入 waiting_confirmation 后，TG 提示“操作等待本机确认，请打开 GUI 或 CLI 查看”；按钮回调明确拒绝 `ControlOperationID != ""`。普通工具审批按钮不能用来确认产品设置。

这影响摘要上限、自动压缩、模型思考、工具配置、扩展开关等所有设置提案。不能把这一点描述成“TG 可以回复一句话完成设置”。

位置：`internal/harness/channel_runtime.go:519,664`。

**修正：** 最小交付先给出指向同一会话、同一待确认提案的已登录 Web 卡片链接，并返回真实应用结果。若提供 TG 内确认，必须复用同一提案协议并验证明确授权的管理身份；不能把任意已配对用户自动当成管理员。保留模型持久修改必须由用户确认的规则。

### P1-06：公网设置页与接口权限不一致，扩展尤其明显

**线上页面 + 隔离路由实测。**

- MCP、Skill、扩展管理控件按 `remote` 整块禁用。
- AffectWeave 页面仍请求 `/api/extensions/{id}/state`，但公网路由不允许，返回纯文本 404；前端变成“服务器没有返回有效响应”。
- “核对原操作结果”调用 `/api/control/reconcile-extension`，公网同样不允许。
- 人物页默认 `space=local, actor=owner, roleID=""`，未跟随当前 TG 会话作用域；空表单不能表示 TG 当前人物。

位置：`internal/chatui/public.go:98`；`frontend/features/settings/CapabilitySettings.tsx:74,398,553,669`；`AffectWeavePage.tsx:74,121,213`；`OperationHistory.tsx:45`；`frontend/lib/api/client.ts:81`（以上 frontend 位于 `internal/chatui/`）。

**修正：** 将正常管理操作接到已有控制面和鉴权；扩展状态提供受限查询，并从选中会话解析明确作用域。不能开放整个本机 attach API 作为快捷修复。确实需要本机的操作在编辑前说明原因和下一步；不要渲染成可操作却只能失败的界面。

### P2-07：多种非秘密操作被标为不可由模型提出

目录共 61 项，其中 13 项 `model_proposable=false`：

| 类别 | 操作 |
| --- | --- |
| MCP | `mcp.set_profile`、`mcp.remove`、`mcp.restart` |
| Key | `keys.set_profile`、`keys.remove`、`keys.probe` |
| Skill | `skills.import`、`skills.remove` |
| 扩展 | `extensions.import`、`extensions.remove`、`extensions.restart`、`extensions.clear_data`、`extensions.init_storage` |

`buildRecordLocked` 会返回 `operation is user-only`。启停现有 MCP/Skill/扩展的 policy 操作可以提案，但安装、删除、重启等不能，当前界面/对话没有统一说明这一区别。

**修正：** 对无秘密的管理操作允许模型提出精确提案，沿用现有预览、权限与危险操作确认。Secret 明文仍用专用输入，AI 可以引用已保存 Key 或引导用户填写，不能为了“对话能改”把秘密送进模型。无需新增一套审批系统。

### P2-08：多数可提案操作没有完整参数契约，部分当前值也读不到

**目录核查。** 48 个可由模型提出的操作中，45 个没有 `InputSchema`，其中部分仅在描述中列出参数。总工具的 `arguments` 只是任意 object。后台虽有严格校验，模型却不一定知道字段、必填项和范围。

`ControlConfigState` 也不是完整的安全设置投影：例如只给 HTTP 开关而无完整允许来源/超时；模型条目没有 context_window_tokens 等完整能力。TG 还有更严格的裁剪。故“目录中有该操作”不代表模型能可靠读改而不丢字段。

位置：`internal/harness/control.go:250,632,802`；`internal/harness/control_tools.go:73,137`。

**修正：** 在现有目录补齐常用设置的 typed schema、只读当前值、修改字段和生效范围；按需读取。优先摘要/压缩、模型、网络与工具，再补 MCP/扩展。不要把大而全的当前状态继续塞进每轮工具说明。

### P2-09：None 模式连设置读取/提案也一起隐藏

**隔离测试确认。** `operationsDenied` 在 None 下为 true，`runtimeTools` 直接返回无工具；`controlToolsEnabled` 也要求非 None。恢复到 Ask 后控制工具才出现。

这是现有权限语义，不是本次生产故障的原因（生产有控制工具）。但“仅聊天”用户也无法通过对话修改普通设置，界面未明确告知。

位置：`internal/harness/memory_tools.go:40,76`；`internal/harness/space_permissions.go:264`。

**修正：** 将允许读取/提出普通产品设置提案，与文件/命令执行权限分开判断；实际应用仍经现有管理权限和用户确认。不能借设置提案自动提升操作权限。

### P2-10：保存位置、有效额度和生效时间仍然分散

代码支持全局输出上限、模型输出上限、模型窗口、全局请求字节上限、摘要字节上限；有效模型输出/上下文额度会取相关限制的较小值。设置页缺少统一的“当前请求到底受哪个值限制”的解释。

公网 Memory 页面只显示已选内容的 JSON，没有本地页的创建/编辑表单；通用工作区选择依赖桌面桥，在普通浏览器只有文字引导；主题/布局属于客户端偏好，没有对话操作。公网最高权限的提高明确要求本机确认，服务器端口等需要重启，不能把这些都作为保存失败。

AffectWeave 的人物上下文字节草稿固定初始化为 `6000`，未从 `settings.context_bytes` 初始化；安装了扩展时，页面可能从一开始就没有展示当前已保存值。此项为代码确认，未另做扩展浏览器重放。

**修正：** 每个编辑入口标明目标（Core/空间/会话/客户端）、当前有效值和生效时机。普通浏览器提供工作区路径的受控提案；外观操作明确目标客户端。不同设置应明确“自动保存”“待保存”“需要确认”“重启生效”。公网禁止的权限提升保留边界，并说明具体本机步骤。

### P2-11：摘要失败后的提示、重试及恢复按钮不对应真实原因

**线上 + 隔离复现。** 非空但超长、正常 stop 的摘要失败没有写入同配置的跨轮暂停记录；同样参数再次压缩又产生两次调用。修复提示只再次要求同一字节上限，没有告诉模型上一次实际多少字节。硬预算提示统一建议调整思考/输出额度，即使当前辅助思考已经关闭。

位置：`internal/harness/context_fragments.go:13`；`context_reliability.go:86`；`context_prepare.go:150`；`frontend/features/conversations/ConversationPage.tsx:348`。

**修正：** 分清思考耗尽、摘要过长、固定工具说明过大、历史过长和配置冲突。给出对应字段及明确动作。超长摘要修复使用实测字节反馈和更保守目标；确定的同配置失败避免每轮重复消耗。保留原始记录，不直接按字节截断事实摘要，也不把 UNKNOWN 当成功。

### P2-12：现有“设置覆盖”测试证明不了保存可用

当前映射登记了 164 个配置字段和 61 个操作。`TestFrontendSettingsCoverage` 只核对字段/操作是否有页面目的地，不检查按钮、提交路径、鉴权、确认、回读或运行生效。该测试通过与本次缺陷同时成立。

位置：`internal/chatui/settings_coverage_test.go:177`。

**修正：** 保留轻量映射检查，同时为高频设置加入实际交互回归：打开 → 编辑 → 保存/确认 → 回读 → 关闭重开 → 新任务生效。模型窗口与能力的连续保存必须专测。将公网和 TG 的确认路径纳入同一批用例。

## 4. 常用设置入口核对表

“支持提案”表示 Core 有该能力，不代表任意模型每次都会正确调用；“TG 确认缺口”指产品设置提案普遍不能在 TG 里确认。

| 设置/操作 | 当前 Web 情况 | 当前 AI 对话情况 | 需要补齐 |
| --- | --- | --- | --- |
| 摘要字节上限 | 全局能保存；对话面板仅临时值 | 支持 runtime.set_limits；长上下文会先失败；TG 确认缺口 | 面板保存、准确回读、受限任务恢复 |
| 自动压缩开关/比例 | 全局能保存；面板只显示 | 支持提案；TG 确认缺口 | 面板直达与生效说明 |
| 默认输出/请求字节/重试 | 有保存入口 | 支持提案 | 与当前任务/模型实际限制对照；恢复旧任务 |
| 模型窗口 | 有独立保存按钮 | 可经完整模型配置提案；读取信息不完整 | 防止后续能力保存覆盖 |
| 主回答/辅助思考 | 在模型能力页预览确认 | 有窄更新；TG 当前模型详情缺失、确认缺口 | 同一保存基线、正确当前值与作用范围 |
| 模型能力/输出额度 | 可保存完整能力声明 | 支持模型配置提案 | 局部修改、编辑版本检查、显示有效限额 |
| Provider 启停/默认模型 | 有界面与控制操作 | 支持提案 | 生效回读；TG 确认缺口 |
| Key 新增/删除/测试 | 有专用界面 | 三项都是 user-only | 秘密输入留在专用表单；无秘密操作可提案 |
| 文件/命令/网络开关与策略 | 有保存或预览确认入口 | 支持提案；多项缺完整 schema | 不同权限层与有效策略说明；TG 确认缺口 |
| Memory 内容/固定 | 公网页只有选中项 JSON；部分会话选择另有入口 | 已有 Memory/固定操作，受范围和确认限制 | 公网受控编辑；可用入口与当前作用域 |
| MCP 新增/修改配置/删除/重启 | 公网管理禁用，本机有入口 | profile/remove/restart 不可提案；policy 可提案 | 非秘密字段提案与公网受控管理 |
| Skill 导入/删除/启用 | 公网管理禁用 | import/remove 不可提案；policy/publish 可提案 | 统一入口与确认；不要混同安装和启用 |
| 扩展导入/删除/重启/初始化 | 公网管理禁用 | 多项 user-only；policy/state 可提案 | 明确无秘密管理提案与受限接口 |
| AffectWeave 人物/分析/上下文 | 公网禁用区域，读取状态 404；默认作用域不对应 TG | 有通用扩展状态提案，但读取过大且确认缺口 | 修复扩展页自身状态与作用域，不下沉到 Core |

### P1-22：接口先返回已接收，随后校验失败，草稿和历史却都没有消息

**真实浏览器与独立 Core 实际复现。** 将每次最多附件数设为 2，界面仍允许连续上传并选中 3 个文件。填写文字点击发送后：

| 核对项 | 实际结果 |
| --- | --- |
| 提交 HTTP 响应 | 202，accepted=true |
| 后台结果 | 附件数量校验失败，仅通过事件提示“请求未完成，请核对任务状态和运行记录” |
| 输入框 | 文字已清空 |
| 本次附件选择 | 已清空 |
| 会话轮次 | 0，没有创建 Run |
| 原请求键查询 | found=false，没有可供接续的已接收记录 |

原因：`startBound` 在后台开始处理前即可返回 202；附件校验在 `submitWithOptions` 内、创建 Run 之前执行。前端把 HTTP 接收成功当作消息已经持久保存，立即清理草稿和请求键。它与上一轮的“回执丢失后附件未清理”是不同分支，不能只修其中之一。

位置：`internal/chatui/server.go:886`、`execution.go:79`；`internal/harness/taskservice.go:889`、`attachments.go:534`；前端 `ConversationPage.tsx:785`。

**修正：** 用现有请求键/Run 机制明确“持久接收”的时点；发生接收前校验失败时返回具体字段错误，异步拒绝时保留或恢复原草稿。前端上传前检查数量与总大小，不能只逐个校验文件；后台仍必须再次校验。不要为了此问题新增第二套任务队列或请求平台。

### P1-23：停用已选中的 MCP，会让原会话无法正常读取

**独立 Core + PG 实际复现。** 会话显式选择一个已启用的 MCP，读取正常；通过控制操作停用 MCP 后，`Chat()` 返回 `ErrStoreFormat`。显式将会话能力选择清空后，读取恢复。测试使用合法的合成 MCP 配置，未启动 MCP 进程。

原因：`selectedCapabilities` 会移除已停用的 Skill 与扩展，却没有移除已停用/已删除的 MCP；后续 validate 检查失败，被当作存储格式错误。`Chat()` 在读取消息前调用这一函数，因此可选能力失效连带阻断整个会话页面。

位置：`internal/harness/capability_selection.go:42,61`、`capabilities.go:134`、`chat.go:172`。

**修正：** 对 MCP 使用与 Skill/扩展一致的失效处理，历史保持可读；把不可用能力作为状态展示，后续派发仍拒绝使用被停用能力。禁止通过重新启用 MCP 才让用户访问自己的历史，也不能把用户主动停用操作误报为数据库损坏。

### P1-24：“从这里重新开始”绕过普通发送的草稿与防重复流程

**两种真实浏览器场景均复现。**

1. 选择一条用户消息重新开始，创建的新分支自动执行成功；输入框却仍留有已经发送的同一句内容。再次点发送，生成第二个独立 Run。本轮用 Echo 验证出现两轮，不执行实际文件/命令副作用。
2. 分支已创建，但创建响应被人为丢弃；页面显示网络失败。用户重复同一操作，因为生成了新的 request_key，Core 创建第二个不同分支，第一次创建的空分支仍然存在。

Core 的同键分支幂等已有测试和实现，本次问题是界面每次重试都换键，并在自动提交时未使用普通发送的 pending request 与成功清理路径。

位置：`frontend/features/conversations/ConversationPage.tsx:903,906,914,919`；`internal/harness/conversation_branch.go:76`。

**修正：** 分支创建和分支首条执行分别保留固定请求键，丢失回执时按原键核对；自动提交复用统一发送流程。接收后仅清理本次内容，失败保留原草稿。不得自动重放已确认执行的工具，也不能只在按钮上加短暂 disabled 作为完整修复。

### P2-25：分支静默丢失原会话的能力排除设置

**独立 Core 实际复现。** 全局启用一个合成 Skill，原会话显式选择空能力列表；从该会话消息创建分支后，原会话仍无 Skill，新分支却自动选中这个全局 Skill。

分支目前复制了模型选择，但未复制会话能力选择。没有显式选择记录的新本地会话回落到全局默认能力，因此从消息“重新开始”可能重新启用原会话排除的可选能力。这里只证明能力选择变化，没有证明越过空间或命令权限。

位置：`internal/harness/conversation_branch.go:197`；`capability_selection.go:22`；`capabilities.go:174`。

**修正：** 明确分支的配置继承规则，默认保留原会话的能力限制，再过滤已失效项；如果选择恢复全局默认值，必须在分支操作时明确显示。人物变体和本轮临时配置分别处理，不混同历史时点与当前默认。

### P2-26：无关配置修改也会把排队消息卡住，“恢复队列”不能解决

**独立 Core 实际复现。** 接收一条排队消息后，仅修改“下次启动的回环端口”，两次恢复队列都再次触发 `ErrConfigChanged` 并暂停，消息一直 pending。

原因：队列保存并比较整个 Config 的摘要，包含不影响该消息执行的监听设置；恢复按钮只修改 paused，没有更新绑定或给出重新核对的路径。

位置：`internal/harness/input_queue.go:170,523,545`；前端 `ConversationPage.tsx:1079`。

**修正：** 无关设置不应使待发消息失效；执行相关配置改变则提供明确的重新核对/重新绑定操作，或保留内容后取消重建。不能为了恢复直接忽略模型、权限、附件、接收人等真实绑定变化。提示应说明哪些配置不同，避免用户反复点恢复。

### P2-27：已经错过目标任务的插话，删除按钮返回成功却删不掉

**Core 与浏览器均实际复现。** 对已完成 Run 提交插话，记录状态为 `target_ended`。界面仍展示它并给出“删除排队消息”；点击后接口返回 200，但状态不变，卡片继续存在。连续调用取消也无效。

原因：前端展示 pending 和 target_ended，`CancelInput` 却只修改 pending。该记录不会再作为普通队列执行，界面也没有将它转换为新消息的操作。

位置：`internal/harness/input_queue.go:228,353,379`；前端 `ConversationPage.tsx:1049,1069`。

**修正：** 将 target_ended 视为可明确丢弃的保留输入；返回真实状态变化。可以提供“复制到输入框/作为新任务发送”，由用户决定，不能偷偷启动新的任务。

### P2-28：有思考选择的排队消息仍显示“转为引导”，但无法转换

**独立 Core 实际复现。** 即使只显式选择 Provider 默认，排队记录中的 Reasoning 仍非空；转为引导时返回“remove the override before using guidance”。现有队列接口没有编辑/移除这一选项的操作，前端却对排队消息普遍显示转换按钮。

位置：`internal/harness/input_queue.go:440`；前端 `ConversationPage.tsx:1062`。

**修正：** 根据消息的模型/思考/能力绑定说明哪些选项不能应用到当前 Run。转换时明确告知仅引入文字/附件并要求用户确认舍弃新任务选项，或者直接禁用并给出取消重发方法。不能静默改变正在执行任务的思考设置。

### P2-29：点击“新对话”后仍显示上一会话的待发消息

**真实浏览器复现。** 在含 target_ended 消息的 A 会话点击“新对话”，地址栏已无 chat 参数，页面尚无选中会话，却继续显示 A 的队列消息及操作按钮。

切换会话会重置多种状态，但没有清空 inputs；读取队列的 effect 遇到空 selected 直接返回。跨会话加载期间也可能短暂展示旧数据。

位置：`frontend/features/conversations/ConversationPage.tsx:443,497,520`。

**修正：** 队列展示显式绑定所属 conversation ID；新对话/切换会话时先清空或展示加载态，只有结果身份匹配才显示可操作内容。不能继续用当前 selected 去操作上一会话留下的卡片。

### P2-30：已有会话尚未加载完成时发送，会意外创建新会话

**真实浏览器受控延迟复现。** 打开带 `?chat=...` 的既有会话页面，延迟首次导航列表请求。模型列表已经载入，输入框和发送按钮可用；此时发送消息，系统另建一个会话并在其中执行，原目标会话仍为 0 轮。

初次启动等待 environment 和 navigation 完成后才从 URL 选择会话；`ensureChat` 把暂时为空的 selected 当成用户明确选择了“新对话”。这是初始化状态与用户意图区分不足，不是 Core 擅自跨会话写历史。

位置：`frontend/app/App.tsx:156`；`frontend/lib/store/runtime.ts:408`；`frontend/features/conversations/ConversationPage.tsx:558,1268`。

**修正：** 区分“明确的新对话”和“指定会话仍在加载”。目标会话及权限尚未确定时保留输入，但暂不提交；加载失败给出重试，不自动换成新建会话。附件上传也走 ensureChat，须纳入同一边界回归。
