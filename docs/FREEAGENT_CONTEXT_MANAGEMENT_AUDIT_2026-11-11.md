## 1. 本次两个问题的结论

### 1.1 Telegram 的裸 `/new` 确实不能正常新建

`channel_runtime.go` 将 `/new` 后的参数直接拼成标题，裸命令得到空字符串；`Store.CreateConversationInSpace` 拒绝空标题。错误最终统一替换成“对话不属于此空间、正在运行或参数无效”，没有告诉用户真实原因。

生产空间已经开启多对话，仍然只有一个会话；记录中存在多次裸 `/new`。因此这次不是没有开启 `/multi on`。

临时用法是 `/new 新对话`。本机验证了带标题可以创建，未向生产 Bot 发送此命令。修正应支持无标题新建，并返回新会话名称和切换结果；创建与设为当前会话也应作为一个操作处理，避免创建成功、切换失败却报告“未更改”。

依据：[命令处理](../internal/harness/channel_runtime.go)、[创建会话](../internal/harness/store.go)、[空间切换](../internal/harness/spaces.go)。

### 1.2 最近一次“超过上下文硬预算”实际是消息分组失败

生产采样时间为 2026-11-11 23:39（北京时间）。最近一次受限任务发生在 23:29–23:32。其最后记录的主请求：

| 项目 | 实际值 |
| --- | ---: |
| 序列化请求 | 93,031 字节 |
| 输出预留 | 16,384 字节，即 4,096 tokens × 4 |
| 本地字节上限 | 131,072 字节 |
| 可用输入空间 | 114,688 字节 |
| 占用比例 | 82% |
| `over_limit` | false |
| 自动压缩阈值 | 80% |
| 当时摘要上限 | 10,240 UTF-8 字节 |
| 辅助思考 | disabled |

即 **93,031 + 16,384 = 109,415 < 131,072**。这是触发预防性压缩，并未触及该请求的本地硬预算。

生产历史中反复出现以下排列，插入项的元数据确认是 Telegram 已发送内容的回传镜像（`Channel.purpose=delivery`、`run_id=NULL`）：

```text
assistant：发起 command_run
assistant：TG 已发送内容的回传镜像
tool：对应 command_run 的结果
```

主请求按 `historyBound(run)` 和当前 Run 选择消息，会排除本轮开始后写入的这些回传镜像。压缩器却按消息 ID 前缀读取全部非 Deferred 记录，没有复用同一条选择规则。它在遇到每条 assistant 消息时切组，于是把一个完整工具调用拆开。

随后发生三次错误转换：

1. `completeMessageGroups` 报消息协议边界不完整。
2. `summaryChunk` 将它改成 `ErrContextLimit`，`applyCompaction` 又按“超大消息组”尝试分片；分片遇到同样的不完整组仍报 `ErrContextLimit`。
3. 该错误不在预防性压缩可回退类别中，任务被停止；TG 再按错误字符串包含 `context` 和 `budget`，显示“超过硬预算”。

独立 PG 复现结果：完整工具组的 **2,075 字节**请求被接受；插入一条回传镜像后的 **2,386 字节**请求，压缩与分片均报上下文超限，且没有模型调用、不能回退。这与线上消息结构一致。

另一个复现确认：本轮历史过滤后有效，下一轮扩大可见边界后同一镜像会重新进入历史，导致 `ErrModelBoundary`。因此修复需要处理已有历史的读取方式，不能只阻止未来插入。

该任务共有 7 次压缩模型调用，全部正常结束并返回非空摘要；最后 4 次分片摘要为 7,344–7,861 字节，均小于 10,240 字节。最终失败不能继续归因于“压缩思考耗尽输出额度”。之前另一次任务确有摘要 4,096 字节约束及输入超限问题，两次原因应分别记录。

依据：[回传入库](../internal/harness/channel_messages.go)、[历史读取](../internal/harness/context_summary.go)、[压缩分组](../internal/harness/context_compaction.go)、[分片](../internal/harness/context_fragments.go)、[回退](../internal/harness/context_reliability.go)、[TG 状态映射](../internal/harness/channel_status.go)。

## 2. 当前上下文到底由什么组成

持久历史、送给模型的上下文、长期 Memory、扩展内部状态是四种不同对象。数据库保留全部执行记录，不意味着每次全部发送给模型；摘要也不是 Memory 或成功执行的证据。

主请求大体按以下过程构造；扩展可以插到 system 后或当前用户输入之前，step 扩展可追加尾部：

```text
Run 冻结的配置、模型、权限、能力和来源
  → 系统约束 + 自定义提示 + 指令文件 + UNKNOWN 提醒
  → 已保存的历史摘要
  → 显式选择/固定的 Memory 与知识条目
  → 摘要覆盖位置之后的历史 + 当前 Run 的消息与工具结果
  → Skill 索引/手动调用正文 + 扩展 turn/step 上下文
  → 文本附件/图片 + 运行时工具定义
  → 预算测量 → 必要时压缩并重建
  → Provider 协议适配、发送和实际 usage 记录
```

### 2.2 三个自动压缩入口

它们最终复用压缩执行函数，但触发和失败处理并不完全一致：

| 入口 | 触发 | 当前特征 |
| --- | --- | --- |
| `buildContext` | 历史读取超限或摘要失效 | 构造主请求前尝试压缩/刷新；不采用完整的预防性失败回退流程 |
| `prepareContextRequest` | 占比达到阈值 | 先缓存本步扩展/附件材料；压缩重建不重复触发 hook；检查抑制、可回退错误和有效缩减 |
| `dispatchModel` | Provider 明确报告 context_limit，且没有正文/工具输出 | 计入恢复额度，压缩并重建后最多进行这一轮上下文恢复重试 |

另有手动维护，以及 Auto 模型候选探测中的“假设压缩后能否放下”判断；后者不实际调用摘要模型。

## 3. 限额清单：必须区分单位与作用范围

| 设置/约束 | Hytron 当前值或代码值 | 含义 |
| --- | --- | --- |
| `max_context_bytes` | 生产 131,072 字节 | 本地请求预算，默认 128 KiB；不等于厂商模型窗口 |
| 模型 `context_bytes` | 生产未设置 | 设置后只能进一步收紧当前全局字节上限 |
| 模型 `context_window_tokens` | 生产未设置/0 | 未启用模型 token 窗口核算；没有根据模型名称自动获得官方窗口 |
| `max_output_tokens` | 生产 4,096 tokens | 单次输出额度；没有 token 窗口时还按 ×4 换算成字节预留 |
| 模型 `output_tokens` | 生产未设置 | 设置后与全局输出额度取较小值 |
| `auto_compact_percent` | 生产 80% | 预防性压缩触发比例；允许范围 50–95 |
| `task_summary_bytes` | 生产 10,240 字节；默认 4,096 | 新摘要的保存上限，同时正数开启自动压缩、0 关闭；不是主请求额度 |
| 摘要硬边界 | 代码 16,384 字节 | 可配置摘要上限的最大值；摘要元数据记录最多 128 KiB |
| `history_page_size` | 生产 40 条 | 每页数据库读取大小；会继续翻页，不能用它限制总历史长度 |
| 历史读取保护 | 代码 16 MiB / 65,536 条 | 装配未压缩尾部时的内存保护，另于模型窗口 |
| 工具结果 | 生产 `max_tool_result_bytes=65,536` | 单个工具结果界限；多次结果仍会累积 |
| 命令/HTTP 输出 | 代码默认各 32,768 字节 | 各适配器自己的输出捕获上限，不能与全局工具结果上限混为一谈 |
| Memory | 生产最多 16 条、上下文 16,384 字节、单文档 65,536 字节 | 文档可保存大小与单次可注入大小不同 |
| 固定 Memory | 代码单条 2,048、合计 8,192 字节 | 还受 Memory 条数和总上下文限制 |
| 扩展上下文 | 生产最多 16,384 字符 | 这是字符，不是 UTF-8 字节；中文可能约占三倍字节 |
| 扩展附加模型调用 | 生产每轮最多 10 次 | 调用次数预算，不是历史窗口 |
| 路由/协作/核查输出 | 代码分别有 512 或 2,048 tokens 上限 | 调高主请求输出额度不保证这些辅助请求同比提高；思考模式需单独核对 |

当前字节模式的可用输入为 `131072 - 4096×4 = 114688` 字节，80% 阈值约为 91.8 KB。代码先向上取整占比再比较阈值，因此会在略低于精确 80% 的位置触发。

如果配置 token 窗口，token 输入预算是 `窗口 - 输出预留 - max(128, 窗口的5%)`，同时仍检查字节上限。仅填写更大的 token 窗口，不会解除较小的本地字节约束。

当前估算来自内部 `ModelRequest` JSON；实际 Provider usage 单独保存，二者不能当成同一数值。图片在消息 JSON 中使用 `json:"-"` 排除，再单独计入编码大小，本次未发现图片因此被重复计字节。

## 4. 设置与手动操作的实际含义

| 用户操作 | 当前作用 | 需要避免的误解 |
| --- | --- | --- |
| GUI 上下文面板“保存默认设置” | 保存 Core 默认摘要字节上限并开启自动压缩 | 不立即替换已有摘要，也不等于所有活跃 Run 立即采用新配置 |
| GUI 设置 → 上下文 | 保存自动开关、触发比例、全局字节/输出等预算 | 模型自己的上限仍可更小 |
| Provider 模型设置 | 保存模型窗口、输出额度、主/辅助思考 | 主回答思考与压缩/扩展分析思考分开；继承不代表一定关闭 |
| “仅本次手动压缩” / CLI `context compact` | 对本次维护采用指定摘要上限 | 不自动保存为全局默认；没有可压缩前缀时可能无需更新 |
| “重新生成摘要” / `refresh` | 从已有摘要覆盖的原始记录重新生成 | 不等于把所有最新消息一起压缩 |
| “清除摘要” / `clear` | 移除摘要选择，保留完整原始历史 | 可能增加下一请求上下文，不能当成清空会话 |
| TG `/compact` | 使用选定模型和当前维护配置压缩可用历史 | 当前命令不提供摘要字节参数，且仍受相同消息分组缺陷影响 |
| AI `context_manage` | 可检查、提议 compact/refresh/clear | 持久修改需确认；有未决工具/UNKNOWN 时不能绕过阻塞 |
| AI `runtime.set_limits`、`model.set_profile` 提案 | 可修改运行预算、摘要、模型窗口和辅助思考等 | 需要先能运行到控制工具；历史已经无法构造时，普通聊天提案也可能走不到 |
| `/new` | 新建独立会话上下文，切换该空间当前会话 | 不删除旧会话、全局/工作区 Memory 或扩展数据库；新会话注入仍按授权和选择决定 |
| 受限后继续 | 在已确认的安全边界接续；必要时用新快照的后继 Run | 不能为了采用新设置自动重放 UNKNOWN 或已经完成的副作用 |

源码已有保存入口，生产摘要值也已经变为 10,240。这次应先修复消息流与恢复逻辑，不能再笼统判断“页面没有保存”。同时，界面应更明确显示“Core 默认”“当前 Run 冻结值”“本次维护值”，减少用户保存后预期与实际不一致。

## 5. 问题优先级与修正建议

### P1：先修正确性与恢复通路

1. **统一主请求、摘要和分片的消息投影。已由生产元数据与独立测试确认。** 依据工具调用 ID/Run 和真实记录重建完整组；渠道投递镜像作为独立记录参与展示/公开对话投影，不打断工具协议，不重复当成主模型回答。原始消息及投递证据保留。对旧历史读取也生效，权限投影必须先明确，不能用无差别丢消息掩盖问题。
2. **拆开错误类别，恢复不能误放行。已确认。** 工具组不完整、历史读取保护、固定输入过大、真实模型窗口满、摘要生成失败应有不同原因。预防性压缩失败时，只有重建的主请求仍有效、未超限、权限及状态校验通过才可继续；数据库/权限/UNKNOWN 错误仍停止。禁止把所有 `ErrContextLimit` 自动当成可分片的大内容。
3. **修复裸 `/new`。已确认。** 默认标题、准确错误、原子创建并切换；同时验证原会话有运行任务时新会话和任务归属，避免暗中取消或迁移原任务。
4. **补全压缩抑制的退出条件。代码确认，其中配置指纹已复现。** `prepareContextRequest` 遇到抑制会直接跳过压缩，硬预算时也一样；指纹包含模型、辅助思考、输出额度与摘要大小，却未包含输入字节/token 窗口。应明确暂停的是预防性压缩；到达硬预算时根据原因与是否有有效修复执行一次有界恢复或给出精确阻塞，不能恢复无意义同参循环。预算配置变化要正确失效旧抑制。最近这条生产会话没有抑制记录，此项不是本次直接根因。

### P2：降低误触发与交互成本

5. **区分本地请求大小与厂商 token 窗口。** 生产模型没有填写 token 窗口，实际由 128 KiB 本地限制控制。明确显示生效的较小上限与来源；厂商窗口只采用已核实的声明。不要通过不断增大输出预留解决输入不足——字节模式下这反而减少可用输入。
6. **预算分项按真实来源统计。** 当前只有 instructions/tools/summary/history/current_input/images；Memory、Skill、扩展及协议接续数据混在其中。`current_input` 只认最后一条 user，工具循环中用户原始目标被归入 history，step 扩展尾部则可能被标成 current_input。应追踪来源，显示持久数据、实际发送文本和协议开销；内部 JSON 大小继续标为本地估算，不能冒充厂商 token 计数。
7. **工具结果占用和压缩频率一起治理。** 本次任务工具消息累计约 140 KB，单条序列化消息最大约 58 KB；两次命令正文约 41 KB。优先让可分页工具/输出预览提供有限片段和后续读取入口，完整结果继续留在证据中；不能任意裁掉当前必要工具结果。压缩应先验证全部待处理组，避免到后面才发现结构错误、浪费前面的摘要调用。保留最终原子提交，不引入第二套摘要数据库。
8. **统一三个自动入口的策略，保留用途差异。** 复用相同投影、预算结果、错误分类和恢复决策。主对话、摘要、路由/协作及扩展分析仍保留各自输入边界；不把所有辅助请求强行塞进完整聊天历史。
9. **把用户能采取的动作与错误匹配。** 消息分组错误应明确说明，不能建议修改思考档位；摘要过长提示摘要上限；真实输入满则指出历史/工具/附件/固定上下文中谁占用。展示上次测量时间、Run、实际配置与新的默认配置，避免把上次请求占用当成实时值。

### 保持轻量 Core 的边界

修正应收敛在现有消息读取、请求装配、预算和摘要模块内：一个公共投影入口、一组结构化错误、一个恢复决策即可。AffectWeave 的人物、情绪、关系、记忆选择仍在扩展中；Core 只接收有来源和额度的上下文块。经验总结仍是可选能力，不能用它代替主会话压缩。无需增加新的向量库、常驻上下文服务或多层摘要编排器。
