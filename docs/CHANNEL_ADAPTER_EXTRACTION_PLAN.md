# 渠道作为可选进程插件的拆分方案

状态：设计草案，尚未实施渠道拆分。依据 2026-11-05 用户提出的轻内核与多核心需求。
本轮输入交互修正独立完成，不将渠道重构混入补丁。
统一的后续版本安排见[设置、恢复与 PostgreSQL 计划](FREEAGENT_NEXT_CORE_SETTINGS_RECOVERY_POSTGRESQL_PLAN_2026-11-05.md)。

## 目标与已核实的现状

默认 FreeAgent core 不包含 TG、QQ、Lark 的平台实现、凭据配置、连接管理和管理页面。
需要渠道时再安装渠道包；多个 core 不各自连接同一 Bot。GUI、CLI、渠道继续共用
核心的会话、空间、消息、Run、权限、审批与执行记录。

用户确认的原则：**core 负责处理，渠道进程负责传递**。渠道侧是平台传输适配层，
不再有一套上下文、Agent 执行或业务权限内核。

目前关闭渠道已能避免网络连接，但 `cmd/freeagent/owner.go` 仍创建三种运行时，
`internal/harness` 直接引用 `internal/channels`，core 配置也包含平台字段。
因此仅隐藏设置或把默认值设为 false，达不到“不编入核心、不由每个 Owner 创建”的目标。
尚未测量拆分后的体积、RSS 或启动耗时，不提前宣称能节省多少资源。

## 建议的边界

| 部分 | 保留职责 |
| --- | --- |
| core | Provider 与工具执行、会话/空间绑定与消息、上下文和压缩、Memory/Skill/固定内容选择、输入采用、准入/权限/审批、执行重试和事实记录 |
| GUI / CLI | 核心的交互入口，可按发行组成提供；默认包没有渠道设置、渠道命令或平台后台对象 |
| 可选渠道进程 | Bot/API 凭据、平台事件验签、长轮询/WebSocket/Webhook、真实账号/聊天/发起人/消息标识传递、按配置转发到 core、附件传输、输出格式转换和投递回执 |
| 服务发行组合 | 同一 core 加渠道可执行文件和部署示例；用户显式配置和启动，不复制一份执行内核 |

插件采用独立可执行进程和有版本的窄接口。优先复用现有 Owner 请求、事件与 receipt
机制；不依赖 Go `.so`、平台 ABI、动态代码载入、插件市场或一套新的生命周期平台。
进程由现有 systemd、容器或用户命令管理，不在 core 中再实现进程编排器。

统一链路为：平台消息 → 渠道进程 → core 处理 → core 输出 → 渠道进程 → 平台。
渠道把正文、来源身份、附件和确认按钮事件交给 core；core 解释请求并决定可用内容与
动作，渠道按平台能力渲染回复、分段或上传附件。渠道不拼 system prompt、不压缩历史、
不选择模型/Skill/Memory、不执行工具、不判断审批有效性，也不触发模型执行重试。

同一 core 会话、同一身份授权和同一能力选择使用同一上下文规则。TG 只是一个入口，
不能仅因入口名称就屏蔽全部 Memory、Skill 或固定内容。空间与内容的可见范围由 core
统一校验；渠道只获得允许投递的输出，不需要拿到内部完整上下文。

## 一份渠道连接对接多个 core

一个渠道进程维护各平台账号的连接，按明确配置把聊天/空间绑定到一个 core。
每个 Bot 账号只有一个负责消费更新的进程，避免多个 core 争抢 Telegram getUpdates。
后续可以增加绑定目标，不提前建设自动发现、负载均衡、跨核心调度或组织平台。

每个 core 保留独立数据目录和自己的 Owner。渠道进程通过受限接口提交、查询状态、
接收事件和回传附件；禁止直接读写 core 的数据库。对话、权限和执行证据仍只有一份
事实来源，不在插件中重建 Task/Run/审批对象。

## 必须一起落实的权限与可靠性

- 不把 GUI 管理员令牌或全权限 attach secret 交给插件。渠道授权限定来源、平台账号、
  允许绑定的空间和可调用操作；模型不能伪造平台发起人或调用插件管理接口。
- 插件验证平台事件真实性；core 根据受信入口、真实发起人、空间和当前权限裁决。
  准入不等于工具权限，普通请求不能携带任意“我是管理员”或任意提升的权限值。
- 平台事件 ID、核心请求键和回传 receipt 保持关联。连接断开和消息超时不自动推出
  “未处理”；已关联 Run 不重建，结果未知的发送不盲重发。
  渠道网络重连和平台投递属于传输恢复；模型/工具重试由 core 决定，两个恢复不能互相触发。
- 文件与图片经过既有附件边界和新会话绑定；插件不能提交任意主机路径绕过核心授权。
- 设置及安装信息由用户显式调整；模型提出的持久修改继续走既有管理员确认机制。
- GUI/CLI 在运行中先排队、可手动引导；TG 普通消息直接插话。同一输入核心支持明确
  的操作类型，默认策略保存在 core 的入口绑定配置中，由 core 处理。渠道只传递来源和
  用户明确动作，不持有另一份运行状态来决定排队或插话。

## 实施顺序与验收

1. 先整理 core 的通用入口契约，把平台类型从 Harness、默认配置和核心 UI 分离。
   保留可组合的执行库；`go list -deps` 应证明默认核心不依赖平台实现。
2. 提取渠道进程，先让 Telegram 通过窄接口完成准入、同一空间接续、插话、停止、
   审批和附件回传。准入/空间绑定/审批处理在 core，平台按钮和连接表单随渠道包提供。
   移除 core 里按 TG/Lark/QQ 名称直接跳过私有上下文能力的特例，改为统一身份、空间与
   内容授权检查；同一授权条件下 GUI/CLI/TG 应使用相同的已选 Memory/Skill/固定内容。
3. 提供默认 core 包与可选服务组合。测试默认 core 启动无渠道对象、网络连接、平台
   凭据或配置入口；启动多个 core 也不重复创建 Bot 连接。
4. 做断线、重复更新、Owner/插件分别重启、权限撤销、跨空间拒绝和 UNKNOWN 回归，
   实测体积、空闲 RSS、启动耗时，记录真实变化。QQ/Lark 只保留已实现的适配和模拟
   回归，不声称完成新的真实平台验收。
5. 最后才更新 Hytron：核查任务和备份，用户明确编辑渠道配置及空间绑定，停旧轮询
   后启新进程。原会话与权限保留；没有兼容旧平台的运行时迁移层，也不同时启动两个
   Bot 消费者。失败时恢复原部署，切换前后分别核对真实 TG 收发。

验收重点是默认核心确实没有平台依赖，渠道连接独立且只运行一份，消息及权限没有
分裂成第二套核心。通用入口变小之后，其他可选重能力也可沿同样边界独立演进。
