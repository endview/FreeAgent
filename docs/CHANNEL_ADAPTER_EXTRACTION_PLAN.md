# 渠道作为可选进程插件的拆分方案

> 本文保留 2026-11-05 的拆分设计与当时状态，当前实现以[渠道指南](CHANNELS.md)为准。v8.5.1 的平台依赖回收按[轻内核整改计划 C 批](FREEAGENT_CORE_BOUNDARY_REFACTOR_PLAN_2026-11-08.md)推进。下文“已发未回执”的旧重投取舍已修正：纯准备可重算，实际发送 UNKNOWN 不自动重投。

状态：设计草案，尚未实施渠道拆分。依据 2026-11-05 用户提出的轻内核与多核心需求。
本轮输入交互修正独立完成，不将渠道重构混入补丁。
已同步 2026-11-05 两轮 review；先做 v7.14 执行恢复，v7.15 交付渠道拆分与通用固定内容。
统一的后续版本安排见[设置、恢复与 PostgreSQL 计划](FREEAGENT_NEXT_CORE_SETTINGS_RECOVERY_POSTGRESQL_PLAN_2026-11-05.md)。

## 目标与已核实的现状

默认 FreeAgent core 不包含 TG、QQ、Lark 的平台实现、凭据配置、连接管理和管理页面。
渠道可选包随发行包提供、默认不启用；默认一 Bot 对应一个 core，多个 Bot 共用 core 须显式配置。
首版每个渠道进程只服务一个 core，同一个 Bot 不由多个 core 重复连接。GUI、CLI、渠道继续共用
核心的会话、空间、消息、Run、权限、审批与执行记录。

用户确认的原则：**core 负责处理，渠道进程负责传递**。渠道侧是平台传输适配层，
不再有一套上下文、Agent 执行或业务权限内核。

目前关闭渠道已能避免网络连接，但 `cmd/freeagent/owner.go` 仍创建三种运行时，
`internal/harness` 直接引用 `internal/channels`，core 配置也包含平台字段。
因此仅隐藏设置或把默认值设为 false，达不到“不编入核心、不由每个 Owner 创建”的目标。
尚未测量拆分后的体积、RSS 或启动耗时，不提前宣称能节省多少资源。

## 建议的边界

| 部分 | 保留职责 |
| --- | --- |
| core | Provider 与工具执行、会话/空间绑定与消息、上下文和压缩、Memory/Skill/固定内容选择、输入采用、准入/权限/审批、执行重试和事实记录 |
| GUI / CLI | 核心的交互入口，可按发行组成提供；默认包没有渠道设置、渠道命令或平台后台对象 |
| 可选渠道进程 | 仅使用所绑定 core 按需交付的渠道凭据、平台事件验签、长轮询/WebSocket/Webhook、真实账号/聊天/发起人/消息标识传递、转发到该 core、附件传输、输出格式转换和投递回执 |
| 发行组合与启动器 | 同一 core 加随包渠道可执行文件；服务器用独立 systemd 服务，桌面仅做启停和就绪检查，不复制执行内核 |

插件采用独立可执行进程和有版本的窄接口。优先复用现有 Owner 请求、事件与 receipt
机制；不依赖 Go `.so`、平台 ABI、动态代码载入、插件市场或一套新的生命周期平台。
服务器渠道作为独立 systemd 服务运行；桌面由启动器管理已启用的渠道，生命周期跟随
Owner。设置只做启用和状态显示，不提供下载/升级管理。启动器只管理随包 PG 和已启用
渠道的启动、就绪检查、有序停止，不做通用进程编排。桌面最后一个 GUI/CLI 断开且无
其他已认证 Web 客户端、运行中任务、待确认或存活后台命令时才自动退出，渠道随之下线。
仍有工作时默认保留 Owner；可交互关闭时明确区分仅断开与停止并退出，意外断连不授权
停止。退出规则及竞态验收统一采用[主计划 §4.1](FREEAGENT_NEXT_CORE_SETTINGS_RECOVERY_POSTGRESQL_PLAN_2026-11-05.md#41-桌面客户端与-owner-的退出规则)。
v7.15 先落实已有依赖，v8.0 再把自管 PG 加入最后停止；外部 PG 不归启动器关闭。
单个客户端退出不能停掉其他客户端仍在使用的 Owner，服务器不因客户端断开而自动退出。

统一链路为：平台消息 → 渠道进程 → core 处理 → core 输出 → 渠道进程 → 平台。
渠道把正文、来源身份、附件和确认按钮事件交给 core；core 解释请求并决定可用内容与
动作，渠道按平台能力渲染回复、分段或上传附件。渠道不拼 system prompt、不压缩历史、
不选择模型/Skill/Memory、不执行工具、不判断审批有效性，也不触发模型执行重试。

同一 core 会话、同一身份授权和同一能力选择使用同一上下文规则。TG 只是一个入口，
不能仅因入口名称就屏蔽全部 Memory、Skill 或固定内容。空间与内容的可见范围由 core
统一校验；渠道只获得允许投递的输出，不需要拿到内部完整上下文。

## Bot 与 core 的默认关系和支持范围

默认一 Bot 对应一个 core。首版一个渠道进程只绑定一个 core，只接收该 core 的凭据
和授权；同一 core 的多个 Bot 可显式共用其渠道进程，不同 core 使用各自的渠道进程。
用户显式配置后，一个 core 可以同时接多个 TG Bot、Lark、QQ，不自动合并新增 Bot。
每个 Bot 账号只有一个负责消费更新的进程，避免多个 core 争抢 Telegram getUpdates。
首版不支持渠道进程跨 core 共享、一个 Bot 分发到多个 core，也不支持同一对话同时
绑定 TG/Lark 等两个外部聊天。每个渠道进程只跟随其所绑定 Owner 的启停。
对话归属于创建它的渠道空间，GUI/Web 可以接着聊，回复仍回传原空间；上下文可见范围
也沿用该空间，不能因换到 GUI/Web 就把私人内容带到群里。

当前只实现渠道需要的窄接口。未来知识库及其他 agent 接口保留版本号、能力授权、
禁止直接读写其他 core 数据库的原则，是否复用渠道入站接口在实际需求出现后再定，
不预先承诺共用同一个协议。本轮不建设自动发现、负载均衡、跨核心调度或组织平台。

每个 core 保留独立数据目录和自己的 Owner。渠道进程通过受限接口提交、查询状态、
接收事件和回传附件；禁止直接读写 core 的数据库。对话、权限和执行证据仍只有一份
事实来源，不在插件中重建 Task/Run/审批对象。

## 必须一起落实的权限与可靠性

- 不把 GUI 管理员令牌或全权限 attach secret 交给插件。渠道授权限定来源、平台账号、
  允许绑定的空间和可调用操作；模型不能伪造平台发起人或调用插件管理接口。
- 插件验证平台事件真实性；core 根据受信入口、真实发起人、空间和当前权限裁决。
  准入不等于工具权限，普通请求不能携带任意“我是管理员”或任意提升的权限值。
- Core 能阻止跨 Bot/平台冒充，不能识别已被攻陷插件伪造的本账号用户身份；插件令牌
  按秘密保存。模型与渠道凭据分开，由 Core 独立命名空间保管平台 Secret，启动插件时
  按需交付，类型、列表、API、表单与导出不能混入模型 Provider。
- 平台事件 ID、核心请求键和回传 receipt 保持关联。连接断开和消息超时不自动推出
  “未处理”；已关联 Run 不重建。Core 持久去重键包含平台、Bot/应用、聊天范围、
  消息/事件 ID；插件收到持久接收回执后才推进游标。回执保证完整输入、附件持久引用、
  来源/目标与采用状态已保存，不能仅入库正文后返回成功。复用消息/输入/Run 记录，
  输入采用和 Run 创建/关联在同一事务提交；重启恢复仍符合原意图和当前授权的未采用
  输入，重复请求返回原关联。已关联 Run 不另建或重放，明确拒绝的不恢复成执行项；
  插话目标已结束则保留 `target_ended` 并提示，不新建任务，不改变 TG 默认不排队。
  Core 记录待投递回复，插件拿到平台消息 ID 后回执；已派发但未收到确定回执即崩溃时，
  保留 UNKNOWN，按原操作核对，不自动重投，也不重新执行模型/工具。审批按审批 ID 及原参数/版本幂等处理，
  重复卡片与点击不能批准两次。
  渠道网络重连和平台投递属于传输恢复；模型/工具重试由 core 决定，两个恢复不能互相触发。
- 文件与图片经过既有附件边界和新会话绑定；插件不能提交任意主机路径绕过核心授权。
- 设置及安装信息由用户显式调整；模型提出的持久修改继续走既有管理员确认机制。
- 明确绑定本机 Owner 的私聊使用该 Owner 已有授权和能力选择，不全量自动加载 Memory。
  群聊（包括 Owner 发言）与他人的空间默认只用本空间内容；全局/工作区内容须明确
  授予具体空间。范围同时约束私人摘要、Skill 附件、历史与输出投递。
- GUI/CLI 在运行中先排队、可手动引导；TG 普通消息直接插话。同一输入核心支持明确
  的操作类型，默认策略保存在 core 的入口绑定配置中，由 core 处理。渠道只传递来源和
  用户明确动作，不持有另一份运行状态来决定排队或插话。

## 实施顺序与验收

1. 先整理 core 的通用入口契约，把平台类型从 Harness、默认配置和核心 UI 分离。
   保留可组合的执行库；`go list -deps` 应证明默认核心不依赖平台实现。
2. 提取渠道进程，先让 Telegram 通过窄接口完成准入、同一空间接续、插话、停止、
   审批和附件回传。准入/空间绑定/审批处理在 core，平台按钮和连接表单随渠道包提供。
   移除 core 里按 TG/Lark/QQ 名称直接跳过私有上下文能力的特例，改为统一身份、空间与
   内容授权检查；同一授权条件下 GUI/CLI/TG 应使用相同的已选 Memory/Skill/固定内容。
   同步完成通用固定内容，复用 Memory 条目的最小固定属性、范围和版本；经验总结另以
   可选 Skill 加按钮交付，不创建独立总结进程，未启用时仍可手动固定内容。
3. 提供默认 core 包与可选服务组合。测试默认 core 启动无渠道对象、网络连接、平台
   凭据或配置入口；默认一 Bot 一 core，显式多 Bot 绑定有效，同一 Bot 不被两个进程
   同时拉取。拒绝一个渠道进程跨 core 绑定，停止一个 core 不影响其他 core。验证
   GUI/Web 接续并回传原空间、Web 单独在线、待确认/后台命令的存活判断、关闭与新入站
   竞态，以及桌面启动失败与有序退出。
4. 做断线、重复更新、Owner/插件分别重启、权限撤销、跨空间拒绝和 UNKNOWN 回归，
   实测体积、空闲 RSS、启动耗时，记录真实变化。QQ/Lark 只保留已实现的适配和模拟
   回归，不声称完成新的真实平台验收。覆盖接收提交前后、回执丢失、已接收未采用、
   Run 已关联但未回执时的崩溃恢复，不丢已接收输入、不重复创建 Run；覆盖目标结束/
   权限撤销/明确拒绝后恢复、出站重复与审批幂等，
   群空间不带入私人内容；经验总结输入脱敏和产物保存检查由 Core 通用流程提供。
5. 最后才更新 Hytron：核查任务和备份，用户明确编辑渠道配置及空间绑定，停旧轮询
   后启新进程。原会话与权限保留；没有兼容旧平台的运行时迁移层，也不同时启动两个
   Bot 消费者。失败时恢复原部署，切换前后分别核对真实 TG 收发。上述保留现有会话指
   v7.15 渠道拆分；v8.0 PG 切换另按主计划使用新库、不导入历史、重新配对。

验收重点是默认核心确实没有平台依赖，渠道连接独立且只运行一份，消息及权限没有
分裂成第二套核心。通用入口变小之后，其他可选重能力也可沿同样边界独立演进。
