# FreeAgent 扩展开发原则：保持 Core 轻量

更新：2026-11-08。适用于 FreeAgent 的功能设计、扩展开发、宿主接口修改和代码审查。

**首先交付好用的单 Core。扩展增加业务能力，Core 提供稳定、可组合的执行能力。安装或移除一个扩展，应主要改变这个扩展及其接入声明，而不是不断修改执行循环、全局配置和公共数据结构。**

本文是设计和审查约束，不宣称当前实现已经全部满足。第 10 节列出已发现的偏差；实际可调用字段、方法和限制以[开发指南](EXTENSION_DEVELOPMENT_GUIDE.md)、[协议](../extension-kit/SPEC.md)及对应版本实现为准。设计目标不能冒充已经可用的 API。

## 1. 轻量化的判断标准

轻量化要同时满足以下四点，不能只看二进制大小、目录名称或有没有开关：

| 方面 | 要求 |
| --- | --- |
| 默认使用 | 不安装业务扩展，也能完成普通对话、模型与工具调用、权限设置、接续和恢复 |
| 默认运行 | 未启用的扩展不自动启动进程、连接、模型分析、业务轮询或专属数据库初始化；Core 自身必需的 PG 和执行记录不属于扩展负担 |
| 依赖方向 | Core 不依赖具体业务扩展或渠道平台实现；扩展通过版本化接口使用宿主能力 |
| 持续维护 | 修改人物算法、总结方法、平台格式等业务规则，通常只需更新所属能力；不能每增加一种扩展都给 Run、Config 或执行循环加专用分支 |

把代码搬到名为 plugin 的目录、在入口外面加 enabled 判断，或者只隐藏按钮，都不能单独证明完成了拆分。

## 2. 职责归属

这里的 Core 指共享执行内核及其权威记录，不等于整个仓库、发行包或产品界面。随包提供可选程序、前端按需加载扩展详情页，并不意味着应把它们的业务算法放进 Core。

| 部分 | 应负责 | 不应承担 |
| --- | --- | --- |
| Core | 会话/空间、输入采用与队列、上下文装配和压缩、模型/工具调度、权限与确认、取消/恢复、预算、执行事实 | 人物性格与情绪规则、经验提炼流程、平台富文本算法、某个扩展的业务对象 |
| Provider 适配层 | 请求协议、模型能力、思考开关/等级、流式解析、用量和必要协议接续 | 人物表达策略、渠道收发和另一套 Key 管理 |
| 通用交付 | 目标授权、有序 outbox、固定内容、期限、用户授予的发送额度、撤销和逐项回执 | 决定人物为何想主动说话，或者根据情绪生成问候 |
| 渠道组件 | 平台连接、事件验签、平台身份事实、格式与资源转换、原生动作、收发与回执 | 第二个 Agent、独立上下文/Memory、另一个任务队列、审批裁决或业务总结 |
| 业务扩展 | 自己的方法、策略、提示内容、业务状态、配置语义和结果解释 | 复制 Harness、绕过宿主取得更多权限、直接改 Core 表或替原操作伪造成功 |
| GUI/CLI/Web | 展示真实能力和状态、收集用户选择、调用同一控制与执行入口 | 自行判断批准或执行成功，为某个入口另存一份权威业务状态 |

具体例子：AffectWeave 拥有人物和回复表达策略；经验总结拥有选源、提炼与产物组织方法；Telegram 拥有格式、贴纸和反应的原生规则。没有 AffectWeave 时，已启用的 Telegram 渠道仍可提供自己支持的贴纸/反应能力。Core 始终核对权限、目标和真实结果。

## 3. 先选择最小接入方式

| 实际需求 | 优先选择 |
| --- | --- |
| 固定步骤、提示方法、可复用操作说明 | Skill；不增加常驻进程或业务数据库 |
| 独立工具 | 已有 MCP 或现有扩展工具接口 |
| 有界上下文增强、需要代码执行的业务工作流、独立持久业务状态 | 现有本地扩展协议；复用 hook、Host 调用和状态确认 |
| 平台收发、长连接或轮询 | 现有独立渠道进程及版本化渠道协议 |
| 扩展配置、结果查看和人工确认 | 现有能力管理、输入区、确认卡片；必要时增加一个按需加载的产品详情页 |

不要求每个能力都做成进程，不要求每个进程都有数据库，也不把八项职责拆成八套子系统。只提供方法的经验总结，不应为了获得一个按钮而再建服务。

## 4. Core 接口保持通用，业务语义由扩展解释

1. Core 可以知道扩展 ID、版本、能力、宿主绑定的身份/范围、调用令牌、设置、原操作 ID、结果和回执。人物、情绪、总结分类、贴纸包规则等不能成为所有扩展必须理解的公共字段。
2. 通用接口不按某个扩展 ID、Skill 名称、动作名称后缀或私有 schema 名切换业务。权限范围应显式声明，并由 Core 根据真实调用身份核对；不能用 `action` 是否以 `role` 结尾判断是否为全局操作。
3. Core 可在已有扩展配置命名空间保存设置、在原 Run 快照冻结本轮选择。**保存设置不等于拥有其业务语义**：字段含义、默认值和策略由扩展定义，宿主负责结构、范围和声明校验。
4. 业务 payload 由所属扩展校验；宿主仍检查来源、大小、能力、目标、确认摘要和版本。泛化不能退化成无约束 JSON 透传，也不能相信扩展自报的管理员身份。
5. 扩展返回内容或候选，Core 核对后采用。上下文片段、格式化分片、分析草稿都不是授权或成功证据；外部文本不能扩大工具和数据范围。
6. 同一次采用应保留原调用身份、设置和来源；恢复不能偷偷换配置或重新执行已不确定的副作用。扩展自行更新不能改写已冻结的待发内容。

现有有限字符串选项足够时，继续复用 manifest 和普通控件。真实出现其他类型需求时再补最小支持，不预建动态表单引擎、任意对象平台或业务 DSL。

## 5. 什么情况可以修改 Core

新增业务首先适配已有能力。只有真实任务缺少宿主基础能力时，才扩充 Core；不为未来可能出现的分布式协作或知识治理提前加框架。

涉及 Core 的修改，评审说明只需回答清楚以下问题：

- 实际缺少什么基础能力，现有接口为什么不够？
- 谁拥有业务语义；去掉扩展名称后，这个接口是否仍有清楚、有限的含义？
- 新增多少宿主字段、路径和依赖；已有记录是否足够？
- 无扩展、停用、失败与恢复时分别怎样工作？
- 用什么针对性检查证明权限与原有行为未退化？

一个实际调用方也可以促成合理的宿主原语，不要求为了满足“复用数量”先开发第二个产品。涉及通用状态或存储时，可用一个不同业务的合成扩展验证接口没有绑死第一家实现。

如果改动需要给主执行循环新增 `if 某扩展/某Skill/某平台`，先检查是否应放在适配层或扩展中。可靠性、权限或数据一致性确实需要调整内核时可以调整，但必须说明依据，不能把必要的执行保证也挪出去。

## 6. 可选能力必须在产品和运行时都可选

| 状态 | 预期行为 |
| --- | --- |
| 未安装 | 普通 Core 正常工作；没有专用动作和空配置页。能力管理可保留简短的发现/安装说明 |
| 已安装但未启用 | 可查看说明和管理配置；不自动执行扩展或初始化业务数据，不获得本轮业务调用权限 |
| 已启用但本轮未选中 | 不向本轮注入扩展上下文、工具或业务策略；已明确启用的渠道连接可按其既有生命周期工作 |
| 本轮选中 | 只提供已声明、可用且当前身份获准的能力，冻结本轮设置；客户端显示不能替代后端校验 |
| 停用或卸载 | 撤销新调用与相关入口；待发项按现有撤权规则处理。已派发请求仍需保留实际回执，不能假定撤回成功 |
| 查看已有结果 | 不因停用删除人物数据、历史草稿、Skill/Memory、执行证据或原回执；查看记录不自动重新启用业务 |

用户明确发起的 `ext check`、安装验收、独立存储初始化等，是有界管理操作；可以按其已说明的行为启动受信程序或写入数据，不等于自动启用业务。不能把这些管理操作放入普通启动或聊天的隐式路径。

可选扩展出错应报告失败并遵循已声明的降级行为；被明确设为本轮必需的能力不可悄悄跳过。两种情况都不能把缺失结果伪装为成功，或擅自扩大权限、换模型和重放工具。

全局默认放到对应扩展/渠道的设置内，本轮选择留在输入区。GUI、CLI、AI 使用同一配置语义和控制入口；AI 可调整的范围以实际声明与已实现的秘密管理边界为准，不为某个页面另做一套状态。

前端允许少量明确注册、按需加载的产品适配页。无需为了去掉前端中的一个扩展名称，引入任意第三方浏览器脚本、插件 UI 运行时或在线市场。

## 7. 权限、数据与证据不能随减重一起丢掉

- Core 继续核对输入身份、空间可见性、工具权限与实际收件人。渠道提供平台事实，不能替 Core 批准；扩展只得到所需范围和短期调用能力，不取得模型 Key 或 Core 管理连接。
- 模型提出的产品设置、人物状态、Skill/Memory 等持久修改继续绑定具体内容、范围、版本和用户确认。普通文件/命令操作仍遵循既有权限模式，不因此变成每个工具都要输入控制确认码。
- 优先使用现有 Conversation、Run、Attempt、消息、附件和 receipt；不预设独立 Task、Step、Checkpoint、Evidence 对象或第二套执行数据库。
- 只有独立持久业务状态才使用受限扩展存储。PG 是当前唯一支持的数据库技术；复用现有实例与运维方式，不为简单 Skill 建库，不引入 SQLite/PG 双后端。
- 扩展拥有业务表和规则；Core 只承担通用的受限存储供应、身份绑定、备份/恢复协调。具体业务 schema 名不能散落在宿主初始化、备份与恢复代码中。
- 停用、升级、卸载、清空数据分别处理。当前用户数据须保留或经过明确删除操作，不能用“无需旧版兼容”作为删除正在使用的数据的理由。
- 有副作用的工具或消息发送结果为 UNKNOWN 时，不自动重复执行。模型请求是否可有界恢复，由现有 Core 恢复策略统一决定并保留原记录；扩展和渠道不另建自动重试循环。
- 本地扩展进程和版本化协议不自动构成 OS 沙箱。Host API 的权限、受限 PG 凭据与同用户原生进程的实际权限要分别说明，不宣称协议限制能阻止所有宿主文件访问。

## 8. 默认成本与依赖方向

调用按需发生，回调有明确的超时、输出上限和取消路径；额外模型调用计入既有预算和事实记录。不要为每次流式增量重跑业务分析，也不要增加没有实际消费者的后台扫描。

默认 Core 可以依赖通用协议数据类型和自身必需的 Provider/执行组件；不能为了某个渠道的富文本渲染直接导入整个平台实现。平台格式、资源解析和原生动作表应由渠道侧提供，Core 接收有界结果并做授权与冻结。

审查时可执行已有 Go 命令：

```text
go list -deps ./cmd/freeagent
go list -deps ./internal/harness
```

检查是否新增业务扩展、平台实现、它们的 SDK 或非必要运行时依赖。依赖图是架构证据，不能代替运行测量；不要仅凭出现某个包名，就声称所有代码都已链接、存在后台连接或内存增加了多少。

有性能影响的改动，按实际范围比较同机同数据下的普通 Core 启动、空闲进程/连接、模型请求数量、上下文字节、首屏资源或峰值内存。采用适当的既有基准，不为了“轻量”另建监控平台，也不凭空增加一套总步数/总时长限制。

## 9. 验收与提交要求

按此次能力的实际边界选取检查，已有有效覆盖可复用；不要求每个文档修改或纯 Skill 都重复全仓测试。

| 场景 | 必须得到的证据 |
| --- | --- |
| 无扩展 / 停用 / 未选中 | 普通任务可用；没有业务注入、专用动作或意外后台工作 |
| 安装启用并选择 | 当前 Core 的真实入口能够发现和调用；不是只通过 mock 或 SDK 自测 |
| 权限与确认 | 超出身份/空间/目标范围被拒绝；预览修改后不能沿用旧确认；拒绝不写入 |
| 错误与恢复 | 超时、退出、取消、重复请求和 UNKNOWN 按原语义记录；不假装成功、不重放副作用 |
| 数据变更 | 停用保留数据；涉及存储时，实际验证备份、恢复、来源与作用域隔离 |
| 多入口 | 本次提供的 GUI/CLI/AI/渠道入口使用同一后端语义；声明不支持的入口不伪装可用 |
| 最终交付 | 支持的平台用最终归档验证，真实服务与模拟结果分开，未运行和阻塞明确说明 |

提交说明包括：问题与结果、职责归属、必要 Core 改动理由、默认运行成本、实际测试、未运行项、更新/停用/恢复办法。所需命令、schema 与支持版本写在开发指南和协议中；本原则文档不复制维护另一份接口定义。

发布包不包含真实凭据、用户对话、人物资料或业务数据库；声明准确的宿主版本、依赖和许可证。运行时不暗中安装依赖。支持能力不足时报告原因，不自动降级到未经授权的宿主执行。

## 10. 本次整改与持续检查

2026-11-08 已按下面顺序实现 v8.6 三批整改，阶段与综合验收结果见[验收记录](VALIDATION_V8_6_2026-11-08.md)。代码完成、最终包验证、生产更新和真人观察分别记录。

实施顺序、具体改动与退出条件见[轻内核整改计划](FREEAGENT_CORE_BOUNDARY_REFACTOR_PLAN_2026-11-08.md)：经验总结 → 扩展状态与存储 → 渠道依赖。

| 顺序 | 原偏差 | 当前实现 |
| --- | --- | --- |
| 1 | 经验总结固定包名与专用执行流程 | 可选 Skill 声明 selected_sources；Core 通用选源分析，不安装不出现新动作，历史仍可读 |
| 2 | 人物字段及动作后缀决定通用权限 | state_version 2：显式 scope、受限 payload、原 Run/已采用输入绑定；AffectWeave 自己翻译人物字段 |
| 2 | PG 初始化和恢复固定 aw | 单 schema 声明贯穿供应、显式更新预检、备份与新目标恢复；保留既有 aw 数据 |
| 3 | 默认 Core 导入平台实现 | 仅依赖 channelwire；格式与资源解析留在渠道，纯准备后冻结整组，UNKNOWN 实际发送不重放 |
| 随相应批次 | 无渠道仍显示完整投递设置 | 无配置只显示发现说明；既有授权、待交付与 receipt 仍可管理 |

已经修正的自然分段归属继续保持：AffectWeave 拥有表达模式、默认值和算法，Core 只验证具体部分。Provider 思考控制继续属于模型适配，不移入人物插件。

**边界修正的完成条件是：能力可增减、普通 Core 仍然好用、业务变化不继续侵入执行内核，并且权限与数据连续性没有退化。**
