# FreeAgent v7.13：连续执行、上下文窗口与运行中交互

日期：2026-11-04。状态：v7.13.0-dev.1 已实施，正在完成整体验收与交付；以[实施记录](FREEAGENT_V7_13_IMPLEMENTATION_ACCEPTANCE_2026-11-05.md)为准。
基线：`f0c49287e75f61f6e4b609f1abf1eaaf61b9a041`，当前版本 `v7.12.0-dev.1`。
目标候选版本：`v7.13.0-dev.1`。

## 1. 用户确认的范围

本版只做五项：

1. 删除任务总步数、总执行时长限制。
2. 先完成上下文窗口管理，再完成基于该管理的自动压缩。
3. 运行中插话、消息排队。
4. 工具执行过程与耗时。
5. 从某条消息重新开始。

以功能和内核行为为主。现有 GUI、CLI、TG 接入必要操作与状态，不另做视觉
改版。SSH 连接池、经验学习、额外思维链系统、RAG 和新的长期记忆体系不在本版。
Lark/QQ 继续只做共用逻辑的必要回归，不扩大真实平台验收范围。

继续使用同一 Owner、TaskService、Store、Run、Attempt、消息和 receipt。
小量输入排队及分支关系优先使用已有消息和关联元数据；不建立任务调度平台、
独立 Trace 服务或第二套权限/审批系统。模型提出的持久化设置与组织操作仍走
既有管理员确认；用户已开启的自动压缩无需逐次确认。

## 2. 已核实的问题与可复用基础

2026-11-04 对 Hytron 做了只读核查，没有调整服务或配置。观察时实际配置为：
12 步、300 秒、40 条上下文消息、131072 字节输入预算、4096 个输出 token，
自动摘要上限 4096 字节。

- 运行记录有 7 轮因 12 步停止，多轮实际用时约 20 秒。模型请求、工具调用及
  摘要调用共享步数，因此正常执行很容易触及这个上限。
- 有一轮在自动压缩已经开启的情况下，0 步就因本地上下文预算不足停止。
  这证明问题不能只归结为开关；该次具体超限组成还需要用分项诊断复现。
- 当前主要在构建上下文失败后尝试压缩；附件和每步扩展随后还能扩大请求，
  最终检查失败未必重新进入压缩处理。
- 131072 是本地字节预算，当前模型未声明真实 token 窗口，不能当作 128K tokens。
- 数据库中存在真实摘要请求记录，说明摘要能力已实现；它不等于窗口管理及
  所有失败恢复路径已经正确。当前通用错误也没有区分实际超限来源。
- 核心已保存 `ModelResponse.LatencyMS`、Provider usage、`ToolOutcome.DurationMS`
  及执行 receipt，主要缺少完整、一致的对外投影，不需要重建采集系统。
- 同会话当前有运行时，新输入主要返回 busy；现有输入去重与渠道消息关联事务
  可扩展为插话/排队的基础。

证据保存在项目忽略目录 `output/hytron-context-*-20261104.json`，仅含所需
配置、状态、计数与用量，不复制对话正文或凭据到公开计划。

## 3. 删除任务总步数与总时长限制

### 3.1 最终行为

普通任务持续执行到正常完成、用户停止、必须确认的操作、明确错误或结果未知。
执行步数与活动耗时继续累计，用于观察、排障和记录，不再作为统一停机条件。

直接删除主任务的 `max_steps`、`max_run_seconds` 配置、校验、控制 schema、
CLI 参数及相关“增加额度/再加几步”入口，不用巨大数字或默认无限但仍保留隐藏
上限的方式替代。普通 Run 与协作父 Run 不再受这套统一步数/秒数预算截断。

单次 Provider/HTTP 调用、命令进程和后台服务各自的超时与停止机制继续明确
归属于该操作。可选协作的子任务显式预算、父任务模型/工具/输出累计额度按其
计划约束，不能再从主任务的总步数/总秒数派生限制，也不能隐式套给普通聊天。

### 3.2 清理与恢复

- 梳理 `Config`、`ExecutionLimits`、`incrementStep`、`runClock`、继续操作、
  扩展调用和协作入口；保留计数/计时，删除主任务超限判定和专用定时取消。
- 全链路继续接受用户取消信号。停止不清除已知结果，已派发且不确定的调用
  保留 UNKNOWN；关闭网页与取消执行仍是不同操作。
- 删除仅为“步数/总秒数耗尽后再开一轮”服务的产品路径；仍需保留的输入过大、
  输出截断、未知调用和后台命令恢复按各自事实处理，不粗暴删掉通用恢复能力。
- 既有历史中的步数、耗时和旧停止原因保留。升级前明确处理活跃/待确认任务，
  不重写旧冻结快照、自动重跑旧工具或建设旧版本续接转换层。

验收：超过原 12 步、100 步仍可完成；超过原 300 秒仍可运行；任意阶段用户
停止有效；一次调用超时不冒充整轮累计超时；协作和扩展不能被删除字段意外卡死。

## 4. 先做好上下文窗口管理

本阶段先建立正确的请求核算、选择和诊断，独立验收后再实现第 5 节自动策略。

### 4.1 统一窗口定义

每个模型支持声明总上下文 token 窗口和输出上限，记录声明来源；复用现有模型
配置与 ControlService，不增加模型注册平台。预设或人工声明可以使用，服务的
模型列表只有名称时不得据此推断窗口。

没有可靠窗口信息时，使用明确标注的本地保守预算并说明模型窗口未知。Provider
上次返回的 input/output tokens 是实际调用用量，不代表模型总窗口，也不是当前
尚未发送请求的精确用量。估算值、真实返回值、字节数必须分别标注。

核算包含系统指令、工具定义、技能/显式记忆、扩展、已有摘要、近期对话、当前
输入和附件，以及预留输出与估算余量。图片等非文本输入使用适配器可支持的
估算；无法可靠估算时保守处理并说明来源。

最终请求必须同时满足模型窗口和本地传输/资源边界。字节边界仍用于避免巨量
请求占用内存，但不伪装成模型 token 窗口。40 条消息不再是独立的用户任务硬停
条件；消息读取分页有界，只有实际协议限制或完整请求放不下时才报告具体问题。

### 4.2 完整请求只核算一次真值

统一流程为：选择当前可见历史 → 装配本次实际模型请求 → 核算 → 必要处理 →
重新核算 → 派发。普通对话、手动/自动压缩、模型选择和扩展辅助请求使用一致
的预算基础，按用途声明输出预留。

附件及每步扩展必须进入最终派发前检查。重算预算不能反复执行扩展 hook、下载
附件或触发工具；一次模型请求准备出的内容在本次检查中复用，需要重新准备时
按新的明确步骤处理。查询上下文状态本身不得调用模型或执行扩展/工具。

完整工具调用与结果组是上下文选择单位。未执行、未决或 UNKNOWN 调用不能被
摘要成“完成”，不能通过截掉结果来满足协议。排队尚未采用的输入也不进入本轮
上下文；被采用的插话必须计入下一次请求。

### 4.3 对所有入口提供同一份状态

扩展既有 ContextState/ChatView 投影，至少能查询：

- 所选模型、声明窗口及来源；当前请求估算、上次真实 usage、预留输出。
- 系统/工具/外部材料/摘要/近期消息/本次输入的占用及主要超限项。
- 当前 Run 的有效参数与下一轮保存设置，避免修改设置后误报已经作用于旧请求。
- 当前可压缩范围、最近一次压缩结果、是否被未决调用阻塞。
- 状态的观察时间，以及当前请求是否尚有待装配材料导致估算不完整。

读取采用有界汇总和现有摘要缓存，避免每个流式 token 都扫描全量历史。模型
读取的状态继续遵循当前入口可见性，不泄露其他空间或管理员私有记录。

错误至少区分：模型不支持该输入、固定指令/工具定义过大、当前输入/附件过大、
历史需要压缩、没有可压缩范围、摘要生成/提交失败、Provider 明确拒绝上下文。
每项给出实际占用、边界来源和可执行的处理方式。

验收：短消息超过 40 条但仍可容纳时可继续；低窗口模型准确阻止超大请求；
切换模型更新后续窗口；附件/扩展不会绕过最终核算；状态读取无执行副作用；
所有入口给出相同事实，真实 token 与估算/字节口径不混用。

## 5. 在窗口管理之上实现自动压缩

### 5.1 触发与目标

自动压缩在每次模型派发前检查，不依赖后台定时扫描。默认触发点为可用输入
预算的 80%；预留输出和估算余量已在可用预算中扣除，不能重复扣减。
触发比例作为一个可调整参数，经现有设置、CLI 和模型控制提案共享。

压缩选择覆盖足够的已完成历史，使本次完整请求回落到可继续工作的范围，默认
目标约为可用输入预算的 60%。初版目标作为内部策略，不再增加一组高级开关。
大输入突然越过触发点时也在派发前处理。

原有 `task_summary_bytes` 表达摘要输出上限及 0 关闭语义；它不再承担“模型
窗口大小”或“何时压缩”的含义。摘要文本、近期对话与当前输入共同占用窗口。
手动压缩使用同一核算和压缩流程，可在自动关闭时运行。

手动压缩在会话空闲或当前调用组已确定完成的安全边界执行；存在待确认、已派发
未收束或 UNKNOWN 时指出具体阻塞对象。停止、审批、压缩等控制命令先由 Owner
解释，不当作普通排队文本送给模型，也不另起第二个执行者争用当前会话。

### 5.2 处理与失败

- 保留近期完整消息组、当前目标及最新插话，原始消息与执行证据留在 Store。
  摘要明确保存目标、约束、决定、已确认结果、未完成工作、关键引用和 UNKNOWN。
- 摘要请求本身也必须装得进窗口。较长的已完成工具正文可作为摘要源分块，
  生成请求不携带待执行工具调用；模型协议中的调用/结果组不得拆成悬空片段。
- 单条当前用户输入、固定工具定义或其他必须保留材料本身过大时，明确报告，
  不循环压缩无关历史，也不偷偷截断用户要求。
- 一次压缩固定源范围，每个分块必须推进覆盖位置；检测无有效缩减，禁止同一
  前缀无进展循环。摘要目标预留余量，实际输出仍校验；必要修整最多一次，保留
  对应调用记录，不静默截断摘要尾部。
- 新摘要只有在源版本核对、有效缩减、重组请求可容纳且持久化成功后才替换。
  失败/取消保留原摘要与历史；压缩期间到来的插话和队列消息不能被错误覆盖。
- 本地超限尚未派发时可直接先压缩。Provider 若明确返回上下文超限且确认没有
  生成结果或工具调用，最多允许一次有记录的压缩后重试；未知网络结果、认证
  错误、限流、取消和任意工具错误不走这条重试路径。
- 无论 GUI/CLI/TG，均可观察准备、压缩、完成或失败，以及前后用量和覆盖范围。
  用既有事件和记录投影，不新增独立压缩任务平台。

验收：多轮真实 Provider 对话实际触发摘要，后续请求复用摘要并保留关键约束；
大工具输出分块可处理；None/TG 只压缩获准可见的内容；取消、崩溃、无进展、
摘要过大和并发插话均有明确结果，不重复派发 UNKNOWN。

## 6. 运行中插话与消息排队

### 6.1 两种明确语义

| 操作 | 生效对象 | 行为 |
| --- | --- | --- |
| 插话 | 指定的当前 Run | 加入新要求，在安全边界修正当前执行方向 |
| 排队 | 当前会话后续新 Run | 按接收顺序等当前任务正常结束，再处理下一条 |
| 停止 | 当前 Run | 请求取消并暂停队列推进，保留未执行输入 |

运行中普通补充默认按插话接收；明确“排队”操作进入后续队列。请求必须携带
操作类型、目标会话、插话对应的 Run、请求去重键和真实发起人，不能仅凭自然
语言文本推断执行权限，也不能让模型把自己的输出变成用户队列消息。

如果插话到达时指定 Run 已结束，返回目标已结束及原输入，不静默丢失或另起
一个自动任务。用户可明确作为新请求发送，或选择排队入口。

### 6.2 插话的执行边界

- 尚未派发的旧工具可以标记为 NOT_RUN，并补齐协议所需的取消结果，然后把
  插话作为真实用户输入交给模型重新决定。插话不替旧参数完成审批。
- 已派发的命令/工具不会因插话而假装没执行；先保存已知结果，用户要求立即
  中断时走既有停止机制。结果未知则维持 UNKNOWN，插话等待处理，不越过它。
- 模型请求正在返回时，记录插话，在新工具派发前再次核对。对已过时且尚未
  执行的工具计划按上条收尾，再使用新要求请求模型；已流出的文字不伪造成未出现。
- 采用插话和推进工具派发之间有同一个核心检查边界；GUI、CLI、TG 不能各自
  使用内存列表决定先后。接收、采用、撤回状态可通过请求键核对。
- 原待确认操作收到插话后，不自动批准。用户明确替换该计划时取消尚未执行的
  旧提案并保留记录；仅补充信息时，说明仍有哪些确认或结果需要处理。

### 6.3 队列与恢复

输入正文复用现有消息记录，小量顺序/状态/关联信息复用 Store/meta。借用现有
渠道消息先保存、再与 Run 事务关联的能力，使同一输入只成为一个 Run 的用户
消息。排队条目不提前创建占位 Run，不另建 Job/Task 表。

初版提供查看、取消未执行条目和恢复队列，采用 FIFO，不做优先级调度或复杂
重排。每会话最多 20 条待采用输入，超过时明确拒绝并保留客户端原文；单条大小
沿用输入与附件边界，不使用任务总步数来限制队列。

取消与消费在同一事务边界竞争：取消成功的条目不会被执行；已经关联 Run 的
条目返回该 Run 的实际状态，需停止时使用既有停止操作，不能删掉条目后声称
任务没有执行。接收响应丢失时按原请求键查明状态，不另造请求键重复提交。

当前任务正常完成后可消费下一条。待确认、用户停止、失败或 UNKNOWN 阻止
自动推进，用户明确处理后恢复。Owner 重启恢复队列和消费关联；若条目已有
Run，先恢复该 Run 的事实，不能重新创建和派发。尚未开始的条目只有在没有
未决工作、队列未被暂停且原授权仍有效时才能继续。

每个条目固定真实入口、发起人、目的地、用户选择的模型和附件引用。派发前
核对当前准入、权限和模型配置；权限只能受提交时授权与当前权限共同约束。
模型地址/能力变更或授权失效时阻止该条目并说明，不静默换模型或扩大权限。
已明确排队的附件需要有界保留，不能被普通临时附件清理误删。

同一群的其他成员不能通过普通文本接管别人的当前 Run；他们获准的新请求可
以自己的身份排队。管理员参与也保留真实身份与原 Run 的权限边界。
继续复用现有 Owner 并发额度，不因队列而增加同会话并发执行。

GUI/Web、交互式 CLI 和 TG 使用同一核心操作；TG 只将获准且确实唤醒 Bot 的
输入送入该流程，群背景消息不自动变成插话。后台命令的标准输入不与任务插话混同。

验收：模型生成中、工具执行中、批量工具中、待确认和最终回答竞争边界均不丢
输入；重复提交/断线/重启只采用一次；停止不自动跳到下一任务；权限撤销与附件
过期正确阻止派发；被替代但未派发的工具明确为 NOT_RUN。

## 7. 工具执行过程与耗时

扩展现有 ChatActivity 和事件投影，统一提供工具名称、简短目标、状态、实际
耗时、结果摘要及原有详情入口。执行记录依旧是唯一事实来源。

- 工具耗时来自 `ToolOutcome.DurationMS`；模型延迟来自 `ModelResponse.LatencyMS`，
  两者分开。Provider 返回的 token 用量属于对应模型调用，不摊成某个 shell 命令的用量。
- 区分等待确认、尚未派发、执行中、成功、明确失败、已取消、输出截断和 UNKNOWN。
  取消/超时标志不自动推出“没有副作用”，实际状态继续由 outcome/receipt 决定。
- 若刷新后展示执行中耗时需要派发时刻，在既有 Attempt 的关联元数据中补齐，
  不逐秒写库。没有可靠时间的旧记录显示“未记录”，不能填 0 冒充测量。
- 同一 Attempt 的开始/结束事件只更新同一条过程记录，重连按快照恢复，避免
  重复行。日志有界并支持按需读取原有详情，不把全部工具正文塞进每次快照。
- 模型可以给出简短执行说明；成功与否、耗时、退出码和变更结果由运行时提供。

验收：正常、失败、取消、超时、截断和未知结果投影准确；模型与工具耗时口径
清楚；重启不伪造时间；连续大量工具调用时快照和日志读取保持有界。

## 8. 从某条消息重新开始

### 8.1 产品语义

创建新对话分支，保留原对话与执行记录。首版支持两个清楚的入口：

- 从用户消息重新执行：取该消息之前的有效前缀，使用原文或用户修改后的文本
  作为分支的第一条新请求；被替换的旧消息及其后续不进入新上下文。
- 从已完成的模型回复继续：取包含该回复的完整前缀，新输入在分支中继续。

工具消息不能作为悬空切点；请求必须选择一个完整交互边界。接口验证真实消息
ID、所属会话、边界和调用者可见性，不能依赖客户端传来的历史正文。

### 8.2 数据与执行

- 复用 Conversation/messages，保存来源会话和分支点的轻量关系；不另建版本
  控制系统。分支前缀形成独立消息记录，后续修改不会相互改写。
- 不复制活动 Run、待审批凭据、后台进程或队列。已完成工具内容可作为来源
  历史进入上下文，其来源关系保留，不伪造成本分支新执行的 Attempt 或成功记录。
- 默认沿用来源会话当前的模型选择，派发时核对有效配置；工具能力与权限来自
  本次操作及当前空间约束，不能从历史 Run 复制一次已经失效的授权。
- 现有摘要只有覆盖范围完全在分支点之前且权限/来源一致时才可复用；否则从
  原始可见前缀按新窗口重建，不能带入分支点之后的信息。
- 附件按新会话的访问绑定重新关联不可变内容，校验来源访问权、存在性和配额；
  不直接复制一个会在新会话下载失败的旧附件 ID。来源内容不可用时明确报告。
- 分支使用当前工作区实际文件状态。历史中的文件修改、命令和外部操作不会
  随对话分支撤销；也不因复制历史自动重放。
- 来源仍在执行或存在 UNKNOWN 时，可以保留分支草稿，但不能用“重新开始”
  绕过源任务的停止、结果检查或相同工作区的已有执行约束。
- 同一分支操作的重复提交只生成一个分支。来源历史跨空间复制继续遵守已有
  发布与权限规则；外部空间多会话关闭时需先明确启用，不偷偷改变空间设置。
- 用户直接执行分支操作沿用其交互授权；模型提出创建分支或改变对话组织时
  复用既有控制确认。GUI、CLI 及获准 TG 多会话入口使用同一分支核心。

前缀复制采用有界读取或数据库内部拷贝，提交时核对来源边界；中断不得留下
一个看起来创建成功但缺少消息或附件关联的半成品。

验收：修改旧用户消息后，分支不含原消息及其后续；从回复继续时包含该回复；
完整工具组保持合法；原会话和文件不被回滚；摘要无未来信息；附件可下载且不
越权；取消/断线/重复提交不会产生重复分支或重放原工具。

## 9. 实施顺序与阶段退出条件

| 阶段 | 工作 | 通过条件 |
| --- | --- | --- |
| A | 删除主任务总步数/总时长限制，保留计数、取消和事实记录；补齐已有耗时数据投影 | 超过旧边界可运行，停止和真实操作超时正确，旧记录可读 |

## 10. 最终验收与交付

必跑 Go、ChatUI JS、Windows/Linux 相关路径，以及插话/队列/分支/压缩并发的
针对性 race。核心场景包括：

1. 长任务跨过原 12/100 步及 300 秒仍能推进；至少一次隔离环境实际长执行，
   同时验证手动停止、后台进程清理及单次调用自身超时。
2. 低窗口、多工具定义、大附件、超长已完成工具输出、模型切换和多种可见性；
   主请求与摘要请求都在最终装配后核算，错误指出真实占用来源。
3. 一次真实 Provider 长对话，实际产生压缩、复用摘要，并核对早期关键约束；
   单次输入不可容纳时给出正确结果，不假称自动压缩已解决。
4. 插话与模型返回/工具启动/审批/压缩提交竞争，排队消费事务中断，Owner 重启，
   重复请求、权限撤销、附件清理、停止后队列暂停。
5. 消息分支截断、完整调用组、摘要覆盖范围、附件归属、重复分支请求，以及
   来源存在副作用或 UNKNOWN 的情况。
6. Windows 全新便携目录启动；Debian 12 非 root 包级与 Bubblewrap 验收；
   当前格式真实数据备份的独立副本升级检查，覆盖 v7.12 索引问题的回归。

Linux 在 Hytron 独立验证目录/端口进行。普通回归不停止常驻 Bot，不用真实
凭据生成公开报告。真实 TG 多账号/群等缺少条件时标 NOT_RUN，模拟结果与真实
结果分别记录；UNKNOWN 仅表示实际派发后无法确定结果的工作。

交付更新源码、使用/恢复说明、实施验收记录及 Windows/Linux 便携包。正式包
固定干净提交与工具链，重复构建核对一致，提供可下载附件即可。生产升级另按
活动任务核查、备份、切换、实际健康检查和回退预案执行，并同步私有 VPS 文档。
