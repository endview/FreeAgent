## 1. 产品目标

用户可以启动开发服务器，在服务运行期间继续对话、运行测试、从宿主浏览器访问，
并通过 GUI、CLI 或 AI 对话查询、延长和停止。服务有独立的有限期限，始终由本机
owner 管理。

常驻服务复用 v7.3 后台命令的启动、进程持有、轮询、停止和记录逻辑。
服务只是后台命令的一种运行模式，不另建 Service 表、执行器或调度平台。

本版的核心验收场景是“启动服务 → 访问页面 → 同时运行测试 → 停止服务”。
仅能启动并显示 PID 不算完成。

## 2. 已确认参数

| 项目 | 默认值 | 限制 |
|---|---|---|
| 单次服务时长 | 30 分钟 | 启动时可指定，受配置的最长时长限制 |
| 服务最长总时长 | 8 小时 | 可下调，产品硬上限 8 小时 |
| 同时运行的服务 | 2 个 | owner 范围内统一计数，不能通过新会话绕过 |
| 非服务命令 | 同时最多 1 个 | 可与服务并行，前提是授权兼容 |
| 服务日志缓冲 | 每服务最近 256 KiB | stdout/stderr 合计，按字节计算 |
| 等待就绪 | 60 秒 | 可指定，最长 300 秒，不能超过服务剩余时长 |
| 普通停止宽限 | 5 秒 | 平台支持时先请求终止，再强制结束受控进程树 |
| 强制结束后确认等待 | 5 秒 | 仍不能证明结束则为 UNKNOWN |

最长总时长从最初启动时刻计算，多次延长不能滚动突破 8 小时。
就绪等待和停止宽限计入服务的墙钟时间；进入停止阶段后不得再延长。

## 3. 实施前置与现有事实

v7.3 必须先实现：启动回执与进程终态分离、独立于前台调用 context 的进程持有、
有界输出、幂等停止和恢复检查。若这些契约未完成，v7.4 不开始接入并发服务。

当前代码核查结果：

- `internal/winlaunch/launch_windows.go`：Windows Job 使用
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；保护路径和临时程序目录授权在关闭时恢复。
- `internal/harness/commands.go`：AppContainer 身份按数据目录和读写模式复用；
  工作区授权可保留，程序目录授权按启动临时添加。
- `internal/winlaunch/process_unix.go`：Linux 使用进程组主动终止；没有 owner
  崩溃后自动清理整个进程组的保证。
- `internal/harness/config.go`：普通命令超时上限目前为 600 秒。
- `internal/chatui/attach.go`：交接判断目前只检查前台执行，尚不包含服务。
- `internal/harness/control.go`：host 执行与控制提交互斥，当前布尔标志不适合
  多个 host 进程重叠，必须随并发接入一并修正。

以上是代码事实，不是 v7.4 的验收结果。

## 4. v7.4-0：先验证可行性

先用小型本地 HTTP 服务和两个受控命令验证以下事项，并记录实际 backend、
Windows 版本、AppContainer 身份、网络配置、地址、错误及退出结果：

1. 沙箱服务绑定 `127.0.0.1` 后，宿主 curl、浏览器分别能否访问。
2. 同一执行配置的测试命令能否访问该服务；需要时另测 `::1`，不能由 IPv4
   通过推断 IPv6 通过。
3. 网络 off/internet 的实际差异，以及回环连通是否要求系统级豁免。
4. 两个命令交错退出时，另一个的目录授权和保护路径是否保持有效。
5. Scoop 真实安装目录，包括 git 这类多层目录，首次授权和释放的实际耗时。

判定规则：

- 不需要管理员或系统级回环豁免即可完成本机访问：实现并公布对应受支持的配置。
- 需要额外系统权限或能力尚不可用：沙箱服务返回 `NOT_SUPPORTED`，可由用户
  明确选择 Full 模式。不得自动加豁免、切换 Full 或声称“已隔离本机监听”。
- 部分配置通过只代表该配置受支持；未执行项目为 `NOT_RUN`，不明确的结果为
  `UNKNOWN`。不能用 Full 模式的连通结果证明沙箱模式通过。

“允许本地监听”是显式服务配置。它能否由 Windows 强制执行取决于上述原型。
若不能强制限制监听范围，界面必须说明实际能力，不能把应用声明包装成系统限制。

## 5. v7.4-A：并发授权

### 5.1 生命周期和引用计数

复用 owner 内存中的授权管理，加入有界引用计数和短临界区：

- 同一路径、相同访问级别和保护规则，首个使用者设置，最后一个使用者释放。
- 临时程序目录授权、保护路径不能在其中一个命令退出时提前撤销。
- 根授权保持现有 owner 会话复用方式；在仍有使用者时禁止同步成另一组根目录。
- `Process.Close` 只释放当前进程的引用，不能撤销其他进程仍依赖的保护。
- 申请过程部分失败时撤销本次新增项，保留其他使用者的有效授权。
- host 执行互斥标志改为按在运行的 host 进程计数，最后一个退出才解除门禁。

此处只管理执行所需的权限生命周期，不提供通用 grant ledger 或模块生命周期。

### 5.2 兼容的并发配置

首版只允许同一 backend 和兼容的完整执行配置并行：工作区、读写模式、文件范围、
额外目录、保护规则、`git_write`、网络能力必须一致。不同身份或规则的请求返回
`execution_profile_busy`，显示阻塞它的命令 ID。

相同 AppContainer 身份意味着共享 OS 授权。引用计数只能防止提前释放，不能防止
新增目录扩大已有进程的读取能力。因此并发组的程序安装只读目录集合必须在首个
服务启动前明确计算并冻结；后续命令不得临时扩大该集合。测试工具链可以预先列入
该集合，由现有命令策略和配置入口管理，模型提出的持久调整仍需确认。

工具链解析必须落到真实版本目录，处理 Scoop `current` 联接和必要的运行资源；
不能默认授权整个用户目录或整个 Scoop 根目录。声明一致但实际目录集合不一致时，
也不能认为授权兼容。

### 5.3 配置变更和异常清理

服务运行时，切换工作区或改变上述授权相关配置，返回受影响的命令清单和 busy
原因。用户先明确停止这些命令，确认进程结束后再应用配置；不自动杀服务。
已成功停止和未能确认停止的结果逐项保留。

不持久化整份旧 DACL 并在重启后盲目覆盖当前 DACL，这可能覆盖用户的新权限。
沿用当前 sandbox SID 授权清理边界，并加入保护路径崩溃测试。若某条恢复路径不能
证明安全，报告失败并阻止沙箱服务启动，不静默恢复或引入自动权限修复平台。

## 6. v7.4-B：时长、延长和预算

### 6.1 启动

启动请求携带显式服务模式、持续秒数和可选就绪文本。普通后台命令默认行为不变。
已有启动预览同时显示程序、最终参数、工作目录、执行配置、期限和日志策略。
审批仍由 Ask / Workspace / Full 及命令规则共同决定。

启动调用消耗当前 Run 的正常步骤和输出预算。服务运行时间采用独立服务期限，
不延长或重新打开已完成的 Run，也不重置其累计用量。
协作父子执行内均不开放服务启动；不通过服务模式绕过父子累计预算。

### 6.2 截止时间

在成功创建进程后记录 `started_at`、`expires_at` 和本次最长总时长。
同一 owner 存活期间用单调时钟执行期限；墙钟时间用于展示和记录。
系统时钟回拨不能延长服务。owner 重启不恢复旧服务，也不重新计算一段新额度。

每个服务一个到期计时器，stdout/stderr 读取和进程结束观察均为有界运行时工作。
无需用户轮询也会到期停止；这些监督任务不派发模型、不重试、不实现调度器。

### 6.3 延长

延长操作绑定命令 ID、当前记录 revision 和目标截止时间：

- 用户通过 GUI 或 CLI 直接延长，不能超出启动时刻起的最长总时长。
- 模型只能提出延长操作，须通过现有 GUI 卡片或 CLI 提示确认后提交。
- 相同 request key 重复提交返回同一结果；过期 revision 重新读取并预览。
- 若到期或停止已开始，延长失败，不恢复进程、不再启动一个替代服务。
- 全局时长配置变更影响未来启动，不能静默改变现有服务的期限。

### 6.4 Stop 保持可用

列出、读取、停止和限定范围内的延长必须有 owner 端受认证入口。
特别是在 Full 模式长期持有 host 门禁时，Stop 不能被该门禁挡住。
延长只更新绑定服务的有限期限，不获得写入任意产品设置的能力。

关闭命令工具只禁止新启动，已有服务仍可直接停止。
用户直接点击 Stop 或运行 CLI Stop 不追加模型确认。
模型调用 Stop 仍遵守现有工具权限规则，不能借此自动停止不相关的命令。

## 7. v7.4-C：停止和终态

| 触发 | 动作 | 记录 |
|---|---|---|
| 用户停止 | 终止受控进程树并确认清理 | `user_stop` |
| 服务期限到达 | 自动执行同一停止路径 | `deadline` |
| 就绪等待超时 | 停止未就绪服务 | `readiness_timeout` |
| 程序自行退出 | 获取退出码、排空有界输出、清理受控后代 | `process_exit` |
| owner 正常退出或交接 | 用户明确同意后停止所有服务，再释放 owner | `owner_shutdown` / `owner_handoff` |
| 配置变更前停止 | 明确逐项停止，完成后再改配置 | `configuration_change` |
| owner 崩溃 | 下次启动只标记未结算服务 UNKNOWN | `owner_lost` |

停止先请求平台支持的终止方式，宽限结束后强制结束受控树，再等待确认。
Windows 当前终止方式不等于应用已完成优雅关闭；实际支持何种机制就记录何种机制。
进程确定结束也不等于文件或外部系统副作用已撤销。

状态分开保存：运行状态、停止原因、根进程退出码、进程树清理结果、输出完整性。
只有确认进程和受控树结束才能显示“已停止”；清理无法确认则显示 UNKNOWN，
保留可能存在残留的说明，不能释放名额后继续假定没有旧进程。

重复 Stop 幂等；延长、到期和 Stop 竞争时通过同一状态锁及 revision 决定唯一结果。
在读取完根进程最终结果之前，不以最后几行日志推断启动或停止成功。

## 8. 持久记录与恢复

复用 v7.3 的结构：工具 Attempt 保存不可变的启动回执，`meta` 中按原 Attempt ID
保存有界的当前运行投影。没有 Service 表或第二套执行记录。

投影字段至少包含：

- 命令 ID、原 Run/会话、模式、owner generation、revision；
- 工作目录、冻结执行配置的摘要、经过既有脱敏的程序和参数；
- 开始时间、截止时间、最长总时长；
- PID 和可取得的进程启动身份，供诊断，不作为自动接管凭证；
- 运行状态、停止原因、退出码、清理状态、host 标记；
- 日志游标、累计输出字节、截断/丢失说明和最终有界尾部；
- 就绪文本是否匹配、观察时刻及启动失败信息。

首次运行中投影必须在向调用者返回“已启动”前提交。进程已启动但保存失败时，
先请求清理，并通过已有派发记录保留不确定性；不返回虚构的成功。

进程终态异步写入投影，不修改原始 tool message，不把已经完成的 Run 改回 active
或 UNKNOWN。新任务仍能在同一会话开始，不破坏“一会话一个未完成 Run”的约束。
未解决的后台 UNKNOWN 由 inspect、服务列表和独立的模型上下文警示暴露。

恢复时只将非终态服务投影变为 UNKNOWN，不自动重启、不重新附着、不凭旧 PID 杀进程。
已知终态保持不变；备份/恢复也不恢复进程，旧 generation 的非终态记录不能显示为
本 owner 的活跃服务。

每个服务最多一个当前投影。终态后只保留有界尾部，不为每次轮询创建新行。

## 9. Windows 与 Linux 边界

Windows：进程必须在恢复执行前进入带 kill-on-close 的 Job，Job 句柄由 owner 持有。
在测试确认 Job 包含受控后代、句柄不外泄的前提下，owner 被强杀会触发系统结束
受控进程树；下次启动仍把未保存终态的服务记为 UNKNOWN，副作用不能推断为不存在。

Linux：首版只支持 Full/host，沿用进程组主动清理。owner 被强杀后进程可能残留；
不把进程组称作崩溃清理保证，不根据复用的 PID/PGID 自动清理。
主进程存活时负责到期与主动停止；崩溃后检查页面提示人工核验。

服务不承诺在 owner 退出、交接或崩溃后继续运行，也不自动迁移到新 owner。

## 10. 网络与就绪判断

服务默认声明 loopback 地址，由启动命令明确设置 `127.0.0.1`，不自动增加端口
转发、代理或防火墙规则。Full 模式是同用户 host 权限，不能保证任意命令只绑定
本机地址；安全证据只采用已通过门槛的沙箱配置。

若需要 internet 权限才能完成本机访问，应如实显示其权限范围，不以“本地监听”
隐藏更广网络能力。不同网络能力的并发配置在首版互不兼容。

就绪文本是可选的有界字面字符串，不接受任意正则。匹配器处理跨输出片段的文本，
不因环形缓冲覆盖而丢失匹配机会。匹配只能表示“观察到指定文本”，不能证明端口
实际可访问或页面健康。

未指定文本时显示“运行中，未检查就绪”；实际 HTTP 可达性通过显式测试命令或
浏览器检查验证。就绪等待计入总期限，失败时停止并记录，不自动重启。

## 11. 输出策略

stdout/stderr 合计保留最近 256 KiB，使用有界环形缓冲，并持续排空管道。
累计字节数为有界整数；日志很大时覆盖旧内容，不持续增长内存或无限写入 SQLite。
日志覆盖不自动停止一个正常运行的服务。

每条输出带 stream 标签和递增字节游标，只承诺 owner 观察到的顺序。
游标早于保留范围时返回 `output_gap` 和当前最早游标；客户端显示丢失区间，
不把尾部当作完整日志。UTF-8 跨片段不截坏字符。

poll 每次按游标返回有限页，默认最多 16 KiB，并受调用 Run 的工具结果上限约束。
轮询不刷新期限、不重置累计输出、不消费重复的状态更新。运行时日志留在内存，
终态写入最后的有界尾部；owner 崩溃时未落盘日志允许缺失，并明确标注。

沿用现有已知凭证脱敏；原始日志仍可能含业务内容，不承诺识别任意秘密。

## 12. GUI、CLI 和 AI 入口

| 入口 | 操作 |
|---|---|
| GUI | 查看服务、剩余时间、输出尾部、停止、有限延长 |
| 交互 CLI | `/services` 列表，按 ID 查询、停止和延长 |
| 一次性 CLI | `freeagent services list\|poll\|stop\|extend`，支持 JSON |
| AI 工具 | `command_run` 的服务模式、`command_poll`、`command_stop` |
| AI 控制 | 查询服务策略、提议修改默认/最长时长、有限延长 |

服务模式拟定请求字段为 `mode: service`、`duration_seconds` 和可选的
`ready_text` / `ready_timeout_seconds`。具体字段在 v7.3 接口定稿后对齐，避免
并存两套后台 API。

所有入口使用同一 owner、命令 ID、revision、状态和进程句柄。
服务占用名额时，拒绝结果列出当前服务，不自动停止最旧服务。
关闭窗口或断开 CLI 仅断开该客户端；owner 真正关闭必须走停止流程。

默认时长、最长时长和启用策略均可通过 AI 对话提议修改，并走现有持久设置确认。
产品硬上限和 2 个服务名额不通过模型自行扩大。

## 13. 实施顺序

1. v7.4-0 原型：本机访问、两个命令重叠、授权耗时；明确支持矩阵。
2. v7.4-A：授权引用计数、冻结目录集合、host 门禁计数及配置变更阻止。
3. v7.4-B：独立期限、幂等延长、Stop 门禁例外、owner 到期监督。
4. v7.4-C：停止结果、终态持久化、owner 退出/交接与恢复。
5. v7.4-D：日志游标、就绪匹配、GUI/CLI/AI 接入。
6. 完整场景测试、平台竞态测试、便携包验证与实施记录。

每个阶段先修复发现的问题再进入下一阶段；阶段证据区分 PASS、FAIL、NOT_RUN、
UNKNOWN 和明确阻塞项。沙箱未通过不妨碍报告 Full 模式的实际完成情况，但不能将
整个沙箱功能标为通过。

## 14. 验收矩阵

| 范围 | 必须实际验证 |
|---|---|
| 产品场景 | 启服务、宿主访问、并行测试、停止，GUI/CLI 接续观察同一命令 |
| 配额 | 2 个服务加 1 个普通命令；第 3 个服务或第 2 个普通命令被拒绝 |
| 授权 | 交错退出、启动失败、不同目录/网络配置被拒绝，保护不提前释放 |
| 期限 | 默认/指定期限、8 小时总上限、多次延长、时钟回拨、到期无需轮询 |
| 竞态 | 延长与到期、Stop 与退出、多端重复 Stop、终态写入仅结算一次 |
| 输出 | 大量日志、游标过期、UTF-8、stdout/stderr、最后输出排空，内存稳定 |
| 就绪 | 分片匹配、超时停止、提前退出、文本匹配不冒充 HTTP 健康 |
| 配置 | 服务在跑时变更授权被阻止，停止后才可变更，关闭工具仍能 Stop |
| owner | 正常关闭、交接、强杀、再次启动均不自动恢复服务 |
| 恢复 | 旧服务 UNKNOWN 不重开旧 Run，不违反活动 Run 唯一约束 |
| 平台 | Windows Job 实测；Linux 进程组和崩溃残留边界分别记录 |
| 失败 | 持久化失败、清理不能确认、部分停止失败均保留真实结果 |
| 宿主门禁 | 两个 Full 服务重叠后一个退出，门禁仍有效；Stop/延长仍可使用 |

计时契约使用可控时钟快速验证，另做真实进程短期到期测试；不能把模拟 8 小时
称作实际运行 8 小时。资源验证至少包含持续高输出和并发服务场景，记录测量条件。

发布前运行 Windows/Linux 相关 Go 测试、race、vet，ChatUI 测试和构建、原生
launcher 测试、notices 检查、便携包干净目录测试。WebView2 的列表、停止、延长
和重连另做实际界面验证。所有未运行项明确标记。

## 15. 非目标与完成条件

不引入服务自动重启、系统服务注册、计划任务、分布式 worker、插件平台、端口代理、
自动管理员豁免、旧格式兼容/迁移层、协作后台服务或 CPU/内存/进程数限制体系。

完成条件：已确认参数全部执行有效；真实的服务加测试场景通过；运行和停止状态
来自进程证据；并发不破坏权限；日志与数据库增长有界；重启不重放；GUI、CLI、
AI 使用同一套核心。未通过的沙箱网络能力、Linux 崩溃清理限制和真实未跑项目
必须在交付记录中保留。

实际支持范围与未运行项目以实施记录为准。AppContainer 的宿主回环访问门槛未通过，
服务模式明确返回 NOT_SUPPORTED；Full/host 的实际完成不能作为沙箱网络安全证据。
停止宽限受剩余期限限制，到期不额外分配五秒运行额度；每个服务最多保留 64 次
已提交延长，确保幂等记录有界且不丢弃旧 request key。
