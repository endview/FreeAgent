### 2.2 实际画面的问题

参考本地 v8.0 验收截图 `output/pg8-ui/database.png`，本轮视觉核查范围为该设置页面，不能据此声称审阅了全部界面：

## 3. 前端重构方向

### 3.1 设计方向

- **产品**：让用户与 AI 持续处理工作，并能看懂进度、接续任务和控制执行。
- **性格**：沉静、直接、可掌控。
- **场景**：桌面工作台，内容与操作都有固定位置。
- **视觉重点**：回答正文、执行进展和需要用户决定的操作。
- **识别细节**：每轮消息旁的紧凑执行轨迹，把当前状态、工具与交付结果串起来；按需展开证据。

初始方向采用冷灰中性色和现有青绿色的克制延续。建议起点：背景 `#F6F7F9`、内容面 `#FFFFFF`、正文 `#20252B`、次要文字 `#637180`、边界 `#DCE1E6`、强调色 `#247D72`。这些是 F1 的候选值，实际页面对比度检查和用户视觉确认后再冻结。状态仍用文字与图形共同表达，不依赖颜色。

中文正文优先离线系统字体；正文、操作标签和辅助说明使用清楚的字号层级。代码另用等宽字体。深浅主题、键盘焦点和减少动态效果设置都属于同一套组件规则。

### 3.2 页面安排

| 页面 | 主内容 | 按需信息 |
| --- | --- | --- |
| 对话 | 左侧空间/会话，中间阅读区，底部输入区 | 右侧详情查看本轮工具、上下文、附件与证据 |
| 执行中 | 当前动作、停止、已采用的引导、待发消息 | 展开逐工具状态、耗时、结果及重试原因 |
| 待确认 | 不抢输入焦点的内联卡片，具体变更、影响范围、批准/拒绝 | 展开原始参数与证据；内容变化重新预览；F3 同时交付工具与控制面确认 |
| 设置 | 独立设置布局，左侧分组与子项，右侧当前表单 | 诊断、版本、完整路径和运行时标识放到相应详情 |
| 能力管理 | 已安装能力、开关、状态、配置入口 | AffectWeave 等启用后提供配置页；当前会话选择仍在输入区 |

保留会话列表宽度、阅读区宽度的像素拖拽；输入框自动增高，拖拽设置最大高度，并提供键盘调整/双击恢复默认。分组即空间，不新增独立对象。运行中 GUI/CLI 先排队、可转引导；TG 默认直接插话。Provider 草稿切页或失焦不丢失，密钥草稿仅留在页面内存。普通成功提示约两秒消失；需要修正的表单问题在字段附近说明。

### 3.3 技术选型建议

| 方案 | 收益 | 成本与适用范围 |
| --- | --- | --- |
| 现有原生 JS 转 TypeScript，拆分页面和状态模块 | 复用多，适合局部整理 | DOM 生命周期、流式更新、表单和事件解绑仍由项目手工维护 |
| React + TypeScript + Vite | 组件和状态边界更清楚，便于持续维护复杂工作台 | 有迁移成本，须逐流程复用现有契约并验收；不能靠换框架保证美观 |

**UI 框架评估建议采用 React + TypeScript + Vite + Tailwind CSS 4 + shadcn/ui（Radix Primitives）**，继续构建为 Go 可嵌入的静态资源。隔离小样的 strict 类型检查、生产构建和 12 项浏览器检查通过；原生 WebView2 和完整产品流程仍需迁移后验收。视觉问题需独立解决。

v8.1 必须同时交付 [前端框架](FRONTEND_ARCHITECTURE_V8_1.md) 和 [开发指南](FRONTEND_DEVELOPMENT_GUIDE_V8_1.md)。当前两份文档为目标草案，实施时补全实际命令、接口和页面示例。

先做对话主界面、执行/审批状态、设置页三个可交互视觉样例，使用真实契约的合成/脱敏状态，覆盖长中文与窄屏。用户确认后进入 F2；从 F3 开始，新旧开发界面可接同一隔离 Core 对照，F5 只交付一套正式前端。

应用按 Shell、会话导航、消息与流、输入器、执行详情、审批、设置、能力管理分组件；API、SSE、会话状态、草稿与布局状态各有明确边界。优先复用现有纯函数及测试。Markdown 等重资源按实际测量决定加载方式。

### 3.4 前端验收

- Windows WebView2 与公网浏览器分别检查；桌面、窄窗口、手机宽度都能完成主要操作。
- 发送、流式回答、停止、引导、队列、切会话、重新接入、审批和附件实际回归。
- 切页/失焦保留表单，密钥不进入 URL、本地持久缓存或日志。
- 重复进入页面不累积事件监听或 SSE，流式输出不反复重建整个消息列表。
- GUI 关闭仍遵守已实现的客户端/Owner 生命周期，不破坏其他客户端接续。
- 会话列表增加服务端分页与搜索；目前 Store 最多返回 50 个置顶和 200 个普通会话。现有聊天按轮分页继续复用。
- 记录首屏、长历史切换、持续流式输入和内存的前后基准；可用性和性能不能由静态截图代替。

## 4. AffectWeave 定位

读取的仓库自述版本为 `v0.2-demo`，Python 3.11+，MIT。其职责是维护人物状态并输出有预算的 `ContextPackage`；宿主继续负责模型、凭据、工具、流式输出、重试、界面和交付。

按用户要求交付 **“角色与关系 / AffectWeave”完整可选扩展**。默认关闭，选择角色和作用范围后按需启动。它管理人物基线、当前情绪、关系及人物经历；FreeAgent 管理执行事实和通用上下文。用户可随时查看、停用或切换该能力。

适配以 FreeAgent 的通用扩展契约为准：受限上下文、现有确认、Run/Attempt/receipt 关联、取消与 UNKNOWN、显式权限、统一 PG、GUI/CLI/AI 入口及可重复发行。**由 AffectWeave 仓库整体 Go 重写，Go 成为唯一生产实现，并主动适配 FreeAgent。** 旧 Python 固定为规则与合成样本的离线参考，不再同步开发功能或承担生产回退。按功能迁写人物业务与上下文编译，重构状态推进、回答/提案、PG 与回执边界；不把人物业务并入默认 Core，也不恢复 Demo 原有 API/SQLite 兼容。

A1 验证 Go 最小协议入口、取消/并发与双平台样包，核对二进制是否超过现有导入上限。成品不要求用户安装 Go/Python/Node；现有通用 Python/Node SDK 仍供其他扩展使用。完整对比见 [AffectWeave 适配决策](AFFECTWEAVE_FREEAGENT_ADAPTATION_DECISION_2026-11-06.md)，实际接口见[扩展开发指南](EXTENSION_DEVELOPMENT_GUIDE.md)。指南区分当前可调用能力与 v8.3 尚需实现部分，Go 示例随 A1 实测后补入。

| 内容 | 归属 |
| --- | --- |
| 模型、工具、审批、Run/Attempt、消息采用、交付事实、总窗口预算 | FreeAgent Core |
| 人物基线、角色状态、人物关系、人物经历及其上下文片段 | AffectWeave |
| 可复用工作方法、Skill、经确认的固定操作经验 | 经验总结与既有 Memory/Skill 管理 |

角色偏好和关系值不改变权限。AffectWeave 的 ActiveThread 表达人物尚未解决的事情，涉及实际工作时引用现有 Run，不发展成另一套任务执行系统。

## 5. AffectWeave 接入前需修正的契约

### 5.1 PG 存储与数据范围

源码 `core/repository.py` 当前提供内存与 SQLite 仓库。FreeAgent 配套版实现同一 Repository 协议的 PG 版本，并使用扩展自己的逻辑库与受限角色；可复用同一个 PG 实例。仅在明确启用持久化时创建扩展数据。

扩展不读取 Core 的执行数据库，也不获取 Core 数据库凭据。FreeAgent 配套版不引入 SQLite 产品运行路径；内存模式用于临时状态和测试。既有 Demo 是否保留 SQLite 属于其独立仓库维护选择。

状态确认复用现有控制操作 ID、摘要和期望版本；扩展将状态更新与该 ID 的去重结果放入同一 PG 事务。回执丢失后查询原结果，无法确认时保留 UNKNOWN，不创建新操作重做，也不引入另一套审批或跨库补偿服务。

配套备份组合已有 Core backup 与扩展 pg_dump，只暂停 AffectWeave 新写回并有界排空在途修改，Core 普通任务继续。记录持久来源边界；扩展落后可补读，领先缺源/混搭备份拒绝启用。超时或未决写入不发布完整备份，最终释放暂停；不建设通用快照协调器。

授权边界至少包含 Core 身份、空间、角色和实际交互者。私聊内容不因同一个角色出现在群里就进入群上下文。角色跨空间共享必须显式选择范围。

### 5.2 上下文与状态推进分开

`prepare_turn()` 会登记输入、创建行为记录并写入新版本，不是纯查询。因此：

- 仅对 Core 已实际采用的输入推进一次，绑定真实消息/输入身份与 Run。
- 上下文预览、token 估算、同轮工具后的模型调用、模型重试不创建新人物事件。
- 复用固定输入和状态版本生成上下文；AffectWeave 的幂等返回会重新从聚合状态构建准备结果，适配层还须明确重试采用哪一版本。
- 排队但尚未采用的文字不推进人物状态；已采用的插话绑定原 Run 和其输入记录。
- FreeAgent 分配该扩展的预算，统一核算渲染后片段、输出契约及所有其他上下文，避免重复加入近期对话和重复摘要。

### 5.3 普通回答与结构化状态提案

当前 Demo 的 `commit_output()` 消费包含回复和状态提案的 JSON，并立即应用部分状态变化。这不能原样包住 FreeAgent 的每个模型步骤。

成品需要同时交付角色配置、有界上下文、临时状态、经确认的长期状态和实际交付追踪；保持普通回答与工具调用链路，并把“候选回复登记”和“状态提案应用”拆开：

- 可见回复按正常方式流式交付；机器提案不混入用户正文。
- 角色配置、长期关系、人物记忆等模型提出的持久修改，复用明确内容/范围/版本的确认流程。
- 开启扩展不等于授权后台隐式人格学习。当前会话的临时变化与长期写回明确区分。
- 如果状态分析需要额外模型调用，必须显式启用、计入用量，并有界执行；不默认给每轮增加一次分析请求。确定性状态推进和模型提出的长期修改分别记录。

### 5.4 交付结果不能从生成结果推断

FreeAgent 当前已有 `context.prepare` 与 `turn.finished` 扩展路径。`turn.finished` 的语义是执行结束；不能将它当作 TG 已发送或 GUI 已呈现。

- 复用渠道已有 send/delivery receipt，必要时补一个按授权范围提供的通用交付结果通知或查询。
- 复用现有记录和游标提供有界补读与幂等应用，不建设全局事件总线。
- 回复生成、平台发送成功、用户后续反应、明确结果确认分别记录；发送成功不代表用户已读。
- failed、UNKNOWN 和部分发送保持原事实。扩展故障后补读 receipt，只补人物记录，不重新发送消息或执行工具。
- Demo 的 delivery 接口以 delivered/complete 表达结果，不能完整表达 FreeAgent 的未知状态；适配前明确 UNKNOWN 的保存与后续核对，不能压成 false 后宣称确定失败。
- 群聊多人、多个对话对同一人物状态并发写入时，以版本检查解决冲突，不用最后写入覆盖。

### 5.5 故障与停用

可选扩展失败时显示原因，普通任务按选定策略继续或提示。若人物状态已产生不确定写入，保留待核对标记。停用立即停止后续上下文注入和新分析调用，数据按明确删除操作处理。已有用户任务、权限与 Core 历史不依赖扩展进程存活。

## 6. AffectWeave 成品交付范围

以下是同一次产品交付的验收清单，可以分步开发，不拆成“先交只有上下文注入的版本，以后再补持久状态”。

| 范围 | 成品要求 |
| --- | --- |
| 角色管理 | 创建、选择、编辑、停用、删除与导出；基线版本明确，模型修改必须确认 |
| 情绪/关系/人物经历 | 有来源、时间、作用范围和版本；临时计算、记录事实、长期模型提案分别处理 |
| 上下文 | Core 授权和总预算控制，按需选择人物片段；不重复装配原聊天历史 |
| 回答与执行 | 支持正常流式回答、工具、引导、停止与恢复；结构化状态提案不混入用户正文 |
| 交付与反馈 | 已生成、实际发送、部分发送、失败、UNKNOWN 和后续反馈分别记录；不以模型声明提升证据等级 |
| 持久化 | 扩展自己的 PG 数据范围、受限角色、CAS/幂等；支持重启和多对话并发冲突处理 |
| 备份恢复 | 含扩展状态、版本、Core 关联及恢复顺序；Core 与扩展备份的时间边界明确，恢复后补核对，不误称跨库原子快照 |
| 空间与身份 | Owner 私聊、其他人、群空间按既有授权；同空间可接续，跨空间使用须显式授权 |
| 产品入口 | 设置中完整配置/状态/错误处理；输入区选择本轮能力；GUI/CLI/AI 使用同一控制操作 |
| 生命周期 | 未启用不启动；启动就绪、失败提示、受控重启、停用、清理与版本检查 |

## 7. 保留的核心优化与经验总结

- v8.1 同时测量界面和 API；v8.2 再按证据处理 Core/PG 查询、上下文装配、模型首字和工具等待。

- 压缩验收检查连续多轮后的约束、关键文件、未决事项和来源；恢复验收检查实际副作用次数。
