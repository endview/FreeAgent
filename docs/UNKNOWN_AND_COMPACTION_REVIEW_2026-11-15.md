排查对象：Hytron 的 FreeAgent v8.8.0-dev.5。只读查询常驻实例，复现使用本机独立 PostgreSQL、合成输入及临时 Go overlay。没有替用户结束任务、重试工具、修改生产设置或调用生产模型。

## 1. P1：确定的只读拒绝被误判为副作用 UNKNOWN

`control_read_state` 的查询参数可以带 `extension_id`。`control_query.go:113` 在本轮没有选择该扩展时返回普通 `ErrPermissionDenied`，这一检查发生在 Execute 阶段。通用工具执行器 `service.go:1389` 仅把 `Certain=true` 的 `CallError` 识别为确定错误；普通错误进入 UNKNOWN。

因此一次确定的读取拒绝被当作操作可能已经产生副作用，触发只读核验。随后 `context_summary.go:351` 按 UNKNOWN 状态禁止上下文修改，产生“先查设置失败 → 任务结果未知 → 无法压缩”的连锁反应。

原 Attempt 的响应只留下空 Content 和 unknown Outcome，没有保留原始的权限拒绝原因。模型与用户最后只看到泛化的英文停止原因。

修复范围：

- 本地可确定的参数、能力选择和授权检查前移到 Prepare，或者转成确定的工具错误；明确说明“扩展已配置，但当前请求未选择，未读取私有状态”。不能为方便读取而自动扩大本轮能力或受众授权。
- 保留有界、脱敏、可定位的错误代码与说明。普通失败不能变成成功；真正的写入、外部请求或提交结果不确定仍保留 UNKNOWN。
- 对现有错误记录只做可审计的精确协调：绑定原 Attempt、工具与冻结请求，证明属于未触发扩展 RPC 的确定拒绝后记录纠正信息。不能批量清空 UNKNOWN，也不能只改 Run 状态掩盖旧 Attempt。

## 2. P1：保留用户原话把大量旧回复和工具内容一并锁住

`context_retention.go:10` 只累计用户输入的大小，`context_retention.go:51` 则把整个可压缩前缀的终点移到该用户输入之前。因此保留一条旧用户输入，也会保留它后面的全部助手回复与工具结果；这些后缀内容没有计入保留预算。

线上手动压缩的新增来源 #m137–#m201 中，可见来源 51 条，用户输入 12 条、合计仅 458 字节，但可见正文合计 59,691 字节，其中工具正文 49,972 字节。自动模式根据很短的用户输入继续向前保留，压缩前缀退回原检查点，结果没有内容可压缩。手动压缩不应用此保留逻辑，所以能成功。

修复范围：按实际保留的完整后缀占用约束保留区，不能只算用户输入。保留当前输入与协议完整组；达到硬预算时向后调整近期保留边界，允许更早的已完成组进入摘要。仍保护当前 Run、未知效果与原始记录，不以丢弃记录或拆断工具协议解决。

测试补齐“连续短用户消息 + 长助手回答/工具结果”，既覆盖默认自动目标，也覆盖已有摘要后的再次压缩。现有许多执行夹具显式使用旧手动字节策略，不能代表默认自动策略。

## 3. 配置缺口：线上模型窗口未声明，旧字节保护仍是主要限制

当前 DeepSeek 配置中 `context_window_tokens` 未声明，ContextState 的窗口为 0，来源为 `local_byte_budget`；请求保护仍为 128 KiB。未知窗口路径额外用 4,096 输出 token × 4 字节进行保守预留，所以可用输入字节为 114,688。本次限额请求比这个输入保护多 2,085 字节。

这能解释为何远未证明达到厂商模型窗口时也停止。不能据本地估算把它解释为厂商 token 超限，也不能未经核实填入任意窗口或直接取消保护。

修复范围：核实实际型号的官方窗口后，通过现有模型设置补能力声明；按所需载荷设置独立的 HTTP 字节保护。界面清楚区分“模型窗口未知”“本地载荷保护”“Provider 明确拒绝”。不静默改写用户已保存的自定义值。

## 4. P2：预防性暂停同时挡住硬预算恢复

`context_recovery.go:17` 在检查压缩计划前读取暂停记录。若 `failure != source`，无论触发来源均立即返回；`trigger` 目前只用于事件说明，不区分预防性与硬预算恢复。

独立复现确认，同一配置的预防性暂停也会挡住 Provider 明确窗口拒绝后的恢复分支。当前线上会话没有该暂停记录，因此这是同类问题中的额外缺陷，不是本次 21:58 限额的直接证据。

修复范围：区分预防性与硬预算决策，但不能在硬预算下反复原参数重试已知会失败的摘要。硬预算应重新检查可压缩来源、可用设置与安全的退路，给出确定原因；必须有人调整配置时提供无需模型的操作入口。

## 5. P2：核验和反馈无法帮助用户退出错误状态

`tool_verification.go:192` 最终只允许同步单文件 create/edit 在满足运行回执及后续读取证据后自动协调，但 `service.go:1395` 会为任何非确定工具错误启动这套核验。对于本次控制读取，它从一开始就不可能通过单文件协调器，增加调用后仍只得到 UNKNOWN。

另外，GUI 对所有 UNKNOWN 固定显示“副作用不自动重放”；没有区分“读取失败”“真正效果未知”“上下文维护被哪条记录阻塞”。TG/群聊控制状态还可能因受众过滤返回空的扩展列表，空值没有表达“不可见”或“未选”，容易被模型解释为“没有安装/没有启用”，并写入后续摘要。

修复范围：核验前判断是否有适用的证据协调器；确定读取失败直接回到模型正常处理。对真正 UNKNOWN 显示具体工具、确定已知的部分、证据和下一步；受众不可见、全局可用、本轮选中分开表达。操作 schema 的读取不应因附带读取了无权访问的扩展私有状态而完全丢失。

## 最小实施顺序

1. 确定拒绝的分类、原错误保留、核验适用范围；补只读查询失败后会话能继续、压缩仍能运行的回归。
2. 近期用户原话保留算法按整个后缀计量；补短输入长结果、已有摘要、三种协议完整性、受众隔离与硬预算测试。
3. 区分预防性暂停和硬预算恢复；保留同源同配置不循环压缩的约束。
4. 补模型窗口与载荷设置的清楚提示，修正扩展状态及 UNKNOWN 的反馈；精确协调当前线上受影响记录，再做 TG/Web 验收。

沿用现有 Attempt、Outcome、meta、控制设置与 UI；不新增数据库表、独立恢复服务或扩展业务内核。

## 验证与限制

临时 overlay 的三个诊断用例均复现了当前缺陷：

- `TestReviewReproduceReadDenialLocksCompaction`：确定权限拒绝 → UNKNOWN → 一次无效核验 → 手动压缩被阻塞。
- `TestReviewReproduceShortInputsPinLargeAssistantHistory`：32,727 字节请求超过 16,000 字节保护；两条短输入把全部旧助手内容锁住；自动可压缩来源为 0，手动有来源，尚未调用摘要模型。
- `TestReviewReproducePreventivePauseAlsoBlocksHardRecovery`：预防性配置暂停同样拦截 prepared 和 provider_refusal 恢复。

这些是断言缺陷确实存在的诊断测试，PASS 不代表修复通过。全部使用合成文本与独立临时 PostgreSQL，不读取生产 Key；overlay 位于忽略目录，不改正式测试。证据在 `output/unknown-context-review-20261115/`，生产完整记录仅作为私有诊断留存。
