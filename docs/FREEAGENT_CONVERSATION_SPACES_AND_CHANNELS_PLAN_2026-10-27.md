# FreeAgent 统一对话空间与外部渠道接入方案

创建：2026-10-27。更新：2026-10-28。状态：已开始 v7.5-A；本文件的后续平台规则仍是验收目标。

依据：[两轮讨论整理](FREEAGENT_CHANNELS_AND_CONVERSATION_SPACES_BRIEF_2026-10-26.md)、“空间与现有结构混合”的结论、对当前代码的核对，以及后续关于两层权限、默认 None 和共享群聊上下文的确认（见第 12 节）。开源项目参考见第 13 节。

## 1. 结论

采用混合方案：本地分组和外部渠道使用同一套空间模型、同一组操作和同一个 attach 接口。GUI、CLI、AI 和外部渠道看到的是同一批空间和对话，可以跨入口接续。

统一的是对话的归属方式。渠道的平台数据由渠道适配器保存；文件和命令的执行边界仍由工作区和执行配置决定。外部渠道的操作权限只取当前空间和本次请求发起人两者中较低的一级，不再叠加对话权限。

空间和未设置的外部人员默认 None。None 表示可以聊天、不能操作，不表示禁止参与或排除其消息。群聊背景包含 None 成员的发言；普通消息只记录，明确唤醒后才启动回答。

| 层 | 处理方式 | 原因 |
|---|---|---|
| 空间与对话 | 统一：同一套表、操作和 attach 接口 | 各入口看到同一批对话，可以接续 |
| 空间和人员权限 | 统一：由核心保存和校验 | 同一平台稳定身份在不同群聊、私聊中使用同一人员记录；每次请求还受所在空间限制 |
| 渠道数据（Bot 配置、消息游标） | 分开：由渠道适配器保存 | 平台私有数据放进核心会让核心变重 |
| 工作区与执行配置 | 分开：不随空间自动切换 | 空间负责归属和权限上限，不代表物理目录；移动对话后按目标空间重新计算权限 |

## 3. 数据模型

新增 `spaces` 表：

```text
id
title
source                      local | telegram | lark | qq
chat_kind                   本地空间为空；private | group
external_chat               本地空间为空；外部聊天的稳定 ID，唯一
default_conversation_id     可为空
active_conversation_id      外部消息的路由目标，可为空
multi_conversation_enabled  只影响外部渠道交互
created_at
updated_at
```

`conversations` 新增必填列 `space_id`。

- 本地空间和外部空间只差 `source`、`chat_kind` 和 `external_chat`，列表、切换、新建、设为默认、移动都走同一组操作。
- 初始化数据目录时创建“本地”空间，它不能删除。新建对话放入当前选中的空间，默认是“本地”。
- 外部空间按聊天绑定：私聊对应一个人，群聊对应一个群。聊天标识为 `<source>:<Bot或应用ID>:<聊天ID>`，飞书还要包含租户。
- 人员身份按平台实际稳定 ID 的有效范围确定，与聊天身份分开。Telegram 使用 `telegram:user:<用户ID>`，同一账号在不同群、私聊和 Bot 中不重复授权；Lark/QQ 的 ID 如果受租户或应用限制，把必要范围纳入键。不同平台账号不自动认定为同一人，不用昵称授权，也不为 Telegram 的同一用户增加手工关联步骤。
- 人员权限存入现有 `meta`，键为 `person/<人员身份>`，记录级别、显示名和更新时间。没有记录的人按 None 处理。
- 空间权限存入现有 `meta`，键为 `space/permission/<空间ID>`，新空间显式写入 None，缺省读取也按 None。空间内新建对话不建立另一份权限记录，不跟随全局默认。
- 对话仍绑定工作区；文件范围、工具开关和沙箱参数复用现有执行配置，不能据此提高空间或人员的权限级别。
- Run 在现有冻结配置里记录入口、空间 ID、真实发起人、本次触发消息 ID、两侧权限及生效权限。由核心根据渠道鉴别后的身份生成，模型不能填写或覆盖。
- 群消息复用现有消息记录，保存真实发送人、平台消息 ID、时间和引用关系，并区分背景消息与触发本次请求的消息。发送人名称仅用于展示。
- 配对关系由外部空间本身表示：配对成功即创建外部空间，解除配对即删除该空间，不另存白名单。配对只接入聊天，不授予操作权限。
- 适配器的平台数据（如消息游标）写入现有有界 `meta`，键以 `channel/<source>/` 开头。一次性配对码只保存在 Owner 内存中，限时、限次。
- Bot Token 存入现有密钥存储，只能通过本机密钥页面或隐藏输入设置，不进入数据库、日志和对话。
- 不新增渠道消息表、独立上下文库或信任评分表。来源和用途使用现有消息元数据；背景消息不能被重新解释成待执行请求。
- 按“不兼容旧版本”的规则，提升存储版本并使用新数据目录，不写迁移层。

## 4. 权限

### 4.1 两层权限与 None

外部渠道只按两层决定操作权限：**当前空间权限**和**本次请求发起人的人员权限**。两侧都使用以下四个级别：

```text
None < Ask < Workspace < Full
本次操作权限 = min(当前空间权限, 本次请求发起人权限)
```

空间和人员的缺省值都是 None。人员权限按稳定身份全局生效，首版不为同一人增加按群角色、用户组或第三层对话权限。

| 空间权限 | 发起人权限 | 本次行为 |
|---|---|---|
| None | 任意 | 可聊天，不执行操作 |
| 任意 | None 或未设置 | 可聊天，不执行操作 |
| Ask | Full | Ask，不能越过空间限制 |
| Full | Ask | Ask，不能借用其他群成员的 Full |
| Workspace | Full | Workspace |
| Full | Full | Full，沿用现有 Full 执行语义 |

- **None 不是封禁**：其发言进入群背景，被明确唤醒时可以纯聊天、总结已提供的群消息。不能读取、搜索、修改或删除本机文件，不能运行命令、操作命令会话、调用网络搜索、MCP、扩展或其他操作工具，也不能读取未向群公开的执行结果。
- None 的限制同时作用于工具提供和实际执行入口，包括模型原生搜索等 Provider 工具。只提供空工具列表不构成验收；绕过列表直接请求执行也必须被核心拒绝。
- 产品正常加载聊天记录、调用聊天模型、保存对话和回复当前聊天，不算给模型授予文件或命令能力。None 仍能使用已开放的对话列表、查看公开状态和参与聊天；不能借整理命令更改配置或权限。
- Ask、Workspace、Full 继续使用现有工具规则和执行边界。Ask 中需要审批的操作使用按钮批准；只读操作和已有允许规则是否免批，以现有核心判定为准。Full 不额外强制逐工具确认，产品设置类确认仍然保留。
- 降级时按较低模式构建执行配置，不沿用 Full 的宿主机能力。Ask/Workspace 命令使用对应沙箱，不能把 MCP 或扩展宿主进程当作降级后的旁路；不能满足限制的能力不提供。
- 本机 GUI/CLI 是可信管理入口，按选中空间的权限使用同一核心，不需要伪造一个 Telegram 发起人。接续外部 Run 时保留原发起人和原权限上限，不能因为由本机点击继续就提高权限。

### 4.2 发起人、审批与权限变化

- 当前请求的发起人来自渠道实际事件。历史发言、转发、引用、显示名以及压缩摘要中的“管理员”字样均不能改变发起人，也不能提供授权。
- 只有 Run 的原发起人和本机可以批准、继续或放弃。群里其他人看得到按钮也不能代批。None 请求不创建可由他人批准来升级权限的待执行操作；有权限的人需要另外发起自己的明确请求。
- 审批复用现有待确认记录，绑定空间、对话、Run、发起人和具体操作内容。按钮点击后由核心校验实际点击者、当前权限、待确认状态和操作内容；内容变化重新确认，重复点击只生效一次。
- GUI 使用卡片，CLI 使用提示，Telegram 使用按钮。群消息中的“批准”“我已同意”只是普通文本，不作为批准入口，不增加聊天确认码协议。
- 停止由原发起人、本机，或当前两层生效权限不低于该 Run 权限且不为 None 的成员操作；旁观者不能仅因持有按钮就停止任务。
- 空间权限、人员权限、配对和渠道启用由本机 GUI/CLI 管理；AI 可以提出具体变更，必须在本机确认。渠道中的 `/mode` 展示空间、本人和生效权限，不作为提升权限的入口。
- Run 保留开始时的权限上限。批准、继续和每次工具执行前重新核验当前两侧权限：后来提高权限不扩大旧 Run，降低或撤销权限后不再发起原权限下的新操作；需要时停止现有执行。停止不代表已经产生的副作用被撤销，UNKNOWN 沿用现有证据规则。
- 撤权必须请求停止已由该空间或人员启动的后台命令和服务，不能仅隐藏后续工具。终止或清理无法确认时保留 UNKNOWN 与资源占用；权限下降不能被正常配置变更的忙碌锁阻塞。
- 产品设置类确认与文件、命令审批保持分开。两者复用已有核心确认能力，不再建立一套渠道专用审批对象。

### 4.3 共享上下文的边界

权限校验保证 None 发起人不能直接操作资源，但不能保证共享群消息不会误导由 Full 用户发起的模型任务。来源标注、“仅作背景”的提示和压缩摘要都不构成提示注入隔离。

保留共享群聊体验，不默默降级 Full，也不为此引入额外代理或逐条信任评分。Ask 的审批、已有工具限制和沙箱继续限制实际操作；双方 Full 的宿主机执行仍属于用户明确启用的 escape hatch，不能宣称已消除间接提示注入。

群聊已经公开的回复对群成员可见，None 不是对公开内容的保密隔离。其他空间的私聊、本机私密记录、未发布到群的工具输出和原始日志不得因共享上下文而自动提供给群成员。

## 5. 行为规则

### 5.1 空间

- 本地空间由用户在 GUI/CLI 中创建，或由 AI 提出、经确认后创建；可以存放任意数量的对话，也可以为空。
- 外部空间在配对成功时创建，同时创建第一个对话，设为默认对话和当前对话。
- 未配对的私聊直接拒绝。群聊配对后，空间与未授权成员均为 None，可以聊天；配对不提升空间或兑换人的权限。
- 外部空间的名称默认取平台显示名（私聊为对方名称，群聊为群名），可以修改；匹配只用稳定 ID。
- 外部身份只能看到和操作自己所在聊天的空间。
- 群里记录实际收到的普通发言，只有明确发给 Bot 的消息才启动回答，例如命令、@Bot 和回复 Bot。是否能收到普通发言受 Telegram 的消息投递规则限制，见第 7 节。

### 5.2 外部渠道的单对话和多对话

- 默认单对话：所有消息进入默认对话，渠道中不提供列表、新建和切换。
- 发送 `/multi on`，或在本机开启后，才可以列出、新建、切换对话和设为默认。
- 关闭多对话后，消息回到默认对话；其他对话保留，在 GUI/CLI 中仍可见。
- 在本机为外部空间新建对话，不会自动开启该渠道的多对话。
- 外部空间的整理（开关多对话、新建、切换、设为默认）需要当前空间与发起人计算后的权限达到 Workspace，或在本机操作；不能只检查人员级别。None 仍可在已开启多对话时查看该聊天的列表。
- 单对话模式下需要清理上下文时，使用现有手动压缩 `/compact`。

### 5.3 当前对话

- `active_conversation_id` 只决定外部消息进入哪个对话，单对话模式下始终等于默认对话。群空间的当前对话由全群共用。
- GUI、CLI 当前查看的对话由各自客户端保存，互不抢占。
- 同一对话可以同时在 GUI、CLI 和外部渠道打开，三方看到同一份消息记录。
- 渠道按 Run 创建时绑定的空间、聊天和对话推送面向该聊天的回复、审批和公开状态，包括从本机发起的 Run。切换当前对话只影响后续消息，不能使旧 Run 改投其他聊天；必要时在卡片标注所属对话。GUI/CLI 打开外部空间时明确显示回复目标；原始工具输出、凭据和本机私密日志不自动广播。

### 5.4 Run 和忙碌

沿用现有规则：每个对话最多一个未结束 Run，Owner 同一时间只执行一个 Run。渠道消息无法创建 Run 时：

| 情况 | 渠道回复 |
|---|---|
| 本对话正在运行 | 提示忙碌；有权停止的人看到停止按钮 |
| 本对话等待确认 | 提示等待确认；原发起人可重看审批卡片，其他人不能凭新消息代批 |
| 本对话已停止、受限或 UNKNOWN | 发起人看到继续和放弃按钮，其他人看到等待提示 |
| 其他对话正在运行 | 提示 FreeAgent 正在处理其他任务；空闲后通知一次，由用户重新发送 |
| 对话不属于 Owner 当前工作区 | 说明原因，不自动切换工作区，也不自动新建对话 |

- 因忙碌未启动的请求不排队，之后也不补执行；其群消息可保留为背景，但不得在空闲后重新解释成待执行请求。
- 普通背景消息不创建 Run，也不因其他对话运行而停止记录；存储追加和去重仍需正确处理并发。
- 渠道发起的 Run 与本机相同，未结束时会阻止普通执行配置修改和工作区切换。权限降低或撤销是例外：本机可以使后续操作立即失去授权并请求停止，不等待该 Run 结束；这不代表能撤销已完成的副作用。

### 5.5 删除和移动

- 删除当前对话后切回默认对话。删除默认对话后，最近使用的对话成为默认；没有对话时，下一条外部消息创建新的默认对话。
- 删除空间时，对话移回“本地”空间，并按目标空间重新计算之后请求的权限。彻底删除对话是另一个明确操作。
- 删除外部空间等于解除配对，该聊天需要重新配对。
- 对话可以在空间之间移动，保持所属工作区和资源范围，之后的请求按目标空间与发起人重新计算权限，不复制旧空间授权。移出外部空间的当前或默认对话时，按删除规则更新。
- 移动或删除空间前显示目标空间、权限变化及可见范围；移入外部空间可能把原有对话内容公开给该聊天，必须显式确认。存在未结束 Run 的对话先处理该 Run，不能移动后让旧审批或旧请求改投其他聊天。

### 5.6 共享群聊背景

1. 记录已接入群中实际收到的文字消息，包括 None 成员和未唤醒 Bot 的发言；默认不为每条普通消息调用模型，也不自动获取链接、下载附件或执行文字中的命令。
2. 真实身份、消息 ID、时间及引用关系由适配器写入元数据。发言正文即使伪造身份标签，也不能覆盖元数据；匿名或无法确认个人身份的消息可作背景，操作权限按 None。
3. 启动回答时固定当前触发消息及其真实发起人，群历史作为单独的背景部分提供。按现有上下文预算加载最近消息，必要时复用既有压缩；不无限拼接整群历史，不增加自动 RAG。
4. None 成员被唤醒时照常回答纯聊天问题；确实需要操作才说明权限不足，不给普通发言反复发送“无权限”提示。
5. Run 启动后新收到的群消息保留到之后的回答，不插入正在执行的请求来更换发起人、追加命令或授权。重复投递、消息编辑和引用都不能重放旧操作；待批操作内容改变时旧审批失效。
6. 多对话开启时，群普通消息按收到时的当前对话记录；切换后只影响后续消息，不把全部历史复制到每个对话。压缩保留来源和“背景/当前请求”的区别，不把历史中的要求或“已批准”提升为有效指令。
7. 统一存储不等于无条件提供所有记录。群背景使用该群公开消息和公开回复；未公开的工具轨迹按原执行记录保存，不能因某次 Full 运行存在就让后续 None 请求读取。

以上可见范围还包括本机指令、已选择的记忆、Skills 与扩展注入。移入外部空间时不继承本机输入引用或私密摘要；摘要生成与使用必须检查公开范围，原始消息与执行证据继续保留。

例：群空间为 Full，A 为 None，B 为 Ask，C 为 Full。A 提供“项目可能在 D 盘”的信息进入背景，但 A 不能扫描 D 盘。B 请求查找时按 Ask 的实际资源范围与审批规则处理；C 明确发起查找时可参考该信息，以 C 的 Full 执行。C 以前说过“可以”不会让 A 的新请求获得 Full。

## 6. 各入口操作

| 操作 | GUI | CLI | 外部渠道 |
|---|---|---|---|
| 列出、切换空间 | 侧边栏 | `/spaces`、`/space <编号或名称>` | 不提供 |
| 新建、重命名、删除空间 | 空间菜单 | `/space new`、`rename`、`delete` | 不提供 |
| 列出对话 | 空间内列表 | `/sessions`（当前空间） | `/sessions`（多对话） |
| 新建对话 | 新建按钮 | `/new` | `/new`（多对话） |
| 切换对话 | 点击对话 | `/resume <编号>` | `/resume <编号>` 或按钮（多对话） |
| 设为默认 | 对话菜单 | `/space default` | `/default`（多对话） |
| 移动对话 | 拖到空间 | `/move <空间>` | 不提供 |
| 开关多对话 | 空间菜单 | `/space multi on` 或 `off` | `/multi on` 或 `off` |
| 空间权限 | 空间详情，复用权限控件 | 空间权限设置 | `/mode` 只查看空间、本人及生效权限 |
| 人员权限 | 空间详情 | `/people`、`/people set <编号> <级别>` | 不提供 |
| 生成配对码 | 渠道设置 | `/pair <渠道>`，不附带权限授予 | 不提供 |
| 状态、停止、继续、放弃、压缩 | 现有入口 | 现有命令 | `/status`、`/stop`、`/continue`、`/abandon`、`/compact` |

- 用户直接操作通过核心授权和必要确认后生效，权限按第 4 节；Full 授权、跨空间公开内容等显式确认不能跳过。
- 空间和对话的调整都提供控制操作。AI 可以提出，确认后生效，沿用 GUI 卡片、CLI 提示及渠道按钮；权限管理等仅限本机确认的操作仍回到本机处理。None 的聊天回复可以解释如何设置，不得借控制工具自行更改配置。
- GUI 中，“本地”空间的对话直接显示在顶层，保持现有置顶和时间分组；其他空间显示为可折叠分组；外部空间只有一个对话时显示为一行，点击直接打开。置顶分组仍是全局的，显示在最上方。
- 外部空间的详情列出在该空间发言过的人，可以直接设置人员权限。
- 界面文案统一称“空间”，避免和“工作区文件夹”混淆。

## 7. 外部渠道

渠道适配器是 Owner 进程内的可选组件，按配置启用，不做插件市场或模块生命周期管理。它调用与 GUI/CLI attach 相同的核心操作，请求带上聊天和发言人身份，由核心校验空间归属和人员权限。

适配器负责：

- 解析聊天和发言人身份，找到对应空间；
- 收发消息和流式回复，采用限频编辑消息，超长内容分段；
- 展示审批按钮或卡片，按点击人的 ID 传递确认；
- 用渠道、Bot/应用、聊天和平台消息 ID 组成去重键，并作为现有 `request_key`；记录背景与触发执行共用消息身份，不能在唤醒、重连或编辑后重复创建 Run；
- 断线重连、按聊天保持消息顺序，按人限流。

核心负责空间、对话、Run、工具、权限、审批、UNKNOWN 和 Owner 生命周期。适配器不直接执行工具。

- **配对**：本机生成一次性配对码。私聊发送配对码完成绑定；在群里发送则把该群接入。新空间为 None，兑换人和其他未授权成员仍为 None，不能因为获得群里的配对码而获得操作权限。
- **审批卡片**：显示操作摘要，内容过长时截断，并提示在本机查看完整内容。同一审批只生效一次。
- **离线**：Owner 未运行时不自动启动。启动后丢弃离线期间积压的消息，每个聊天提示一次，不执行。
- **连接方式**：优先使用不需要公网入口的方式：Telegram 用长轮询，飞书用官方长连接。QQ 按官方当前支持的方式接入；如果只能用 Webhook，需要用户自备公网入口，作为平台限制写明。QQ 对主动消息和被动回复有时限和次数限制，长任务可能只能推送最终结果。
- **范围**：Telegram 支持私聊和群聊的文字消息。附件、图片和文件回传放到后续版本。
- **群消息投递**：接收普通群消息通常需要关闭 Bot 的 Privacy Mode，或让 Bot 拥有管理员身份。接入界面说明当前能否收集普通发言及操作方法，不自动扩大 Telegram 权限。Telegram 投递设置只控制能收到什么，不改变 FreeAgent 的空间或人员权限。
- **历史范围**：首版只使用接入后实际接收到并保存的消息，不承诺补齐加入前或离线期间的整群历史；被离线规则丢弃的请求不重放。平台实际投递不到的内容不得伪装成已记录。

## 8. 跨对话并行运行评估

**现状**：数据库只要求每个对话一个未结束 Run，本身允许多个对话同时运行。限制来自四处单例状态：`TaskService` 的 `cancel` 和 `activeChat`，`Store.runMu` 全局锁（处理、继续、放弃都要拿），ChatUI 服务端的 `active`，以及只有一份的审批和事件回调。

**对效率的影响**：

- 外部用户和本机互相等待。一个长任务运行几分钟，其他对话的消息只能被拒绝后重发。
- 同一个对话本来就只能有一个 Run。群里多人共用一个对话时，并行帮不上忙，它只改善不同对话之间的等待。
- 其他对话运行时，无法放弃另一个对话里已停止的 Run。

**已有基础**：

- 每个 Run 使用独立的 Service 副本和冻结配置。
  - 文件工具带修改前哈希，但现有检查和替换不是原子提交。v7.7 需要 Owner 共享的短时修改锁覆盖最终检查和发布，才能保证两个 Harness 工具的交错写入不会基于同一旧哈希都成功；命令和外部程序直接改文件仍不受该锁保护。
- 命令和服务已有 Owner 级名额，Windows 沙箱授权已有引用计数。

**需要的改动**：

1. Run 锁从全局改成按对话，另设一个全局独占门，供修改配置、切换工作区和备份恢复使用。
2. `TaskService` 按对话保存取消函数，停止只取消指定对话的 Run。
3. 审批和事件按 Run 路由；GUI 按对话显示忙碌，可以复用现有的 `running_elsewhere`。
4. 设置并发上限，建议默认 2，控制模型请求频率和本机负载。
5. 专门测试协作子任务和 UNKNOWN 恢复在多个 Run 同时存在时的行为。

**成本和风险**：改动集中在核心执行入口和 GUI 状态，规模约一个独立小版本。主要风险是审批串到别的 Run、UNKNOWN 恢复出错和竞态，需要完整的竞态测试和双对话实测。

**结论**：

- v7.5 保持单 Run，先把功能做出来。忙碌时给出明确回复，空闲后通知一次。
- 渠道稳定后安排 v7.7，在同一工作区内按对话并行。
- 让每个对话在各自的工作区运行、不受本机切换影响，改动更大，确有需要再做。

## 10. 验收

**v7.5 第一段**

- 新数据目录初始化后存在“本地”空间，所有对话都有 `space_id`。
- GUI、CLI 和 AI 操作同一批空间和对话，GUI 与 CLI 接续后状态一致。
- 新空间默认 None；本机和渠道均不因全局默认 Full 而自动提升空间权限。
- 切换查看不改变正在运行的请求；移动对话保持工作区和资源范围，之后按目标空间重新计算权限，公开范围变化必须明确确认。
- 删除空间后对话回到“本地”空间；“本地”空间不能删除。
- AI 提出的持久调整必须确认；用户直接操作通过授权和必要确认后生效。GUI 卡片与 CLI 提示继续复用已有确认机制。

**v7.5 第二段（Telegram 私聊）**

- 未配对的私聊不能创建空间或对话，也不能确认审批。
- 配对后创建空间和默认对话；单对话模式始终使用默认对话。
- 空间和未设置人员默认 None，即使全局默认是 Full；新建对话不增加第三层权限。
- 穷举四种空间权限与四种人员权限的 16 种组合，生效权限均取较低一级；任意一侧 None 都能纯聊天且不能操作。
- None 的直接或伪造工具调用均被核心拒绝：覆盖文件读取/搜索/修改、命令及命令会话、网络和 Provider 原生搜索、MCP/扩展、控制改动和未公开执行结果；不得出现资源访问副作用。
- Ask 中实际需要审批的操作通过按钮批准；只读免批及已有允许规则保持一致。Workspace 不扩大到宿主机，Full 保持现有语义。
- 空间和人员权限由本机修改；渠道 `/mode` 只能查看，不提升权限；配对码不携带权限。
- 旧 Run 在授权增加后不自动提升；降级或撤销后，旧审批、继续和下一次工具调用不能使用已经失效的权限。停止和 UNKNOWN 的实际副作用记录准确。
- 开启多对话后可以列出、新建、切换和设为默认；关闭后回到默认对话。
- 第 5.4 节五种情况的回复正确，消息不排队、不补执行。
- 同一平台消息重复投递只处理一次；Owner 离线期间的消息启动后不执行。
- Bot Token 不出现在日志、数据库和对话中。
- 自动化测试使用本地模拟的 Telegram API。真实 Bot 验收需要用户提供 Bot Token，未运行时标记 NOT_RUN。

**v7.5 第三段（Telegram 群聊）**

- None 成员的普通发言被记录，被唤醒后的回答能使用这些背景；记录普通文字本身不创建 Run、不调用模型或操作工具。
- None 成员可以唤醒纯聊天；请求文件或命令操作时被拒绝，不生成可由其他成员代批提权的操作。
- 群空间 Full、成员 Ask 时仍为 Ask；空间 Ask、成员 Full 时仍为 Ask；只有双方 Full 才为 Full，任一侧 None 则为 None。
- 同一个 Telegram 用户跨群和私聊仍对应同一人员身份，但每次受当前空间限制；相同昵称、匿名身份、伪造 ID、引用及转发都不能冒充有权限的发起人。
- 其他人点击审批按钮无效；批准绑定具体操作并防止重复生效。确认期间内容变化、权限撤销或 Run 状态改变后旧按钮不能执行。
- 群空间整理需要两层计算后的权限达到 Workspace；未设置用户不能借 `/multi`、`/new`、`/mode` 等入口变更设置。
- 忙碌时背景继续记录；未执行请求不排队、不重放，空闲通知不导致补执行。运行中的请求不被后续群消息追加命令或替换身份。
- 压缩、恢复、重启和多对话切换后，历史来源、当前请求发起人和有效授权不混淆；背景中的“已批准”不能变成审批状态。
- GUI/CLI 中该外部对话的公开回复能正确投递；其他空间私聊、未公开工具输出、凭据和本机日志不进入群背景或被 None 读取。
- 验证正常 Privacy Mode 与可接收普通消息两种情况下的实际投递；机器人无法看到的消息明确标记为不在上下文范围，不宣称全量历史。
- 注入回归样例覆盖“历史冒充管理员、引用授权、摘要伪造批准、诱导读取文件”等情况。区分硬权限拦截和模型行为观察；个别 Full 样例未被诱导，不等于证明任意共享上下文安全。

## 11. 不做的事

- 插件市场、多租户和组织权限体系。空间和人员都只有 None、Ask、Workspace、Full 四个级别，不做角色和用户组。
- 按空间切换工作区，或为空间单独设置执行目录。
- 自动启动 Owner、离线消息补执行和消息排队。
- 渠道专用的消息表、任务对象或调度器。
- 旧数据目录的兼容和迁移。
- 自动 RAG、独立群聊知识治理、额外安全代理和逐条内容信任评分。
- 聊天确认码、用普通文本代替操作审批、依靠压缩摘要消除提示注入的承诺。

## 12. 决定记录

2026-10-27 至 2026-10-28 的讨论以以下最终决定为准；早先“默认 Ask、按对话权限、禁止成员不进入上下文”的表述已被替换：

1. 统一空间和对话模型，渠道私有数据与执行范围分别处理。
2. 操作权限只看当前空间和本次发起人，取较低一级，不按历史发言人的权限共同计算，也不增加对话权限层。
3. 新空间和未设置人员默认 None。None 可以参与聊天并进入群背景，但不能执行操作；它不是封禁状态。
4. 群普通消息只记录，明确唤醒才启动回答。历史、转发、引用和压缩摘要不能充当请求发起人或有效批准。
5. Ask 中需要审批的操作在 Telegram 点按钮；None 不能通过他人代批提权。GUI 卡片、CLI 提示与渠道按钮复用现有确认机制。
6. 使用平台真实稳定 ID，同一个 Telegram 账号在群和私聊中保持同一人员身份，不增加手工账号关联。
7. 接受共享群上下文仍可能影响有权限者发起任务的事实，不把身份检查或提示词宣称为完整的注入隔离，不默默削减 Full。
8. 外部渠道和本机并行运行属于效率问题。先保持单 Run 完成功能，跨对话并行按第 8 节后续优化。

为落实以上决定，首版将权限授予和配对管理集中在本机，外部 `/mode` 只读；空间整理按生效权限校验，审批、继续和放弃仍只认原发起人和本机。
