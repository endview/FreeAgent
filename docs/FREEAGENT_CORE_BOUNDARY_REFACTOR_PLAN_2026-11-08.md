# FreeAgent 轻内核整改实施计划

日期：2026-11-08。状态：**A/B/C 已实现并通过阶段回归；R 逐项结果见验收和随包交付记录**。核查基线为 FreeAgent `v8.5.1-dev.1`、AffectWeave `1.0.1-dev.1`、经验总结 Skill `0.1.0`，包括已有未提交改动。当前配套版本为 Core `v8.6.0-dev.1`、AffectWeave `1.1.0-dev.1`、Skill `0.1.1`；实际测试与部署以[验收记录](VALIDATION_V8_6_2026-11-08.md)为准。

执行顺序：**经验总结 → 扩展状态与存储 → 渠道依赖**。三个批次逐项实现和回归，再做配套归档；不把源码完成视为生产和真人验收完成。

约束见[扩展开发原则](EXTENSION_DEVELOPMENT_PRINCIPLES.md)。现行可调用接口见[扩展开发指南](EXTENSION_DEVELOPMENT_GUIDE.md)、[状态契约 v2](EXTENSION_STATE_CONTRACT_V2.md)和[协议](../extension-kit/SPEC.md)。后文保留实施要求与退出条件，是否满足以实际验收结果核对。

## 1. 这次解决什么

目标是让普通单 Core 保持好用，让可选业务真正可以增减；不借本次整改扩展产品功能。

| 批次 | 已核实的问题 | 完成后的归属 | Core 继续负责 |
| --- | --- | --- | --- |
| A：经验总结 | 固定 Skill 名称、总结提示、专用发布判断和轮次字段仍在 Core；未安装也显示按钮 | 可选 Skill 承载提炼方法，入口按能力出现；必要的草稿展示留在产品适配层 | 有界选源、可见范围、受限分析、脱敏、来源绑定、确认和通用发布 |
| B：扩展状态与存储 | 通用状态含 Persona/RoleID/MemoryID；权限靠动作后缀；PG 初始化、备份、恢复固定 `aw` | AffectWeave 解释人物状态；扩展声明自己的单一存储 schema | 身份、授权、精确预览、确认、幂等与结果核对、受限 PG 供应和配套备份 |
| C：渠道依赖 | `internal/harness` 引入 `internal/channels`，直接做 TG 格式、贴纸和反应处理 | 渠道进程拥有平台格式、资源和原生动作实现 | 输入采用与去重、执行、目标授权、冻结具体交付、有序派发、逐项回执和 UNKNOWN |

AffectWeave 的自然分段和人物表达继续由它自己提供；不安装时不显示人物回复设置。Telegram 的贴纸、反应和输入提示属于渠道，启用 Telegram 后可独立于 AffectWeave 使用。模型选择与思考开关/强度继续属于 Provider 与 Core 执行输入。

不做：新工作流引擎、任意插件 UI、模块生命周期平台、插件市场、通用对象数据库、多存储后端、共享知识治理、自动经验学习、人物算法升级或新的主动发送策略。Lark/QQ 保持已有能力和适配契约，不扩大真实平台验收范围。

## 2. 实施规则与阶段

1. 先记录当前工作区、已有改动和可用发行基线；不回滚、不用旧提交覆盖精简工作。按批次隔离自己的改动。
2. 复用 Conversation、Run、Attempt、消息、附件、控制确认、receipt 和 outbox。新增必要字段或有限状态可以接受，不预设独立 Task/Step/Checkpoint/Evidence 对象。
3. 模型提出的持久设置、人物定义、Skill/Memory 修改继续确认。普通文件和命令使用已有 Full/Workspace/Ask 规则，不扩大控制确认范围。
4. 工具、状态写入和实际发送结果不确定时，不自动重放副作用。模型请求仍可按已有 Core 策略有界恢复；不能把 UNKNOWN 一概解释为禁用所有恢复。
5. 每批先完成对应回归再进入下一批。失败先定位修复，不能通过删除测试、吞掉错误、强制取消用户任务或隐藏入口冒充完成。

| 阶段 | 产物 | 退出条件 |
| --- | --- | --- |
| P0 | 当前行为、依赖和成本基线；更新风险清单；脱敏夹具 | 明确真实数据路径、待处理记录及各包版本，能对照整改前后 |
| A | 可选分析 Skill 与通用选源/发布路径 | 无包不出现新动作；第二个非同名分析 Skill 不改 Core 即可调用 |
| B | 中性状态契约、声明式单 schema、配套 AffectWeave | 非人物扩展和现有人物扩展都通过权限、真实 PG、确认与恢复测试 |
| C | 平台实现移出 Core，既有渠道进程完成准备与传输 | 默认 Core 依赖检查通过，发送可靠性与 TG 既有能力无退化 |
| R | 文档、双平台最终归档、隔离验收与部署记录 | 发布条件有实际结果；生产更新与真人验收分别记录 |

P0 记录默认 Core 的依赖图、启动时间、空闲进程/连接、普通请求的额外模型调用及上下文字节；涉及前端时记录首屏资源，涉及进程时记录同机内存。沿用已有测量方法，不新增监控系统。尚无数据前不承诺体积或性能下降比例。

三个批次不得给未启用能力增加后台进程、业务连接或模型请求。协议封装的实际开销在对应场景测量；性能退化要说明原因，不能仅以“代码更通用”作为接受理由。

## 3. A 批：经验总结回归可选 Skill

### 3.1 选择的方案

采用 **可选 Skill + 通用有界来源分析 + 现有持久确认/发布 + 有限产品展示适配**。

只把按钮藏起来，不能解决 Core 专用流程。反过来，为一份方法提示新开常驻进程、数据库或工作流服务，也不合适。

Skill 中保留总结方法、成功与失败的解释、Skill/Memory/保留草稿的选择规则及输出示例。Core 只知道“使用用户选择的一份方法，分析一组有权读取的记录，生成结果”，不解释经验分类或自动决定哪些内容应该固定。

### 3.2 具体工作

| 步骤 | 改动 | 主要位置 |
| --- | --- | --- |
| A1 | 给现有 Skill 元数据补最小的“基于已选记录分析”声明；显示信息复用包元数据。登记可用动作时检查安装、启用、作用域和调用权限 | `internal/harness/skills.go`、能力发现、`optional-skills/experience-summary/` |
| A2 | 将来源预览、摘要绑定和 `analysisOnly` 路径通用化；移除按 `experience-summary` 固定名称分支和经验专用提示 | `internal/harness/experience_summary.go`、Run 快照与上下文装配 |
| A3 | GUI/CLI/AI/渠道调用同一通用动作；没有可用方法就不显示新总结动作；撤去公共 ChatTurn 的经验专用字段 | `internal/harness/chat.go`、`internal/chatui/experience.go`、`cmd/freeagent/experience.go`、`internal/harness/channel_experience.go`、会话前端 |
| A4 | 将秘密去除抽成通用函数，保留现有检测范围；Skill 发布、Memory 保存和投递共用。发布绑定具体草稿、来源和目标，不依赖经验专用 analysis kind | `internal/harness/skill_publish.go`、Memory 控制路径、`internal/harness/delivery_schedule.go` |
| A5 | 更新包说明与使用入口；以第二份合成分析 Skill 验证名称无关，删除不再使用的专用执行分支 | 经验总结说明、契约与入口回归 |

A1 只定义一种有界调用方式，字段和 schema 在该步定稿并同步文档；不加入步骤图、任意脚本、复杂动作注册语言或表单 DSL。CLI 的具体命令名随既有入口确定，不在本文虚构已经存在的命令。

可保留由 FreeAgent 自己维护的“经验草稿”展示适配，但只在相应能力可用或查看历史结果时加载。普通分析结果必须有通用查看、复制和显式保存路径，第二个 Skill 不必先开发一套 UI。

### 3.3 必须保留的限制

- 来源由用户显式选择；沿用当前 1–16 个 Run、每 Run 最多 256 条消息、来源总量 64 KiB 和可选消息范围。超限明确要求缩小范围，不静默截断后假装完整。
- 同时验证当前用户、会话、空间和记录可见性。渠道使用已授权的公开投影，不能读未发出的私人回答、私有思考或扩展私有表。
- 受限分析不混入普通完整历史、未选 Memory/Skill、人物上下文，不获得工具、协作或后台执行权限。来源文本按资料处理，不能升级成指令或授权。
- 在启动普通 Run 前冻结方法正文/版本、来源摘要、模型选择和相应执行参数；幂等键绑定这些内容。修改方法、选源或模型后不能复用旧请求冒充同一次分析。
- 结果先成为草稿。来源为失败、部分或 UNKNOWN 时保留其局限，不能把模型判断写成实际成功证据。
- 保存 Skill 或 Memory 继续绑定用户看到的精确内容、作用范围和原版本。模型提议走确认；修改后重新预览。保存 Skill 不默认启用或执行；“保存并固定”仍是明确选择。
- 停用/卸载方法不删除既有草稿、Skill、Memory 和来源。历史记录可读，不维持一条永久的旧经验 API 执行支路。

### 3.4 A 批验收

| 场景 | 预期 |
| --- | --- |
| 未安装、未启用、无范围权限 | 不出现新总结动作；直接构造调用也被拒绝；普通对话正常 |
| 安装并启用经验总结 | GUI/CLI/渠道可显式选源，经过同一 Core 校验，得到草稿 |
| 第二个非同名合成 Skill | 不修改 Core 的标识分支、全局对象或发布判断即可完成同类分析 |
| 跨空间、超量、含凭据、恶意来源、来源变化 | 范围/大小限制有效，敏感内容处理保持，旧摘要与旧确认失效 |
| 重复点击、断连、拒绝、保存冲突 | 不重复创建 Run 或持久产物；拒绝不写入，冲突重新预览 |
| 停用后查看旧结果 | 草稿和已确认产物仍能查看、复制、管理；不隐式重新运行总结 |

本批不要求新的真实模型付费验收。优先使用真实 Core + PG + 可控模型完成行为回归；若实际改变 Provider 请求协议，再补相关 Provider 测试并单独记录。

## 4. B 批：中性扩展状态与单 schema 存储

### 4.1 状态接口的最小边界

继续复用 `state.read/preview/apply/result`、原操作 ID、摘要、期望版本与 receipt。公共信封保留以下信息，人物业务字段移入 AffectWeave 的有界 payload：

| 信息 | 归属与校验 |
| --- | --- |
| 扩展 ID、契约修订、操作名 | 来自已加载的声明；未知操作、契约不匹配直接拒绝 |
| Core/空间/会话/Run/已采用输入身份 | Core 根据真实调用绑定；模型或扩展不能自报管理员和替换发起人 |
| 操作作用域 | 每个操作显式声明有限的全局/空间/本人范围及是否允许模型提出；Core 结合已有权限裁决 |
| 资源引用和业务 payload | 长度、数量、结构有界；资源引用不承载宿主路径或任意 SQL；人物等内容由所属扩展验证 |
| expected revision、operation ID、digest | 复用既有并发与幂等约束，绑定完整信封、声明版本和具体内容 |
| before/after、说明、结果 receipt | 有界且可供用户检查；摘要绑定精确预览；实际提交结果由原操作核对 |

删除 `HasSuffix(action, "role")` 这样的权限推断，删除通用层对 `role_id` 的默认读取。Core 的 variant 只是本轮冻结的不透明选择，AffectWeave 自己解释默认人物与人物 ID。

外部模型提案继续不能修改全局定义或他人范围，不因泛化而放宽现行约束；Owner 的显式管理仍走已有控制身份与确认。这里不重新设计渠道准入或管理员政策。范围校验不能只相信扩展返回“允许”。

状态请求必须绑定发起该操作的原 Run 和当时已采用的输入；禁止查询“该会话最近一个 running Run”来猜身份。多用户插话时，当前调用的有效发起人要能从采用记录确定，不能混用排队但未采用的输入。确认时再次检查当前权限和版本，不因 Run 已结束而借用新 Run 身份。

操作声明只是有限白名单和结构约束，不发展成资源类型平台、策略脚本或任意 CRUD。已安装的原生扩展仍是受信程序：协议与 PG 角色限制不能宣称可以隔离同一 OS 用户下的恶意宿主代码。

### 4.2 存储选择：声明单 schema，保留现有 aw 数据

选择**每个有存储需求的扩展声明一个受限 schema，继续使用现有独立扩展数据库和受限角色**。AffectWeave 显式声明 `aw`，不为去掉 Core 的硬编码搬动人物数据。

| 事项 | 实施规则 |
| --- | --- |
| 声明 | 复用现有 manifest/storage 信息，增加一个单 schema 声明；采用 PostgreSQL 普通标识符的严格白名单和长度限制，禁止 `fa`、`public`、系统 schema 及保留前缀 |
| 绑定 | 初始化时记录扩展 ID、Core 身份、数据库、角色、schema 和存储格式；声明与已绑定信息不符时停止，不自动改名/切库 |
| 权限 | 继续一个扩展独立数据库/角色，不给 Core 库或其他扩展库权限；schema 不是模型可编辑设置，不接收模型提供的 SQL、库名或连接串 |
| 默认行为 | 未安装/停用不自动建库；显式初始化、检查、备份属于有界管理操作，不代表后台启用业务 |
| 备份 | `pg_dump` 等参数从校验后的绑定生成，移除 `--schema=aw` 固定值；备份记录来源、schema、配套包和契约版本 |
| 恢复 | 移除 Core 中 `aw` 表名枚举和专用清表逻辑；仅在确认的新恢复目标，用受限角色和配套归档恢复声明范围，验证来源与对象范围，不执行任意上传的 SQL |
| 数据格式 | 业务表、字段和业务版本由扩展维护；Core 不引入多后端接口、跨库事务、迁移脚本平台或另一套备份服务 |

现有绑定若缺 schema 信息，在**显式更新预检**中核对已安装包声明、真实唯一业务 schema、数据库角色与 Core 身份后，一次性补全绑定。发现多个候选、属主不符或内容冲突则报告具体问题。不能在普通聊天中猜测 `aw` 并自动补写，也不维持永久兼容分支。

配套备份沿用当前有限暂停扩展写回、记录游标和核对原结果的方式，普通 Core 任务派发继续。数据库快照、扩展写回边界和附件引用分别记录；不为了备份暂停所有任务。正式换包时的短暂维护窗口与日常在线备份分开。

### 4.3 配套实现与版本处理

| 步骤 | 改动 |
| --- | --- |
| B1 | 在 Extension Kit 定稿最小状态操作声明、信封与契约样例；给破坏性变化明确修订号，握手拒绝不匹配 |
| B2 | 改 `extension_state.go`、`extension_identity.go`，同步 AffectWeave 的状态适配；保留人物/情绪/关系算法和实际数据 |
| B3 | 改 `internal/postgres/extension.go`、`extension_backup.go`、`extension_restore.go`，显式 schema 绑定贯穿初始化、备份和恢复 |
| B4 | GUI/CLI/AI 继续使用同一预览/确认；人物详情页在产品层翻译 payload，Core 不读人物字段；事实补读复用原 Run/receipt |
| B5 | 完成协议不匹配、升级预检、真实 PG、原结果核对与配套恢复测试，删除旧状态执行处理器 |

优先在既有 `freeagent-ext` 承载内对状态能力做显式修订，不无理由升级所有无状态工具契约；若现有握手无法表达安全区分，再做必要主协议升级并说明影响。运行时只保留一个当前状态处理器，不维护新旧双写/双读执行路径。

更新前列出旧待确认、已派发及 UNKNOWN 的状态写入。未派发的旧提案在新版本中重新预览，不翻译后直接 apply；已派发的必须用原操作核对。若旧结果核对依赖旧包，在更新前用原配套包完成，不能靠新处理器猜测成功。历史预览和 receipt 保留原始事实。

### 4.4 B 批验收

- 用真实 AffectWeave 和一份只管理“项目标签”的非人物合成扩展，跑通 read → preview → 确认/拒绝 → apply → result。非人物扩展不得要求新增 Core 业务字段。
- 两份扩展使用各自独立数据库、不同声明 schema 和受限角色，实际验证无法跨扩展或读取 Core 数据；非法 schema、角色冲突、绑定与声明不一致均拒绝。
- 覆盖跨空间/他人/全局越权、伪造 Run、排队输入冒充已采用输入、旧 invocation、多用户插话及确认时权限撤销。
- 覆盖预览后数据变化、重复 operation、同 ID 异内容、提交后丢回执、超时/进程退出、只查原结果和保留 UNKNOWN；不得重新执行模型或业务写入补证据。
- 实际备份/恢复人物、关系、记忆、原操作结果和同步位置；覆盖损坏归档、错误来源、错误 schema、配套包不匹配及恢复失败。用合成数据验收，不把生产人物资料写进仓库。
- 未安装/停用扩展时，不自动初始化扩展库、启动人物进程或执行状态读取；普通 Core 的 PG、模型和工具能力正常。

## 5. C 批：移除 Core 的平台实现依赖

### 5.1 依赖边界

默认 `cmd/freeagent` / `internal/harness` 可以依赖中性的 `channelwire` 数据契约；不再依赖 `internal/channels`、`internal/channelplugin` 或平台客户端/渲染实现。渠道程序可以依赖平台包。把实现搬进另一个仍被 Core 导入的目录不算完成。

Core 可以保存 `telegram` 这样的来源标识、准入记录和审计命名空间，不以“源码中不存在 Telegram 字符串”为验收目标。平台格式算法、原生动作枚举、贴纸包规则和平台客户端才是本批移出对象。

| 内容 | 去向与约束 |
| --- | --- |
| TG Markdown/实体/UTF-16 分片、纯文本降级规则 | 渠道侧 formatter；使用合成语料做格式回归 |
| TG 贴纸包名、贴纸类型、反应枚举、原生请求参数 | 渠道侧校验和转换；Core 仍核对动作授权、目标和已授权资源引用 |
| 可用渠道动作 | 经当前受限连接声明已实现的有限动作、参数边界和是否有副作用；复用已有工具/权限执行，不提供任意 RPC、Shell 或 URL 调用入口 |
| 图片来源 | Core 按已授权附件/工具结果处理通用图片；平台动画预览和帧说明由渠道提供，移除 Provider 通用图片路径中的贴纸业务假设 |
| 输入与行为 | Core 继续处理同一会话、上下文、压缩、停止、队列/引导、审批和模型恢复；渠道不另建 Agent、任务执行队列或 Memory |
| 设置与历史 | 完整渠道/投递配置按已安装、已配置或实际可用能力呈现；无能力时仅保留简短发现入口；历史授权、待投递和 receipt 始终可查看、撤销或清理 |

本批只补现有渠道动作需要的有限声明，沿用 `channelwire` 和现有拉取/回执连接；不做通用插件注册中心或新消息总线。

### 5.2 具体交付：准备完成后冻结，再派发

移出 formatter 时，不能把未冻结的原回答交给发送端任意切片后直接发送。采用以下顺序：

1. **Core 记录待准备内容。** 绑定原 Run/候选、原文摘要、目标、逻辑部分和授权，复用现有 outbox/meta；只增加必要的准备字段/状态，不新建 RenderJob 系统。
2. **渠道完成纯准备。** 用当前连接拉取准备请求，生成有界平台分片、格式版本和原生格式数据。此阶段不发消息、不调用模型/工具、不触发任何平台写操作。需要资源信息时使用已授权缓存/独立只读解析结果，不能把查资源和发送混成一次模糊操作。
3. **Core 校验并原子冻结整组。** 核对 Bot/平台/连接代次、源摘要、目标、部分顺序、大小/数量、资源授权和完整组；保存具体内容、版本与摘要。格式语义由适配器保证并测试，Core 不再实现一套 TG 解析器，也不声称摘要能证明适配器忠实转换了原文。
4. **逐项派发并保存真实回执。** 发出前再次检查授权、取消、期限、静默/额度和顺序；渠道仅发送已冻结部分，不能再自行分段或添加内容。每片分别记录派发意图、平台消息 ID、失败/UNKNOWN。
5. **分别处理准备重做与发送恢复。** 未冻结的纯准备可用相同输入和版本重新计算；冻结后不得因升级、重连重新渲染。已派发但未获确定结果的发送保留 UNKNOWN，禁止当作“未发送”自动重发。
6. **区分生成与交付。** 渠道离线时可以显示“回答已完成，交付待处理”，不能报告已送达。取消或撤权后返回的准备结果不能重新激活投递；旧连接代次不能覆盖当前记录。

需要逐次确认的发送，预览绑定准备后的具体内容、目标和整组摘要；内容变化重新确认，不能先批准原文，再替换正文沿用旧批准。已获持续授权的发送仍按原授权规则逐项检查，不能借本次整改把它们全部改成逐次确认。

已明确证实未发送的格式拒绝，才可按既有规则准备并保存替代格式、重新授权检查后发送。网络超时、取消、429 和确定拒绝分别按平台证据处理，不能统一走降级重发；无法证明未发送就保留 UNKNOWN。已经送达的部分不因后续部分失败而重放。

`typing` 继续是短时活动提示，不形成一条持久消息；停止/任务结束后自然到期或停止刷新。输入提示与反应不能充当正文已送达的证据。

### 5.4 C 批验收

默认依赖检查至少使用：

```text
go list -deps ./cmd/freeagent
go list -deps ./internal/harness
```

结果不得包含平台客户端/渲染实现；同时人工核对是否把平台逻辑藏进中性包。测试夹具的依赖与默认运行依赖分别记录；`goldmark` 等库若由其他必要功能使用，按实际依赖链判断，不能仅凭名字一刀切。

运行验收覆盖：

- 无渠道配置时不创建平台连接、轮询或适配器进程；普通对话/文件/命令/Provider 与 GUI/CLI 接续可用。
- 真实渠道进程与 Core 通过受限连接完成入站、准备、冻结、发送和回执；平台 API 可使用本地受控服务，不仅直接调用函数测试。
- Core 已持久接收但 ACK 丢失、平台重复 update、插件重启恢复游标，不重复采用输入或创建 Run。TG 插话目标已结束仍保留 `target_ended`，不擅自转换为新排队任务。
- 在准备前、准备后、冻结事务中、派发前、第一片成功后和回执前分别中断；验证整组原子性、顺序、逐项状态、迟到回执和 UNKNOWN 不重放。
- 准备期间取消/撤权、旧代次准备或回执、变更 source digest、伪造其他 Bot/平台/目标、越权附件和资源均被正确处理。
- 长中文、代码、表格、未闭合 Markdown、链接、emoji/组合字符与平台长度边界；实体不越界，明确失败时的纯文本降级不重复投递。
- 无 AffectWeave 的 TG 可用贴纸/反应/输入提示；有 AffectWeave 的自然分段保持具体内容和回执；动画预览不声称模型看到了完整动画。
- 清晰记录模拟通过、真实平台请求通过和用户客户端观察。历史一次授权的发送测试不扩展成无限次任意发送。

## 6. 数据连续性与更新边界

不建设旧平台兼容层，也不以此为理由删除本次更新前的用户资料。保留当前数据与事实记录，是正常版本更新责任。

| 数据/操作 | 更新处理 |
| --- | --- |
| 原对话、Run、Attempt、附件、确认与 receipt | 保留原记录和关联，不重写历史输出或补造成功 |
| 经验草稿、Skill、Memory | 方法停用仍可读和管理；旧业务标记作为历史事实，不用于触发旧执行流程 |
| AffectWeave 人物、关系、记忆 | 原数据库与 `aw` schema 保留；变动以通用信封和绑定信息为主，不顺带改人物参数 |
| 未派发的旧提案 | 按新契约重新预览/确认；原提案标记失效，不静默翻译执行 |
| 已派发/UNKNOWN 的状态或工具操作 | 用原 ID 和原配套版本核对；无法安全解释时形成明确更新阻塞，不自动 cancel、apply 或重放 |
| 已冻结交付 | 原内容、目标、顺序、格式、派发意图和 receipt 保留；不得用新 formatter 重新生成 |
| 尚未完成的交付 | 优先在原配套版本完成或核对；若新版本无法安全接续，保持原服务并报告具体阻塞，不跨协议猜测 |
| 凭据、授权、服务设置 | 保留当前值，不在更新中改默认模型、Owner、Bot、密码、人物选择或用户权限 |

回退使用更新前的配套程序与一致备份；先保全更新后新增数据，不能把新写入目录直接交给旧程序读取，或用旧备份覆盖新对话后宣称无损回退。若缺少安全接续或恢复证据，该批不能上线。

Windows 验收包括真实 WebView2 的入口显隐与确认流程；Debian 12 使用 Hytron 的独立验证环境。依赖、编译器或设备不可用则记录 NOT_RUN，不能把未运行改成通过；涉及关键权限、数据恢复或重复副作用的缺口会阻止相应发布。

每批记录“已完成、未完成、UNKNOWN、NOT_RUN、阻塞”，并写清下一步所需条件。源码实现完成、隔离验收完成、生产更新成功、真人验收通过是四件不同的事。UNKNOWN 是执行结果状态，NOT_RUN 是测试未运行，二者不能互换。

## 8. 最终交付与 Hytron 更新

本节是后续执行步骤，**写入计划不等于已经部署**。实际部署按当时有效授权和本机协作约定执行。

1. 生成 Core、AffectWeave、经验 Skill、渠道程序的配套版本清单、更新说明和 Windows/Linux 可下载归档；不要求用户复制哈希，内部完整性校验继续保留。
2. 在 Hytron 的独立 unit、端口、数据目录验证最终 Linux 归档；不用生产 Bot 凭据启动第二个消费者，不改动其他 VPS 服务。
3. 从当前 unit 和私有运维记录核对真实数据路径、活跃 Run、待确认、UNKNOWN、后台命令和 outbox。不能把旧文档中的路径当成当前事实。
4. 做 Core 与扩展配套备份，核对凭据引用、空间/Owner/Bot 授权、数据计数、原操作和同步位置。备份和诊断不把秘密或人物资料写入公开产物。
5. 满足空闲与可接续条件后，配套切换 Core、AffectWeave 和渠道；沿用不强制取消活动任务的维护方式。遇到未解决的不确定写入或不能接续的交付，保持当前服务并报告，不擅自清状态。
6. 更新后检查 doctor、PG、扩展状态、渠道连接、HTTPS 与前端资源；不顺带修改 NPM、公网认证或模型/人物设置。
7. 真实 TG 发送按明确授权的目标和内容验收；没有当前可用授权或用户观察条件，标明待验收，不虚构用户看到的效果。
8. 将实际部署、回退点与后续操作同步到私有 VPS 文档及项目忽略的运维记录；公开文档只写脱敏结果。
