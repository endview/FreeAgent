# FreeAgent 后续开发：可选渠道、统一设置、执行恢复与 PostgreSQL

日期：2026-11-05（Asia/Shanghai）。状态：计划，尚未开始本文件中的架构改造。
本版已合并两轮 review 的结论（2026-11-05）。
2026-11-06 补充：确认从 v8.0 起统一使用 PostgreSQL，补入性能实测依据及数据设计指南。
输入交互补丁 v7.13.0-dev.2 独立交付，不作为本计划已完成的证明。

**当前最高优先级是好用的单 Core。** 先解决日常交互、可靠执行、上下文与本地数据体验。
未来多 Core 协作、全局拓扑和分布式知识库只保留必要边界，不提前实现、不阻塞单 Core 交付。
每阶段先验收：首次启动和设置可用、任务可完成或清楚地恢复、GUI/CLI/Web 接续一致、
上下文与 Memory 可控、大历史下交互流畅。PG 的初始化、启停和常见排障由产品承担；
普通单 Core 用户无需手动建库、分配数据库角色或理解集群概念。

## 1. 用户确认的产品边界

1. TG、QQ、Lark 从默认 core 和默认配置中移除，渠道插件随发行包提供、按需启用。
2. 模型 Provider/Key 与渠道凭据分别管理。模型协议列表不再出现 Bot 或应用 Secret。
3. 全局能力集中到统一设置，提供二级菜单；现有 Key 管理和能力管理归入其中。
4. 本轮/本对话能力留在输入框。GUI/CLI 运行中先排队，可手动引导；TG 直接插话。
5. 模型请求结果未知时允许自动重试；失败和 UNKNOWN 的原始记录保留，不能伪造成功。
6. 从 v8.0 起，PostgreSQL 是唯一受支持的运行时数据库，目标是统一存储技术与维护方式，
   为以后的 Core 自有知识、共享知识库、多 core 协作和 Agent 集群准备并发与运维能力。
   便携版随包携带 PG，由启动器管理本机实例；服务器和多 core 场景可连接外部 PG，
   使用同一套查询代码。默认 Core 依赖 PG，可选的是重知识库/协作扩展，不是另一种
   默认数据库；不长期维护 SQLite/PG 双后端、自动回退或双写同步。
7. 可选扩展统一命名为**经验总结**，位于“能力管理 → 扩展”，做成可选 Skill 加一个
   “总结经验”按钮。复杂且可重复的固定流程整理成 Skill；简单、稳定的经验经用户确认
   保存为可固定的 Memory。提炼逻辑不放进 core，不增加核心经验学习、资产治理、
   自动知识整理或后台扫描。
8. **core 统一处理，渠道进程只传递**。上下文、能力选择、准入/权限、运行状态与恢复
   都在 core；渠道完成平台连接、事件验签、来源身份和输入输出传输。

保持一套可组合 Harness。复用现有 Conversation/Run/Attempt/消息与 receipt，
不新增任务平台、插件市场、组织权限、多租户控制台或独立 Evidence/Checkpoint 系统。

### 1.1 后续各版本统一遵守的职责划分

**Core 负责处理，渠道层负责传递，经验总结由可选扩展完成。**

| 部分 | 负责的工作 |
| --- | --- |
| Core | 会话和空间、上下文装配/压缩、已授权 Memory/Skill/固定内容加载、Provider 与工具调用、权限、审批、输入采用、执行恢复和事实记录 |
| 渠道层 | Telegram/QQ/Lark 的连接与平台事件验签，传入正文/真实身份/附件/用户操作，回传 Core 的回复/文件/状态及投递回执 |
| 经验总结扩展 | 根据用户选择的执行记录提炼经验；复杂固定流程生成 Skill，简单经验生成可固定的短文本；确认后的产物交给 Core 的通用能力使用 |

消息处理链路固定为：**用户入口 → 渠道传递 → Core 处理 → 渠道回传 → 用户**。
GUI/CLI 直接使用同一 Core 接口。渠道层不维护独立的上下文、Memory、执行任务或审批状态。
相同会话、身份授权和能力选择必须得到一致的上下文与执行规则；GUI/CLI 排队、TG 直接
插话的默认差异由 Core 的入口配置处理，不复制一套执行逻辑。

这条原则贯穿第 3 节的版本安排、第 4 节渠道拆分、第 5 节统一设置、第 6 节执行恢复、
第 7 节 PostgreSQL 和第 8 节经验总结。每阶段验收都要确认业务处理仍由 Core 统一承担，
渠道侧仅保留传输状态；不能因拆分插件而出现第二套 Harness 或按平台名称截断已授权上下文。

## 2. 代码与生产核查结论

- `cmd/freeagent/owner.go` 在每个 Owner 创建 TG/Lark/QQ 运行时；关闭后不建立连接，
  但平台代码仍编入二进制。Harness、配置、UI 与平台实现存在直接依赖。
- `internal/chatui/src/main.mjs` 的 `key-protocol` 同时包含模型协议和 TG/Lark/QQ。
  当前设置入口集中呈现权限、工具、网络、渠道、压缩等内容，缺少清楚的二级导航。
- `internal/harness/channel_runtime.go` 在回复正文为空时，把任意 Run 状态与“UNKNOWN
  不会自动重试”拼在一起。生产最近一条 failed 记录实际属于输出限制，不能据此判为 UNKNOWN。
- `internal/harness/model.go` 的 `CallError.Certain/Category/Retryable` 已有分类基础；
  `Retryable` 目前只是建议，不授权自动重放。运行时已有 Attempt 与 UNKNOWN 事实记录。
- Store 目前依赖 SQLite，包括 JSON 路径查询/更新、`?` 参数、行号顺序、LastInsertId、
  部分唯一索引、PRAGMA、文件 Owner 锁、WAL 快照及 `VACUUM INTO` 备份。不能只换 DSN。
- 当前 `externalContext/publicContext` 会让外部渠道跳过本机 Memory/Skill/扩展，并
  替换配置指令。这是现有实现限制；渠道拆分时改为 core 的统一授权与上下文选择，
  不把这种按入口名称分支的限制保留为目标架构。

这些是核实的实现边界。渠道拆分后的体积/RSS/启动耗时仍未测量。

Hytron 的隔离测试已完成 348 轮正式测量：初始 10 万 Run、40 万消息、30 万 Attempt 下，
当前 Core 单并发零模型等待任务约 9.18 秒，测试副本补齐四个查询索引后约 49.73ms。
等价存储原型在 16 路压力下，补索引的 SQLite 单连接约 148 流程/秒，PG 16 连接约 265，
PG 单连接控制约 108；这不是完整 PG 产品适配的验收，也不是所有工作负载的性能上限。
因此近期索引修复与 v8.0 统一 PG 分别推进；选择 PG 的依据是长期架构和维护一致性，
不能以“SQLite 已达到引擎容量上限”解释这次实测。测试方法与边界见数据指南第 1 节。

| 独立扩展迭代 | 经验总结：可选 Skill 加按钮；复杂固定流程 → Skill，简单经验 → 可固定 Memory | 不依赖 core 内置提炼；选择来源、审核内容和范围后发布，可撤销，无隐式学习 |

执行恢复先做：TG 失败是日常最常见的问题；恢复逻辑在 core 运行循环内，不依赖渠道拆分，
它的故障注入测试也能为后续改造兜底。PostgreSQL 放最后：新功能基本复用现有记录，以减少
最后存储替换的重复改造。版本号是本计划建议，尚未发布；存储替换不塞进普通维护补丁。
每阶段完成实际测试和交付后，再继续下一阶段。现有线上 Bot 在正常测试期间保持运行。

## 4. 可选渠道进程与凭据分离

详细拆分边界见[渠道插件草案](CHANNEL_ADAPTER_EXTRACTION_PLAN.md)。

- 默认 core 包没有平台协议实现、Bot 凭据、轮询/长连接和专用配置。默认设置也不展示
  未启用渠道的空表单；在“扩展”中启用随发行包提供的渠道后，才出现对应入口。
- 默认一 Bot 对应一个 core。首版一个渠道进程只服务一个 core，只接收该 core 的凭据
  和授权；同一进程可以运行归属于该 core 的多个 Bot。不同 core 使用各自的渠道进程，
  不共享进程生命周期。用户显式配置后，一个 core 可以同时接多个 Bot 和平台，不自动
  把新增 Bot 归入已有 core。
  同一个 Bot 只能由一个进程拉取更新（Telegram 遇到并发 getUpdates 会返回 409），
  不在每个执行核心重复维护连接、webhook、平台缓存和重试循环。
- core 保留标准化入口、空间/会话、身份映射、准入/权限与审批裁决，并统一装配指令、
  Memory/Skill/固定内容、压缩历史和执行模型/工具。渠道只传递平台事件与返回结果。
  插件持有的能力令牌只允许所绑定来源与操作，不使用 GUI 管理员令牌，不直接打开核心数据库。
- 渠道不解释业务命令、不持有第二份 Run/排队状态、不生成摘要或改变模型输入。停止、
  引导、审批按钮、设置请求都转给 core；core 按来源绑定决定默认交互行为。
- 入站去重键至少包含平台、Bot/应用、聊天范围和消息/事件 ID，不能只用裸消息 ID；
  插件收到 Core 的持久接收回执后，才推进拉取游标。接收回执须意味着完整输入、附件
  持久引用、来源/目标与采用状态已保存，Core 崩溃后能继续处理；不能仅保存消息正文。
  复用现有消息、输入与 Run 关联，在同一事务中提交输入采用及创建/关联 Run。重投返回
  原关联；重启只恢复仍符合原意图及当前授权的未采用输入，已关联 Run 不另建或重放。
  插话目标已经结束时保留 `target_ended` 并提示，不转成新任务；故障恢复不改变 TG
  默认插话、不排队的产品行为。明确拒绝的输入保存处理结果，不能被恢复成待执行项。
- 出站由 Core 记录待投递回复，插件
  拿到平台返回的消息 ID 后回执；如果插件已发出消息、尚未回执就崩溃，可能重复发送一条回复，
  这可以接受。审批按钮按审批 ID 处理，重复点击或重复卡片都不能批准两次；重投回复
  不重新执行模型或工具，也不改变已有审批的参数、版本与有效性检查。
- 插件负责确认平台身份的真实性。Core 能阻止跨 Bot/平台冒充，但无法识别被攻陷的插件
  伪造的本账号用户身份；插件令牌按秘密保存。
- 能做什么看身份，能看到什么看空间。明确绑定为本机 Owner 的私聊，使用该 Owner 已有
  的授权和能力选择；有权访问不代表把全部 Memory 自动加入上下文。群聊和其他人的空间
  只用本空间内容，全局或工作区内容需要显式授予给具体空间。Owner 在群里发言也遵守
  群空间范围，不带入私人摘要、Skill 附件或历史内容。内容可见性由 core 校验，不向渠道
  暴露内部完整上下文。
- 模型凭据属于 Provider 管理；平台账号和 Secret 属于渠道，由 Core 分区保存，启动插件时
  按需交付。可复用底层保密存储原语，但类型、枚举、列表 API、表单、校验与导出都要
  隔离命名空间，不能只改菜单名称。
- Provider 列表只显示模型提供方与其请求协议；OpenAI 兼容、Responses、Anthropic 等
  按实际适配器能力呈现。Telegram/Lark/QQ 永远不出现在模型协议下拉列表。
- 可选包随发行包提供。服务器上的渠道程序作为独立 systemd 服务运行；桌面版由启动器启动、
  做就绪检查并有序停止，生命周期跟随 Owner。设置页只负责启用和显示状态，不做下载和
  升级管理。启动器只管理随包 PG 和已启用的渠道进程，不做通用进程编排；不使用 Go 动态
  ABI 插件，不建设在线插件市场，也不维护另一份 Harness。
  v7.15 先落实下述 §4.1 的客户端/Owner 退出规则；v8.0 只把自管 PG 加入相同停止顺序。
- 未来知识库插件与 agent 接口只保留版本号、能力授权、禁止直接读写其他 core 数据库
  的原则。当前只实现渠道所需的窄接口，未来按实际需求决定哪些部分可复用；不预先
  承诺知识库、其他 agent 与渠道使用完全相同的入站接口，也不提前实现跨 core 调度。

首版支持范围：

| 场景 | 首版 |
| --- | --- |
| 一 Bot 对应一个 core | 默认方式 |
| 一个 core 同时接多个 TG Bot、Lark、QQ | 支持，须由用户显式配置 |
| 在 GUI/Web 里接着聊 TG 的对话，回复同步回 TG | 支持，保持现有做法 |
| 一个 Bot 把消息分给多个 core | 不支持 |
| 一个渠道进程同时服务多个 core | 不支持；不同 core 各自运行渠道进程 |
| 同一个对话同时绑定两个外部聊天，如 TG 和 Lark | 暂不支持：需要先关联两边身份并双向投递 |

对话归属于创建它的渠道空间；不管输入来自 GUI、Web 还是 TG，回复都推回该空间。
GUI/Web 接续渠道对话时沿用该空间的内容可见范围，不因切换入口扩大该空间的授权范围。

验收包括默认 core 的 `go list -deps` 无平台实现、空闲时无平台连接、同一 Bot 不被两个
进程同时拉取、插件/Owner 分别重启不重复执行入站消息、跨 Bot/平台身份伪造与跨空间访问
被拒绝、附件与回传可追溯。覆盖去重键与接收回执、出站重复与审批幂等、群空间不带入私人内容。
入站故障注入覆盖接收提交前后、回执丢失、输入已接收但未采用、Run 已关联但未回执；
不能丢弃已确认接收的待处理输入，也不能重复创建 Run。另测目标已结束、权限撤销和
明确拒绝后的恢复，以及跨 core 渠道进程绑定被拒绝、停止一个 core 不影响其他 core。
增加同一授权会话跨 GUI/CLI/TG 的固定内容、Memory、Skill、压缩和审批一致性测试；
渠道传递期间不调用模型、不访问核心数据库、不自行重启或重试执行任务。
TG 做真实私聊联调。Lark/QQ 保留已实现能力和模拟回归，其真实平台验收由用户后续安排。

### 4.1 桌面客户端与 Owner 的退出规则

关闭客户端与停止 Owner 是不同操作。桌面 Owner 的存活条件包括已连接的 GUI、attach
CLI 和已认证 Web 客户端，以及运行中的 Run、等待确认和仍存活的后台命令。复用现有
连接/存活检测与任务记录，不新建会话管理服务；服务器 Owner 由 systemd 管理，客户端
全部断开也不自动退出。桌面具体行为如下：

| 操作/情况 | Owner、任务及依赖进程 |
| --- | --- |
| 关闭一个 GUI/CLI/Web 客户端，其他客户端仍在线 | 只断开当前客户端；Owner、渠道及自管 PG 继续运行 |
| 最后一个客户端离开，但有运行任务、待确认或后台命令 | 默认保留 Owner；可交互关闭时提示“仅断开”“停止并退出”及受影响内容，意外断连不等于授权停止；重新 attach 可接续或处理审批 |
| 所有客户端离开且无上述工作 | 有序退出；主动关闭时若渠道在线，先提示渠道将下线。渠道连接本身不无限延长桌面生命周期，常驻 Bot 使用服务器部署 |
| 用户明确选择“停止并退出” | 按现有管理授权停止该 Owner，影响其所有客户端；先拒绝新输入/派发并暂停队列，停止运行任务和后台命令，保存真实结果，待确认保持未批准，重开时重新校验；随后停渠道、Owner，最后停自管 PG |
| 强制退出、关闭超时或 Owner 崩溃 | 尽力停止本实例进程；未能确认结束或效果的调用保留 UNKNOWN，不宣称撤销成功；启动时核对残留及恢复事实，不自动重放 |

自动退出前须在同一 Owner 的关闭判断中重查客户端与工作状态，并停止接收新工作，避免
“刚判空闲就收到消息”的竞态；未持久接收的输入不能回成功回执。外部 PG 不参与停止。
验收覆盖 Web 单独在线、待确认但无模型调用、后台命令在 Run 结束后仍存活、意外断连、
最后连接退出与新入站并发，以及自管/外部 PG 的停止边界；v7.15 先测现有依赖，v8.0 补 PG。

和未保存草稿状态明确；切应用、切子页、刷新数据不清空正在填写的 Provider/Key。

### 全局与当前会话的边界

- 全局：安装/启用 Provider、工具、Skills/扩展、默认权限、文件/网络策略、压缩策略、
  数据库、渠道账号和公网安全，全部进入统一设置。持久化修改由 AI 提案时继续确认。
- 当前会话：选模型、在全局已允许的范围内选本对话能力、附件、当次权限选择、待发消息
  与引导、查看/排除固定经验，留在输入框。全局未安装/禁用的能力不能被会话选择重新启用。
- 当前 Run：仍冻结有效配置与权限；设置页明确说明新值对哪一轮生效。手动压缩可保留
  对话上下文入口，不能因集中全局设置而移走必要的就地操作。
- GUI、CLI 和 AI 对话使用同一控制契约，不能形成只在网页生效的设置或绕过确认的聊天接口。

验收：键盘/窄屏/深色模式可用；未保存 Key 不因失焦或导航丢失；连接测试不重置表单；
默认模型/模型列表操作持久有效；禁用全局能力后新 Run 与当前会话选择一致受限。

## 6. 可靠执行：先分类，再自动恢复

### 6.1 正确显示事实

失败、用户停止、输出截断、等待确认、上下文不足和 UNKNOWN 分开显示。TG 要给当前
问题的简短原因和可执行操作；有已确认的部分结果就保留并投递，不用万能 UNKNOWN
说明替代每个错误。原始诊断保存在记录中，按权限查询，提示不携带 Key 或服务器路径秘密。

“输出限制”先查清来源：可能是模型输出 token、本地响应大小、渠道投递或其他预算；
不能把所有限制一起删除。

### 6.2 自动重试策略

普通任务仍没有总步数/总执行秒数限制；重试属于一次调用失败后的恢复规则，必须有界。
建议默认最多自动重试 2 次，退避约 1s/3s 并加小量抖动；Provider 给 Retry-After 时遵守，
等待过长时显示等待并允许取消。默认值通过统一设置与现有控制协议调整，不另建调度系统。

| 已记录事实 | 处理 |
| --- | --- |
| 认证/权限拒绝、无效模型或参数 | 不用相同参数自动重试；显示具体配置问题 |
| 额度不足：DeepSeek 余额不足返回 402；OpenAI 返回 429 且错误类型为 insufficient_quota，与普通限流状态码相同 | 不重试；按错误体类型区分，提示充值或更换 Key |
| 可恢复的 429（普通限流）/5xx、连接建立失败 | 在调用级次数内重试；记录每次真实派发及结果 |
| 纯模型请求已发出但响应未知/流中断 | 允许新 Attempt 重试，原 Attempt 保留 UNKNOWN；重试成功不把旧调用伪造为未发生 |
| 明确输出限制/length | 保留片段；在已有授权输出边界内尝试简短回答或合法续接，最多同一恢复预算；不执行未完成响应中的工具 |
| 明确上下文拒绝且未生成结果 | 沿用已有有记录的压缩后一次重试，并纳入统一恢复预算，防止两层各自无限重试 |
| 只读工具失败 | 仅当目标/输入与权限仍有效、工具声明允许时重试 |
| 已派发的写文件/命令/外部动作结果未知 | 进入只读核查，见 6.3。 |
| 用户停止、取消、Owner 正在关闭 | 立即停止重试和等待，不因自动恢复又开一轮 |

用户要求 UNKNOWN 自动恢复，首先落在**结果尚未交付给任何本地工具的模型请求**上。
这样可能增加 Provider 计费，设置和日志明确可见。若 Provider 请求自身携带可能产生
不可逆外部作用的托管工具，则不能按纯模型请求重试，必须有该 Provider 的幂等/结果核对能力。
不能把“保留了失败日志”当作任意 Shell 命令或远端发送可安全执行两次的证明。
第 4 节允许的是同一渠道回复的重复投递，不是重新派发产生业务副作用的工具。

### 6.3 工具结果未知后的只读核查

- 当前 Run 不直接结束。把 UNKNOWN 和已知事实交给模型；Harness 暂时只开放可靠的只读
  查询，关闭命令、写入和其他可能产生副作用的入口。只靠一句“不要重复执行”的提示，
  不足以避免重跑。
- MCP 默认按有副作用处理。复用现有 `trustReadOnlyHint`：缺省与导入默认均为 false，
  用户明确启用该服务的只读信任，且具体工具声明 `readOnlyHint=true`，才可用于核查。
  当前 `MCPServerConfig.UnmarshalJSON` 的缺省 true 必须同步修正；CLI、GUI、AI 配置
  共用同一规则，不能把解析时的默认值或服务端自行声明视作用户授权。该设置是用户
  对服务的信任，不是 OS 沙箱保证；不新增工具信誉系统或自动可信评分。
- 模型可以依据核查结果提出“已发生”的处置，绑定原 Attempt、参数/目标及具体 receipt
  或核查结果。恢复正常工具还要求：原执行已终止、相关未决效果已经核清、证据对应当前
  操作且权限仍有效。Harness 先校验这些运行时条件，再采用模型结论；看到一个文件存在
  不足以证明“复制文件并重启服务”全部完成。复合命令部分完成、旧进程仍在运行、
  结论为“未发生”或无法判断时均暂停，由用户明确处理；不构建通用 Shell 副作用证明器。
- 处置与证据关联复用 Attempt/receipt 及已有轻量 meta，原 UNKNOWN 保持不变；模型
  核查结论不能变成原调用已确认成功，也不能授权再次执行原操作。只有满足恢复条件的
  处置才能解除对应阻塞，其他未决调用仍然阻塞；迟到结果按原 Attempt 关联，不重复采纳。
- 初版每次未决操作最多核查 2 轮模型决策及其只读查询，沿原 Attempt 持久记录次数，
  模型调用重试仍受 6.2 的调用级预算约束；Owner 重启不清零，用尽仍未核清就暂停。
  Full 在正常执行时保持原行为，但不能自动绕过
  未决副作用。核查限制同时用于工具暴露与实际派发，不能通过子 Agent 或扩展绕过。

### 6.4 记录、接续与并发

- 同一 Run 继续工作，每次重试创建新 Attempt 并关联原 Attempt、输入指纹、原因、
  次数与决定；原 UNKNOWN/failed、流片段、usage 和已确认结果保持不可变。
- 一次逻辑模型请求只采纳一个完整响应；失败/部分响应返回的工具调用不能派发。
  迟到响应不能和重试响应一起进入工具执行。
- 为允许已安全替代的模型 UNKNOWN 后继续执行，增加轻量的结果处置关联；不改写旧
  Attempt 状态，也不让全局 UNKNOWN 阻断逻辑误把这个已处置的纯生成请求当成未决命令。
  工具 UNKNOWN 的阻塞解除复用同一关联并遵守 6.3 条件，不能仅凭模型写了“已发生”放行。
- 预算、重试派发与结果采用持久保存；Owner 崩溃后不能把次数清零或默认重放。未决
  写命令继续原核对规则，待发消息仍不能越过审批或未决作用。
- 引导、用户停止、权限撤销、模型变更发生时重新检查下一次派发。旧输入重试不能
  压过用户的新要求或换成权限更高的配置。

验收：故障注入覆盖首包前、流中、结束前断线、重复/迟到返回、普通限流与额度不足的
区分、输出截断、停止、重启和引导竞态；覆盖 Full 下只读核查、MCP 缺省/导入/显式授权
与声明不符、部分完成/旧执行存活/证据错配/多个未决操作、核查结论与原 UNKNOWN 分开
记录、迟到结果及重启后次数不清零。模型能恢复，工具副作用计数严格为一次。
真实 DeepSeek 跑长对话与受控中断，区分实际结果、模拟结果、未运行和 UNKNOWN。

## 7. PostgreSQL：单一新存储后端

按用户要求，从 v8.0 起统一使用 PG 保存运行状态及现有显式 Memory/知识记录；默认 Core
也依赖 PG。当前 v7.x 的 SQLite 是切换前实现，v8.0 不继续打包其运行驱动，不提供
双后端、双写同步、SQLite 自动回退或旧平台兼容层。配置文件、受保护凭据和附件文件
仍按自身职责保存，不因数据库统一而全部塞进 PG。

实施依据：[PostgreSQL 数据设计指南](FREEAGENT_PG_DATA_DESIGN_GUIDE_2026-11-06.md)。
该指南区分 v8.0 必做约束和后续可选扩展原则，字段设计以切换前已落地的 v7.16 记录为准。

已确定不导入历史，删除导入工具的开发范围。切换前保留经过验证的旧数据库和附件备份；
新库重新配置、配对。计划阶段不删除或改写现有 SQLite 数据。

### 7.1 产品与部署选择

- 目标：统一一种数据库技术、驱动和运维流程，同时让运行记录、Core 自有知识、共享
  知识和协作协调保持明确归属；不提前建设分布式数据库平台。
- 便携版随包携带固定主版本的 PG 程序。启动器在数据目录里启动一个只供本机访问的
  实例，只负责启动、就绪检查和有序停止；不注册系统服务，不装 Docker。
- 生命周期跟随 Owner，沿用 §4.1 的退出表：GUI、attach CLI、Web、运行任务、等待
  确认和后台命令统一参与存活判断。v8.0 把自管 PG 加到最后停止，不重新建设生命周期
  管理；需要一直在线的 Bot 部署在服务器上。
- 服务器和多 core 场景可连接外部 PG，使用同一套查询代码；每个 core 使用独立数据库和
  最小权限角色。外部 PG 不归启动器关闭；v8.0 外部连接范围见 3.1。
- 同一 PG 实例可承载多个独立 Core 数据库。独立便携包默认管理自己的本机 PG；用户
  显式配置共用已有实例时，不再启动随包实例，也不自动发现或接管其他便携包的数据库。
  Core 自有 Memory/小型显式知识集合与其运行记录同库受权管理；更大的知识库由可选
  扩展维护 PG 数据域，Core 通过获授权工具处理，不把提炼、索引治理或学习器内置到 core。
- 各 core 不直接读写其他 core 的私有状态和知识。后续共享知识库、协作协调可各自拥有
  独立 PG 数据库，由相应模块管理；仍只维护一种数据库技术。跨库引用使用明确的来源
  Core/记录/版本，不假设跨库外键或单一事务。拓扑视图从执行关系生成，不另建图数据库。
- v8.0 只交付现有能力的 PG 实现和这些边界。跨 Core 任务认领/租约、全局执行拓扑、
  自动知识维护、向量检索、跨机接管及分片属于后续可选能力，不预建空表或后台服务。
  单 Core 完整功能和首次启动体验优先；两独立 Core 共用同机 PG 的检查只是数据隔离与
  资源预算回归，不扩展成集群管理产品，也不替代单 Core 的真实使用验收。
- GUI/CLI 继续 attach 同一 Owner。当前阶段不允许两个 Owner 同时执行同一个逻辑数据库；
  不新增多租户/组织权限平台。
- 外部连接的 DSN/密码使用秘密输入或凭据引用，不放进命令参数、聊天日志、公共报告和
  发行包；数据库端口不暴露到公网。

### 7.2 随包实例要求

- 初始化明确指定 UTF8（`-E UTF8`），避免继承中文 Windows 的 GBK 等不受支持的服务端
  编码而导致 initdb 失败。排序与字符分类规则随 PG 发行物明确固定；`LC_CTYPE` 还影响
  trigram 字符识别，不能仅凭 `--locale=C` 就宣称中文检索具有索引加速。按数据指南 6.2
  验证 Windows/Debian 12 的实际行为，不要求普通用户自行调整 locale。
- 只监听 127.0.0.1，端口和密码随机生成，同时打开多个便携包也不冲突；使用 SCRAM 密码
  认证，不用 trust。端口须在实际启动时确认占用情况，冲突则有限重选；不能连接到占用
  该端口的其他实例来冒充启动成功。
- Owner 崩溃时，自管 PG 由启动器收束停止；下次启动先检查残留实例并自动恢复，不能留下
  占着端口的进程。只处理经数据目录和进程身份核实属于本实例的进程，不停止外部 PG。
- Linux 上 postgres/initdb 不能以 root 运行。Hytron 部署记录显示已使用非 root 的
  freeagent 用户，实施前再核实实际配置，并重新验证该身份下的 Linux 命令沙箱。
- Windows 使用配套的 initdb/pg_ctl，验证受限令牌启动和 VC++ 运行库依赖；不能要求用户
  靠管理员权限解决问题。
- 主版本固定，升级大版本时通过明确的导出、导入完成；这指 PG 到 PG 的维护升级，不恢复
  SQLite 历史导入范围。PG 程序预计增加数十 MB 以上的发行体积，实际包体积和冷启动耗时
  测量后写进发行说明。测试使用同一套程序临时建库，不依赖 Docker。
- Windows 和 Debian 12 都要验收：首次启动、异常退出后重启、端口被占、磁盘满、
  路径带空格和中文；Windows 额外覆盖全新目录直接双击、普通/管理员身份、干净系统运行库，
  Debian 12 覆盖非 root 启动与 Linux 沙箱。故障测试使用独立目录，不影响常驻 Bot。

### 7.3 存储实现

优先使用 `pgx` 的现有连接池和事务能力。先提取 Store 内部连接/事务接口与关键 SQL，
不抽象一个能支持所有数据库的 ORM 平台。SQL 按实际 PostgreSQL 语义重写并集成测试。

- 参数改为 `$1...`，新增采用 `INSERT ... RETURNING`。消息按会话、Attempt 按 Run 在
  短事务内分配顺序号；普通 PG identity/sequence 只作身份，不能当作提交顺序，避免
  并发晚提交的消息被增量游标跳过。消息分支与压缩边界按同一作用域序列定位。
- 关系、状态、过滤/排序键用类型化列，扩展快照和轻量 meta 使用有格式约束的 JSONB。
  审批摘要和协议原文需要的字节表示另按指南保留，不能把 JSONB 重新序列化后当作原文。
  复用现有记录，不趁机拆成八套子系统；现有显式关键词检索也要替代 FTS5 并实际验收。
- 连接池不沿用 SQLite 的单连接配置。初版建议普通池最多 4 条、最小空闲 0 条，Owner
  锁另占一条专用连接；按实测调整，合计所有 Core 和备份连接不得超过实例预算。
  查询锁、连接池等待与模型/工具等待分别记录，事务不跨模型请求、工具执行或平台发送。
- 队列取消、转引导、消费与 Run 创建使用同一事务锁定事实；源版本、唯一请求键、活动
  Run 唯一约束和审批摘要检查继续有效。并发写冲突只重试确定未产生作用的 DB 事务。
- 单 Owner 使用长连接 session advisory lock 或等价 PG 锁；连接断开会释放锁，Owner
  必须在检测到失锁后停止新派发并收束已有调用。锁连接必须独立持有，不能归还普通连接池。
  每次派发事务核对数据库保存的 Owner 代次；回写结果同样核对原派发代次，旧进程不能
  在失锁后继续以新 Owner 的身份记账。文件锁不能替代数据库 Owner 锁。
- advisory lock 和代次校验不能撤销已经启动的宿主命令。跨机器接管不在 v8.0 范围；
  旧 Owner 消失但仍有已派发调用时，先保留 UNKNOWN 并核对旧进程与实际效果，不让新
  Owner 立即重复执行。本机人工恢复须确认原进程停止、工作区与附件可用后再启用。
- 明确“失去 DB 连接但命令已执行”的处理：结果先按可保存的本机 receipt 保全并报告
  UNKNOWN；不能因事务没提交就再执行命令。DB 恢复后核对关联，再决定接续。
- 附件正文先持久化再提交可见引用。`Commit()` 返回连接错误不等于事务回滚；提交
  结果未知时保留文件、原请求键/附件 ID 和最小待核对标记，禁止沿用失败清理直接删文件。
  重连后核对原事务与引用：已提交则采用原记录，不重复发布；确认原事务终止且无引用
  后才允许回收；仍不可判断就保留待核对。查询失败不能当成“无引用”，暂存/孤儿清理
  跳过未决文件，回收继续与备份互斥；复用附件记录，不建立独立恢复服务。
- 本地工作区、附件不可变文件和 OS 句柄仍在有权访问的机器上，不把所有大文件或秘密
  塞进数据库。跨机器搬 Owner 不在 v8.0 范围，不把数据库共享等同于文件共享。
- schema 初始化/升级是显式、可验证的部署步骤；未知 schema 拒绝。最小角色权限、
  连接池大小、连接/查询/事务超时和取消都有明确边界。

### 7.4 备份、性能与测试

备份时不暂停任务。用导出的 PG 快照同时生成 dump 和附件引用清单（`pg_export_snapshot`
配合 `pg_dump --snapshot`），再复制不可变的附件文件。删除附件时先撤销访问，物理回收与
备份互斥；配置和 Skill 文件也先固定版本再复制。当前代码会直接删除附件，这部分需要改造。
使用随包、版本匹配的 pg_dump；不新增分布式备份服务。恢复到新数据库和新数据目录后，
验证数据关系与文件；禁止在线覆盖生产数据库。

导出事务保持到 dump 与清单读取完成，不能事后取一份当前清单拼到旧快照。物理回收互斥
覆盖暂存/孤儿清理；缺文件或导出失败不标记完整备份。配置/Skill 的固定副本须与快照的
配置版本对应，取得快照与副本后即可释放短暂的配置保存锁，不阻塞普通任务派发。

验收使用真实 PostgreSQL（固定受支持版本）、独立测试数据库：

1. 核心全量/事务/并发、输入队列与引导、分支、摘要、附件、审批和失败记录等原契约通过。
2. 两个进程竞争同一逻辑数据库时，严格只有一个 Owner；失锁、DB 重启不产生
   重复命令。同一个 PG 实例上多个 core（各自独立数据库）并发运行。
3. 故障插入事务提交前后、连接池耗尽、死锁/序列化失败、命令结束但保存失败等边界。
   附件覆盖“数据库提交成功但回执丢失”、真正回滚、重连查询失败、进程崩溃后清理及
   重复请求：不得出现已提交引用的正文被删、未决文件被当孤儿清理或重复发布。
4. 升级、备份、空库恢复、附件缺失与回退完整演练；生产旧备份始终保留。
   大版本升级走导出、导入；覆盖任务与上传持续进行时的备份、删除撤权与物理回收互斥。
5. 对比同样工作负载下的启动时间、空闲 RSS、请求 p50/p95、SQL 往返次数、并发吞吐
   和大历史查询。减少 N+1；队列、快照和日志查询继续有界。未测量不宣称性能更优。
6. 按数据指南验证各 Core 数据库/角色互不越权、消息晚提交不会被游标遗漏、JSONB
   规范化不改变审批绑定、Memory 版本与可见范围有效、关键词中文/短词检索不退化成越权扫描。

### 7.5 v8.0 内部实施顺序与退出条件

| 阶段 | 必须产出 | 退出条件 |
| --- | --- | --- |

## 8. 独立扩展计划：经验总结

### 8.1 名称与职责

用户可见名称统一为“经验总结”，归入“设置 → 能力管理 → 扩展”。经验总结做成可选
Skill，并提供一个对选中消息使用的“总结经验”按钮；按钮调用同一 Skill，生成候选内容后
走已有确认。不需要专用进程、后台扫描或新的存储体系。core 保存真实记录、提供有界
授权读取与既有能力调用，以及通用的上下文选择；core 不内置提炼器、经验评分或后台学习。

“经验总结”与自动上下文压缩分别工作：压缩维持当前对话可继续，摘要会随对话更新；
经验总结产物需审核和选择用途，不因为发生了一次压缩就生成 Skill 或永久经验。

### 8.2 两类产物

| 适用内容 | 产物 | 运行时如何使用 |
| --- | --- | --- |
| 有明确触发条件、输入、步骤、分支/检查点与验收方式的可重复流程 | Skill | 平时提供名称和描述；用户调用或模型按已授予能力加载时才加入正文 |
| 一两条稳定事实、约定、偏好或简短操作经验，不需要整套流程 | 可固定的 Memory | 用户确认固定后，在选定范围的后续请求中持续带入短文本，并计入窗口预算 |
| 证据不足、一次性巧合、仍含未解决 UNKNOWN 的结果声明 | 保留草稿或原记录 | 不自动发布为确定的成功经验；可以明确写成失败教训或待验证项 |

判断看流程是否可重复、步骤是否固定，不能只按字符长度自动决定。用户可在预览时
把产物改成另一种形式。生成一个 Skill 不默认把它的全文固定进每轮上下文。

例：带备份、配置修改、启动、健康检查和回退分支的服务部署过程适合 Skill；
“Linux 验收使用 Hytron Debian 12，普通测试使用独立目录”适合固定上下文。
“本次部署成功”是一次结果记录，不能直接升级为长期稳定规则。

### 8.3 用户流程与保存

1. 用户启用经验总结，选中 Run/会话或明确的消息范围后，点击“总结经验”。
   默认不扫描整个历史，也不在每次任务结束时自动运行。
2. Core 把选中的记录作为输入，启动一次普通 Run。交给模型前，Core 按已保存的
   凭据精确替换密钥，并尽量识别常见密钥格式；保存 Skill 或 Memory 时，Core 再检查一遍，
   发现密钥就拒绝保存。两项检查都在 Core 的通用流程中，不能只靠 Skill 里的说明。
   模型自报成功不能当作执行证据；不能读取其他空间、凭据或未选择的私有内容。
3. 预览显示建议类型、标题、正文、适用条件、来源和局限。Skill 显示输入/步骤/验收/
   失败处理；固定内容显示预计占用与生效范围。用户可以编辑或拒绝。
4. 用户确认具体内容及范围后发布。Skill 沿用现有 Skill 目录/格式和启用开关；
   简单经验复用 Memory 条目，只增加最小的固定属性、范围和版本，不新增经验表。
   保存不等于自动启用：需要固定时，在同一次确认中明确“保存并固定”及目标范围。
5. 同一请求标识避免重复发布；已有内容的修改绑定期望版本，冲突时重新预览。禁止
   静默合并相反经验或覆盖用户已修改的 Skill。失败/取消保留已有产物。
   语义冲突只在预览时提示；并发修改造成的版本冲突在保存时检查，两者分开处理。

固定内容是普通用户可管理的通用输入，不是插件专用核心对象。即使经验总结停用，已经
确认保存的 Skill 或固定文本仍可使用、修改、取消固定和删除；停用经验总结会停止后续
总结调用，不擅自删除用户产物。模型提出任何持久化修改继续走既有确认。

### 8.4 固定到上下文的准确语义

- 默认只固定到当前对话。用户可明确选工作区或全局范围；跨核心不自动同步。全局与
  工作区内容在设置中管理，对话输入区显示本会话实际带入的内容及其来源，可排除。
- 固定内容按源记录独立装配，不混进历史摘要，不随历史压缩消失；清除摘要不清除固定
  内容，取消固定则后续新请求不再带入。已发送的模型请求和旧记录不会被追溯改写。
- 同一固定条目在请求中只出现一次，当前对话显式排除项优先；条目间的语义冲突在总结
  预览时提示，由用户选择替换或排除；Core 装配时不判断语义冲突。当前明确用户要求
  可以覆盖普通经验约定，固定文本不能提高权限、启用工具或把历史宣称变成执行证据。
- 初版建议单条最多 2 KiB UTF-8、合计最多 8 KiB，同时受现有 Memory 与完整请求预算
  约束；先用少量内部默认值，不新增复杂预算面板。超限提示精简、取消固定或改为 Skill，
  不悄悄截断固定文本，也不无限压缩无关历史。
- 固定经验由 core 统一选择与装配，GUI/CLI/TG 共用同一范围、版本、可见性和撤销规则，
  不新增 TG 专用固定内容或公开 Memory 系统。当前外部入口直接跳过 Memory/Skill 的
  实现需在渠道拆分阶段改成统一授权检查：已明确授予当前身份/空间的内容可以使用，
  其他私有内容仍不可见。None 的工具执行限制与文本可读范围分别判断，不能用“无工具”
  直接推出“无权读取已授予的固定经验”。渠道只传递发布/选择操作和 core 的确认结果。
- 经验内容确认、保存和选择的版本需要一致。当前 Run 的选择保持冻结；修改或取消生效
  于后续新 Run，下一次派发继续检查源有效性，不能在后台给已授权运行加一条新规则。
- 固定内容的 core 侧装配随 v7.15 渠道拆分交付；用户可独立手动固定或取消，不依赖经验总结。
- 以后的多层知识库（可启用的共享知识库、以运行时为核心的单会话知识库）接入 v7.13 的
  上下文预算和这里的固定内容，按同一套预算放进请求；本轮不提前建设知识库。

因此这不是“把扩展生成文本直接塞进最高优先级 system prompt”。普通 Memory 参考数据
与用户明确确认的固定约定要保留不同来源标识，后者仍受当前请求与运行权限约束。

### 8.5 验收

- 未启用经验总结时，没有总结模型调用、扫描或后台工作；默认 core 不包含提炼器。
- 复杂流程形成可加载的 Skill，简单经验形成有范围和预算的固定文本，预览允许用户改选。
- 固定文本跨重启和多次压缩仍在所选范围生效；取消固定后新请求不再包含；全文不会因
  旧摘要又被自动固定回来。历史中对它的引用只是历史，不能被宣称为已删除旧历史。
- 同一身份和范围下各入口固定内容一致；群/私人空间与其他私有范围互不泄露。
  未授权发布、来源失效、源版本冲突和重复确认正确处理。
- Skill 生成不自动调用其中的命令；固定内容不能扩大工具权限；未决结果不能被总结成已完成。
- 经验总结停用后已有产物仍可手动管理，删除产物按现有文件/Memory 删除确认执行。
- 发给模型的记录和保存的产物里不出现已知密钥；分别测试输入脱敏和保存拒绝，不能仅
  验证 Skill 提示。未知密钥格式识别为尽力检查，不宣称能识别所有秘密。

## 9. 交付规则与停止条件

逐阶段提供实际源码、针对性和必要全量测试、使用/恢复说明及可下载产物，标明未运行的
真实 Provider/渠道矩阵。用户不需要模型输出哈希值。重试/插件/PostgreSQL 未实现前，
发行说明和界面不得提前宣称已支持。

Hytron 部署使用专门维护窗口：先查任务、备份并验证，再明确切换和健康检查；常规回归
使用独立 unit、端口、逻辑数据库和文件目录，不动 NPM 或其他业务。
渠道连接与数据库切换分别有回退路径，禁止一个维护步骤同时替换所有边界而无法定位失败。

Hytron 切换到新库时，先停止旧实例，再启动新实例。新实例首次启动时丢弃 Telegram 积压的更新
（调用 `deleteWebhook`，并设置 `drop_pending_updates=true`），同时忽略切换时间之前的消息，
避免把切换前的旧消息当成新指令执行。新库重新配置、配对。
这是本次切换的一次性操作，完成后持久记录；普通重启不得再次清空积压更新。
