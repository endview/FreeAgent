## 1. 归属、代码和数据

本专项属于 **FreeAgent Core 的通用会话与交付能力**。用户直接发出的指令、普通模型和获准扩展都可使用同一入口。Core 不根据某个人物的情绪自行决定“该关心用户了”。

| 工作 | 所在位置 | 责任 |
| --- | --- | --- |
| 目标/来源授权、表达能力、内容冻结 | `internal/harness/channel_bridge.go`、`channel_runtime.go`、权限与控制路径 | 谁可向哪发、何时可发；校验扩展给出的具体部分并形成交付记录 |
| 顺序、调度、取消、到期、逐条结果 | `internal/harness/channel_outbox.go`、`channel_delivery_queue.go`、`channel_messages.go` | 复用 outbox、消息、Run/Attempt/receipt，保存唯一交付事实 |
| 资源读取与已选资源 | 现有附件/渠道资源路径 | 资源属于哪个空间、哪些身份可读和使用 |
| 扩展调用 Host | `internal/harness/extensions.go`、`extension_identity.go`、`extension-kit/SPEC.md` 与 schema | 接收候选、验证身份和当前能力；能力未实现前不列入当前协议 |
| 客户端入口 | `internal/chatui/frontend`、`cmd/freeagent`、控制目录 | 通用投递授权；本轮表达入口由已安装并选中的扩展元数据提供；TG 页仅提供目标适配配置/链接 |

权威状态留在 Core 的既有 PG 消息、outbox、控制和附件记录中。只持久化一次授权与一次真实交付；扩展记录它引用的结果，不另存可独立派发的发送队列。typing 等短效活动不写成永久消息。

Core 管理产品层的每日额度、冷却、静默与到期；TG 管理平台 API 的短期限流信号，并把 retry_after 等事实交回 Core 安排后续派发。两层不各自运行一份完整重试/定时队列。

### 1.1 谁决定表达，谁执行

- 用户或普通模型：提出回复内容与获准资源选择；普通模型没有内置语义分段工具。
- AffectWeave：拥有回复形式、默认值、自然段算法及相应设置声明；可返回具体部分。表情/贴纸倾向与有依据的主动动机仍按独立后续计划实现，不拥有发送权限。
- Core：按用户选择、作用域、权限、预算、静默时间和当前状态决定是否受理，并安排具体投递。
- TG 渠道：按平台规则渲染、拆成合法分片、调用发送/反应 API、返回真实结果；不修改人物状态。
- Provider：只处理生成请求及协议，不直接发送 TG 内容。

收到 sticker/reaction 的流程相反：渠道报告平台事实 → Core 核对身份与可见范围并保存 → 当前模型或显式启用的 AffectWeave 读取获准事实。Core 不把某个 reaction 直接升级为关系变化或 L3 成功。

### 1.2 分段有三个层次

| 层次 | 归属 | 示例 |
| --- | --- | --- |
| 表达意图 | 用户选择已安装扩展的选项；AffectWeave 执行策略 | 想分两句、先回应再发一张贴纸 |
| 逻辑部分与交付 | Core | 固定内容与顺序、取消尾段、记录部分送达 |
| 平台分片 | 渠道适配器 | TG 长度限制、实体偏移、代码块拆分 |

“主动表达动机”和“定时派发”也按同样原则分开。扩展只提出/撤销自己的候选；Core 拥有有效授权、触发与待派发记录。扩展在有效回调中确认人物事项是否仍适用；Core 只处理候选是否有效，不直接查询或解释 AffectWeave 私有 PG。

## 2. v8.5：分段表达与统一交付

### 2.1 区分平台拆分与表达分段

- 平台拆分：为满足长度和格式限制，将原内容拆成合法消息；现有能力的可靠性修复在 v8.3.1 完成。
- 表达分段：一个回答有意分成几条，例如两条短文字后跟一张贴纸；由安装并选中的 AffectWeave 等扩展提供策略及具体部分。

普通 Core 保持原回答，只因平台长度/格式进行必要分片。安装并启用 AffectWeave 后才提供完整一条/自然分段与默认值；扩展在 turn.finished 返回最多 3 个无损具体文字部分。Core 不解释模式或运行语义算法，只核对原文、来源与传输上限。额外平台分片另算，不删除尾部内容。GUI/CLI 使用扩展声明的通用本轮设置，冻结到原 Run/队列；停用/卸载撤销后续策略，已冻结组保持原事实。

首版在回答内容确定后分条发送，GUI/Web 原有 token 流式继续。TG 不做每 token 更新，也不承诺边生成边发送多个不可撤回半成品。

### 2.2 复用数据与职责

一个逻辑回答仍绑定原 Conversation/Run。复用现有 outbox Operation，补充一组最小字段：逻辑回复标识、表达部分序号、平台分片序号、总数、内容类型、源内容引用、可选最早发送时间和失效时间。

Core 负责内容/目标/顺序与确认，TG 渲染器负责平台文本和实体。需要平台二次拆分时，先由渠道返回有界、确定性的渲染结果，Core 持久化各分片后再逐条派发；不能让一个“已发送”回执暗含多个无法逐条核对的 API 请求。

每个分片使用固定内容与稳定 ID。渲染后的文本、格式实体和渲染版本一起冻结，重启或升级不能改变旧待发送消息的内容/切分。

首版采用最小适配接口，不建立通用消息编排器：已有 text/file 加 sticker/reaction；typing 是短效活动，不属于持久交付部分。

### 2.3 顺序、取消和 UNKNOWN

1. 同一目标按逻辑回复和部分序号发送。某个回复中的片段不能按内容哈希顺序派发；多个会话指向同一 chat 时也不能交错破坏一组内容。
2. 第一条成功、第二条失败时记录逐项结果和整体 partial，后续未发送部分保留待处理。已送达部分不重复创建。
3. UNKNOWN 表示平台可能已接收。初稿要求修正的自动重投路径已在现行版本回归覆盖；当前 UNKNOWN 不再自动变成可派发候选。后续动态生成也必须保持：TG 无可证明的幂等发送支持时，不自动再次发送 UNKNOWN 项。
4. 429 等明确未接收的可重试错误按 retry_after 有界调度；请求一旦可能送达，不能用换格式、换 ID 或重跑模型掩盖不确定性。
5. 后续片段在每次派发前检查取消、授权、目标有效性和期限。停止只取消未派发部分，不假装撤回已送达消息。
6. 分段间默认遵守现有平台限流，不增加随机“装作真人打字”的长等待。可选短间隔计入发送计划并受取消约束。
7. reaction 回执、贴纸回执、文字回执保留各自含义。只有实际送达部分进入渠道公开上下文和后续反馈来源。

UNKNOWN 暂停的是该逻辑回复未发完的部分，不占住模型槽或永久阻塞同一聊天。用户的新请求可以正常处理；旧回复的未发部分需明确续送或放弃，不能在新对话过程中突然补出旧尾段。所有待发项绑定原 Bot/空间/会话/目标，GUI 切换会话或 TG 改默认会话不会重定向它们。

## 3. v8.5：受限主动投递

### 3.1 三类触发

| 场景 | 触发与授权 | 首版范围 |
| --- | --- | --- |
| 已委托任务完成后通知 | 原任务明确的结果目的地 | 复用现有结果回传，补一致的目标与回执 |
| 用户明确要求稍后提醒/跟进 | 具体一次性时间、目标、固定内容 | 有限、可查看、可取消的一次性待投递项 |
| AffectWeave 等扩展主动表达 | 预先确认的触发规则与范围，扩展提出候选 | 首版只做明确事件触发和一次性 follow-up，不做周期性“随机来聊” |

主动投递默认关闭。单独允许某个扩展、某个空间/会话和明确目标；加入 Bot 白名单或开启 Full 不等于允许向任意人主动发消息。

### 3.2 最小执行路径

扩展或用户提出带来源的投递候选 → Core 验证已授权规则和当前身份/目标 → 需要新持久规则时生成现有控制预览 → 触发时再次验证 → 将已冻结的内容放入现有 outbox → 保存真实结果。v8.5 只接受固定文字或获准贴纸，到时不再调用模型或命令。

- 扩展不取得 TG Key 或 Core 数据库连接，不自行调平台发送；扩展仍可使用自己的受限 PG。AffectWeave 负责“为何想说、拟表达什么”，Core 决定是否允许，渠道负责送出。
- 新的通用 Host 能力只用于提出候选和查询自己的结果，必须显式声明并受 invocation、目标和额度限制；人物被动上下文默认不获得它。
- 扩展进程退出后不能继续使用旧 invocation；未来时间的任务由 Core 保存的明确一次性项触发，不能要求扩展常驻循环偷偷发。
- 复用现有渠道 outbox 轮询检查待到期候选；没有候选时不增加专用定时器或后台任务，不建设 cron 平台、跨机器调度或独立 scheduler 服务。
- 候选触发不意味着生成内容已获准跨空间读取。模型生成只使用目标空间获准的上下文，不挪用另一私聊的人物经历。

### 3.3 用户可控的边界

每项规则明确：来源扩展、接收会话、触发类型、有效时间、用户时区、静默时间、冷却、每日上限、是否允许贴纸、是否需产生文本及是否遇到新消息就取消。

首版自动 follow-up 默认每目标每天最多 1 次、冷却 6 小时、只发一条文字或一张已授权贴纸；明确任务完成通知单列，不能借通知类型绕过限制。数字属于可调整产品初值，不代表平台配额。

发前 Core 检查最新权限、目标连接、扩展是否启用、原会话是否已有新输入、候选是否有效及是否仍在静默时间。TG 负责返回平台是否允许实际发送；人物事项是否已解决由 AffectWeave 在有效回调中复核，或主动撤销自己的候选，Core 不读取人物私表。必要的扩展复核不可用时跳过本次可选表达，不猜测仍然适用。缺少时区不猜当地时间，使用界面显示的用户配置；到期后不在重启时集中补发过期问候。

用户要求新增规则、或模型建议修改规则时确认具体内容和范围。规则生效后的每次符合规则的触发不再逐条打断确认；超出规则时不发送。用户可以随时关闭，关闭后取消尚未派发的候选。

本版本不做群发、联系人发现、后台人格驱动社交、未授权陌生人触达或自动情感关系维护。所有提议、抑制原因、实际生成及交付结果可从原记录查看。

## 4. 本专项验收与能力契约

### 4.1 扩展与渠道两条交界

本节定义已实现契约的数据责任。实际方法和参数以 `extension-kit/SPEC.md`、schema 和扩展开发指南为准；真实平台验收边界见[本批记录](VALIDATION_V8_5_2026-11-08.md)。

| 方向 | 可传递内容 | 边界 |
| --- | --- | --- |
| Core → 扩展 | 本轮允许的表达类型、当前作用域、资源/消息引用、有界可信事实 | 不交付 Bot token、任意目标或 Core 私表连接 |
| 扩展 → Core | 候选来源、授权目标引用、期望的逻辑部分/表达类型、内容或生成范围、有效期与取消条件 | 候选不等于批准/已发；不提交 Telegram entities 或 Provider 私有字段 |
| Core → 渠道 | 已授权目标、固定内容、平台渲染任务或已冻结分片、派发 ID 与短效活动 | 不交付人物状态和人格算法；渠道不能拓宽目标 |
| 渠道 → Core | 平台资源、渲染结果、真实入站事件、逐分片/动作回执 | 不解释关系、不替 Core 批准、不私自重排/重试 UNKNOWN |
| Core → 扩展 | 受理/拒绝/取消及已核对的发送、部分、失败、UNKNOWN 来源 | 扩展据此分析后再走自己的持久确认；单个回执不证明用户满意 |

公共 Host 合同由 FreeAgent 提供并验收，AffectWeave `internal/extension` 只实现调用和结果转换。当前的被动上下文接口不能顺便发送消息；表达候选能力须单独声明和授权。对同一内容只形成一份 Core 待发记录，扩展重试提交同源候选只查询或复用原结果。

### 4.2 验收归属

| 范围 | 必须覆盖 |
| --- | --- |
| 文本传输 | 多段顺序、同 chat 并发、第一段成功后失败、429、格式确定拒绝降级、UNKNOWN 不重发、重启续传未发部分 |
| 分段表达 | 文本＋贴纸顺序、单个逻辑回答、逐段回执、停止取消尾段、平台二次分片、回执迟到和内容冻结 |
| 主动投递 | 未授权拒绝、开关撤销、指定目标、静默时间/时区、过期、冷却/每日限额、新消息取消、重启不突发补发 |

用无人物扩展的普通任务、一个合成候选来源和真实渠道联测；Core 交付能力通过后，AffectWeave 再验收自己的人物表达策略。两项结果分开记录，不能用普通投递 PASS 声称人物主动表达已完成。

实施时在 `extension-kit/SPEC.md`、schema 和 `docs/EXTENSION_DEVELOPMENT_GUIDE.md` 增加实际完成的 Host 能力，在渠道协议中声明真实支持的内容/回执类型。`docs/AFFECTWEAVE_HOST_CONTRACT_V8_3.md` 保留原文件名，当前已有状态契约 v2 的更新说明；它和现行开发指南均不能直接混入未实现能力伪装当前行为。

## 5. 后续：可选扩展的到期生成与主动对话

状态：**待实现**，配套 AffectWeave 1.3。产品策略与完整验收由 [AffectWeave 仓库](https://github.com/endview/affectweave)的 `docs/AFFECTWEAVE_PROACTIVE_CONVERSATION_PLAN_2026-11-08.md` 维护；下表明确 FreeAgent 的最小职责，不复制人物策略或另一套默认值。

### 5.1 已核实的缺口

现有 `delivery.check` 只复核已冻结候选，禁止 model.generate/tool.call/task.delegate 等调用；它不能负责到期生成。现有 `extensionIdentity` 依赖真实用户 adopted_inputs，也不能复制旧输入冒充这次主动执行。`ChannelBridge.Outbox` 当前同步调用 prepareScheduled；慢模型不能放进这一 HTTP 路径，拖住正常发送和回执。

允许扩展在已确认规则下获得一次有限唤醒、使用现有 Run/Attempt 执行生成，再进入既有固定投递。Core 不决定为什么聊天、选什么人物话题，也不读取 aw 表解释动机。

### 5.2 拟议增量及实现位置

| 位置 | 必要增量 | 保持的边界 |
| --- | --- | --- |
| 扩展声明/Host 权限 | 能力暂称 scheduled_generation；turn.finished 可返回有限 wake_hint，到期用新 wake.evaluate 回调；严格 schema 与能力握手 | 名称为待定稿契约；旧 passive_context、delivery.check 不获得额外模型权限，不按扩展 ID 特判 |
| 配置与控制确认 | 每扩展的通用主动生成总授权 enabled、具体目标/时间/用量规则；人物页操作同一份权威配置 | 总开关默认关闭；安装、开分析、Full 或旧固定提醒规则均不能隐式开启；模型修改授权仍具体确认 |
| 既有 meta/Run/Attempt | 有界机会、唯一时间槽/来源键、短事务领取、关联一个 Run、派发与用量记录 | 不新建任务平台或第二份调度数据库；模型调用不持 PG 行锁 |
| 扩展身份 | 区分真实用户采用与已授权扩展触发；新 Run/事件/规则/目标由 Core 绑定 | adopted_inputs 可明确为空，但只在新能力的合法触发分支；不放宽正常模型状态提案的原输入校验 |
| TaskService/Owner | 按现有可用执行槽低优先级派发，有用户任务时让行；无工具、一次模型请求，取消及时 | 不在渠道 HTTP/outbox 轮询中等待模型；不增加独立执行池或常驻人物进程 |
| Context/Provider | 只读且获准的有限来源与扩展片段，冻结模型/来源/规则版本，派发前预留额度 | 没有分析修复、模型替代或隐式重试；不启动普通完整工具循环，不拥有人物规则 |
| 通用交付 | 生成结果持久化后再核对授权/输入水位，原子关联现有准备/冻结/outbox/receipt | 总开关关闭或有新输入时未派发内容取消；已派发不能假装撤回；UNKNOWN 不重发 |
| 客户端 | 同源控制的开关、状态、用量、暂停/恢复、只生成预览；会话展示主动来源 | 未安装时无人物专用入口；公网管理能力按实际支持展示，登录不等于允许一切管理操作 |

### 5.3 不可省略的验收

- 总开关在创建机会、派发模型、采用结果、平台发送四处有效；关闭后撤销未派发工作与旧 invocation，重启/重新安装不会自动恢复开启。仅改 UI 显隐不算关闭。
- 规则内的唤醒/发送是已授权执行，日志正常保存；不借此自动写入长期 Memory/关系/人格。开场生成与实际送达分开。
- 用户输入与主动执行的并发需通过同一身份/水位检查；用户新任务不被无工具的主动 UNKNOWN 永久卡住。
- 多规则、改 ID、换人物、重启不重置已消费额度；同一机会最多一个原 Run/一次真实模型请求，实际结果未知保留额度。
- 无规则时无新增周期扫描/连接/模型请求；启用时的慢模型不延迟渠道收发与回执。Owner 离线不承诺唤醒，过期机会不堆积补发。
- 用一个不含人物字段的合成扩展跑通合法唤醒、skip/生成、撤销和恢复，再做真实 AffectWeave 联测。主体人物策略只在扩展中改变。
- 首版范围与具体预算见配套主动专项；待契约联调通过后才写入现行 Extension Kit SPEC/schema 和开发指南。本轮文档修订不升级 Core、不启用线上主动能力。
