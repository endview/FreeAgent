## 2. Telegram：采用一套申请与批准流程

参考 OpenClaw 的分层准入、Hermes 的身份绑定申请与限流、nanobot 的集中入口检查。只移植这些机制，不引入它们的多账号平台、角色系统、迁移体系或并行授权存储。

### 2.1 用户流程

1. 私聊陌生用户发送 `/start`，即发起一次接入申请，得到“申请已提交，等待管理员批准”和一个短申请码。请求绑定真实数字用户 ID、Bot ID 和聊天 ID；普通陌生消息不自动创建申请。
2. 管理员在已登录的 FreeAgent Web/GUI 的 Telegram 页面或本机 CLI 查看请求；卡片显示同一申请码、昵称、数字 ID、私聊/群、申请时间和授权范围。用户可通过与管理员已有的联系渠道核对申请码，避免只凭可更改的昵称认人。GUI 点击批准；CLI 可用申请码定位请求，展示完整身份与范围后确认。
3. 管理员批准后，在同一核心提交中写入接入策略并创建或关联现有空间及默认对话。批准默认只授予聊天资格。提交成功后 Bot 通知申请人；通知失败不撤销已批准资格，明确的再次 `/start` 可查询结果，UNKNOWN 通知不自动重发。
4. 用户可另获工具权限；页面直接展示最终能做什么及限制来自哪里。可以在同一设置页完成，但不得因批准接入而隐式提升 Full。
5. 停用访问保留空间和历史。重新授权由管理员明确操作，不通过重新发送旧码恢复。

管理员也可直接添加已知数字用户 ID，走相同的准入提交逻辑；这是同一名单的编辑入口，不是另一套配对授权来源。申请码仅帮助双方识别一条已经绑定身份的申请，持有码不能授权自己、兑换另一个身份或跳过管理员确认。

已授权用户再次发送 `/start` 时显示当前接入状态和帮助，不创建新申请或重复空间。带参数的 `/start` 仍按真实事件身份处理；参数不得提供用户 ID、群 ID、权限或可兑换的旧码。过期申请需用户重新发起，不自动重开。

### 2.2 群聊规则

- 群默认不接入。用户在目标群发送 `/start@机器人用户名` 发起申请，管理员批准时同时核对群 ID、申请人数字 ID 和申请码；采用“指定成员”时，该申请人成为首个允许成员。管理员也可直接指定群 ID 和首批成员授权。申请人是群管理员，不代表其拥有 FreeAgent 管理权。
- 群内使用方式只有“指定成员”和“全员可聊天”，默认指定成员。群的准入、发起人的准入和唤醒条件共同生效。
- 私聊批准不自动允许用户在其他群使用；群内批准也不自动授予私聊资格。
- “全员可聊天”不授予工具权限。成员实际执行仍受现有空间与人员工具权限约束。开启时说明群内所有成员均可消耗本实例模型额度；继续复用已有有限执行预算，不新增计费系统。
- 未获得明确用户身份的匿名管理员/频道代发不能冒充个人，也不能审批工具；本版不增加匿名身份授权路径。
- 群公开回复对 Telegram 群成员可见。FreeAgent 的名单控制谁能调用 Bot，不能隐藏已经发到群里的消息，不能据此承诺按成员隔离群历史。

### 2.3 精简后的状态归属

沿用外部空间保存 `source + application_id + chat_id` 绑定。在现有 Store/meta 保存该绑定的接入开关及允许发起人；UI 的“用户/群白名单”是这些准入记录的投影。不再独立持久化“已配对用户名单”并与白名单取并集。

批准后的记录以 Bot 数字 ID 隔离。Token 轮换且 Bot ID 相同可继续使用既有授权；换成另一只 Bot 不继承。用户名、昵称只作为显示信息，不参与授权。

待批准请求使用有界 Owner 内存，1 小时有效。当前只支持一个 TG Bot，待处理总容量为 32 条；按 Bot ID、聊天类型、聊天 ID、发起人 ID 去重，同一人申请私聊和申请群属于不同范围。重复申请复用原请求与到期时间，60 秒内不向申请人重复发送状态通知；管理员只在申请列表看到一条记录，不接收每次重复请求的推送。容量满拒绝新申请，拒绝反馈也沿用现有渠道发送限流。Owner 重启、Bot 身份改变后旧请求失效，已批准准入保留。阈值集中定义，不增加多 Bot 总量策略或一组高级设置。

申请码使用随机生成的 8 位易读字符，在当前待批准集合内检查唯一性，仅绑定该请求，不持久化为授权凭据。昵称、群名按展示文本转义和截断；相同昵称不合并身份。

批准绑定服务端生成的请求 ID、原始用户/群/Bot 和当前策略版本；请求正文、昵称、转发、模型回复均不能提供管理员身份。并发重复批准只产生一次生效结果。

### 2.4 本版删除的旧设计

- 删除 TG 的 Owner 全局通用配对码，以及 `/pair CODE` 兑换即创建访问资格的路径。
- 删除 TG 的“生成 10 分钟配对码”入口，替换成申请列表与允许名单。
- 普通停用使用“停用访问”，保留空间和历史。删除外部空间会同时撤销该绑定的准入并解除外部关联；删除确认明确列出影响，现有对话按原有规则移回本地，不因后来重新建群绑定而自动发布旧记录。
- 删除“已配对即可聊天”作为另一条独立授权捷径。
- 移除 TG 已不再使用的辅助代码和测试，改为新流程回归；停止 TG 对旧配对数据的读写，不为删除旧记录修改 SQLite 表结构或清空用户数据。新准入复用现有 Store/meta 和数据目录。Lark/QQ 仍使用的共享实现按真实调用关系保留，本版不重构其鉴权，不为 TG 留兼容分支。
- 不保留旧 TG 命令兼容层。旧事件或旧码不会自动转成新授权。

现有会话和真实记录必须保留。首次上线的 TG 设置页列出当前 Bot 的已有外部空间，标记“尚未授权”，提供单条“允许此私聊/群”的操作；身份来自已有平台绑定和记录，不从标题解析。群需同时确认允许成员，私聊需能验证原数字身份；缺失或歧义时要求重新申请。策略缺失按未授权处理，不自动继承旧配对授权。

部署前保留备份和 SSH 恢复路径，升级后使用当前凭据重新登录管理员网页完成核对；不假定重启前 Cookie 仍然有效。同步更新 GUI 文案、CLI 帮助、README 与 TG 使用说明中的旧配对命令。启动新版本无需建设旧版本兼容或数据迁移层。

### 2.5 准入与撤权的执行边界

- 同一准入判断覆盖消息、斜杠命令、附件输入、按钮回调、后台群消息和结果回传。检查位于下载附件、写入上下文、创建 Run 之前。
- 未授权 `/start` 仅进入有界的申请处理分支，不调用模型、不创建会话、不接受配置指令；它不是通用命令绕过。普通工具/管理按钮不享有该例外。
- 被拒绝的群成员正文不进入背景上下文；只保留有界、不含正文的拒绝计数或诊断。
- 撤权前已合法收到的记录保留，不自动重写历史或已保存摘要；后续新输入与回传按最新资格检查。
- 撤权保存后立即拒绝新请求和新工具派发，旧按钮失效；按现有机制取消相关运行与后台命令，投递前再次校验资格。
- 已经发出的消息不能收回为“未发生”，已执行命令可能留下副作用。实际中断与不确定结果继续按原 receipt/UNKNOWN 规则记录，不伪造回滚。
- 运行中的模型已收到的上下文不能撤回；结果可留本地供管理员检查，但不得继续投递到被撤销的目标。
- 确定失败与 UNKNOWN 回传分开；不借撤权/恢复之机重新运行模型或工具。
- 接入管理复用 ControlService 和现有认证。公网管理员需通过现有登录、Origin 和 CSRF；TG 发起人无权批准自己或修改准入名单。FreeAgent 仍为单管理员。
- AI 可以提出准入变更；持久化改动必须由管理员在可信 UI/CLI 确认。外部渠道查看状态只返回本目标/本发起人所需字段，不暴露其他空间、人员名单与无关提案。

## 3. 有效权限与命令诊断

### 3.1 使用同一套事实输出

扩展现有状态投影，明确区分：

- 当前 Run：入口、实际发起人、冻结权限、工具定义、执行后端、网络与文件范围、冻结版本。
- 当前保存设置：全局默认、空间权限、人员上限、命令规则和工具开关；说明其对下一次 Run 的作用。
- 当前变化：权限降低、准入撤销、后端失效等会立即限制后续派发的事实。

模型的 `control_read_state`、GUI 权限详情、CLI/TG `/mode` 和诊断共享该投影，不各写一套推断。敏感路径和身份按入口脱敏；提供权限原因所需范围，不返回凭据。

同一个空间可以由 TG 用户或管理员入口发起新请求，结果权限可能不同。继续已有 Run 必须保留原发起人；管理员新发起任务与代用户续接明确区分，不能把前者包装成提升旧任务权限。

人员和空间权限继续使用现有核心。TG 页面将二者放在同一个详情中，显示“空间 Full，人员 None，最终仅聊天”。只调空间时，如仍受人员上限限制，保存后立即说明原因及可操作入口。人员权限目前跨空间生效，修改预览必须说明影响范围，不能为了某个群而静默提升此人在其他空间的能力。

### 3.2 命令 readiness 与规则

`command_ready` 不能用原始配置是否填写 execution 推断。显示工具是否启用、有效后端、后端是否可用、当前权限是否允许；针对具体命令再显示规则匹配结果。没有命令参数时不得声称所有命令都可运行或都被拒绝。

错误至少区分：工具关闭、后端不可用、权限不足、程序找不到、不安全路径、显式 deny、可执行文件白名单不匹配、需要审批、配置已改变。没有匹配规则时记录“按当前权限模式处理”，不再单独作为拒绝原因。诊断携带实际规则或默认决策与下一步建议，避免模型让用户盲目换档。

本版修正未匹配命令规则时的行为，不再因规则列表非空就形成隐式白名单：

| 条件 | 决策 |
|---|---|
| 工具关闭、None、后端不可用、路径或当前准入不允许 | 拒绝；规则不能授予这些能力。 |
| 存在匹配的显式 deny，或非空可执行文件白名单不匹配 | 拒绝，包括 Full。 |
| 存在匹配的显式 ask，且没有 deny | 沿用精确审批，包括 Full。 |
| 匹配 allow，且上述约束均通过 | 沿用现有 allow 语义；仍受实际后端、文件范围和执行边界限制。 |
| 没有匹配规则：Ask | 精确预览并批准后执行。 |
| 没有匹配规则：Workspace | 按现有策略在允许写入范围的真实沙箱中自动执行；不可用则拒绝，不回退 host。 |
| 没有匹配规则：Full | 在服务 OS 用户的 host 后端直接执行，不因缺少匹配项再次审批。 |

这一变化必须进入发行说明和升级提示。严格限制可执行程序继续使用现有非空可执行文件白名单，无需增加另一项“未匹配默认策略”。现有冻结 Run 不因升级静默扩权：仍受未匹配默认拒绝行为的未结束 Run，应在部署前处理完毕，或阻止续接并提示显式开始新请求。

Linux 专用诊断命令预设延后，本版通过 `/bin/echo`、磁盘空间检查等实际命令验证通用规则；`sh`、Python 等通用解释器不能被标成“只读命令”。参数、可执行文件解析与使用前再次验证继续生效。

Full/host 使用 FreeAgent 服务的 OS 用户，当前 Hytron 为非 root 的 `freeagent`。产品 Full 不等于 root，也不绕过 systemd 或文件权限。HTTP 工具开关、命令宿主网络、Provider/TG 传输、Web 下载分别展示。

## 4. 自动与手动上下文压缩：本版必交付

### 4.1 配置与默认行为

- 复用现有持久摘要和 `task_summary_bytes`：0 表示关闭自动压缩，1–16384 表示开启并给出摘要字节上限，不新增第二份配置真值。
- 新安装默认开启自动压缩，默认摘要上限 4096 字节。已有目录中的关闭/省略值继续解释为关闭，升级不悄悄改写；升级说明和管理员设置页给出明确启用入口。
- GUI/公网提供“自动压缩上下文”开关及摘要上限；CLI 与 AI 提案复用 `runtime.set_limits`。操作目录提供输入 schema、字段含义、0 的关闭语义和合法范围，模型可准确提出开启/关闭请求。
- 模型提出持久开关修改需用户确认。手动压缩不隐式改变自动开关，关闭自动压缩也不删除已保存摘要；配置修改只影响后续新 Run。

### 4.2 实际触发、预算与失败

- 每次模型请求组装前，按该 Run 的有效输入限额检查完整上下文；继续复用现有“加入本次输入后将超出消息数/字节限额，或已有摘要前缀失效”触发条件。通过摘要腾出空间后重新组装请求，不把超限请求先发给 Provider。本版不新增百分比阈值或后台定时扫描。
- 满足条件时自动执行有界、无工具的摘要请求，包括已获准聊天的 None 会话；不得要求提升为 Full 才能自动压缩，也不能因已开启的自动压缩反复要求确认。
- 摘要来源严格限于当前入口可见的历史：TG 只处理对应公开上下文，不能把管理员私有工具结果带入群或私聊。保留近期完整的用户/模型/工具消息组，原始历史和执行证据不删除、不拆散。
- 摘要写入按当前源记录版本原子提交；并发新消息不能被遗漏、重复覆盖或错误标成已压缩。摘要模型调用、时间和输出计入原有预算，预算耗尽就报告具体限制。
- GUI/公网显示“正在压缩上下文”和完成结果；TG 在实际耗时的压缩中最多给出一次简短进度提示，最终回答正常投递。状态读取可看到开关、最近压缩、覆盖范围及失败原因。
- 模型失败、取消、摘要过大、无有效缩减、不可分割的新消息组过大时保留原摘要和原文，给出可操作的限额/失败结果。已派发但结果不确定保持 UNKNOWN，不自动重试或循环压缩同一前缀；重启后不重放未知摘要请求。

### 4.3 手动操作与当前 Run

- 保留现有手动压缩、刷新、清除。TG 已有 `/compact`，本版修正其仅聊天权限限制：已获准接入的用户可直接压缩当前私聊；已获准的群成员可压缩该群当前共享对话的公开上下文。这是用户直接发起的维护操作，不向 None 的模型暴露文件、命令或配置修改工具。
- `/compact` 不修改自动压缩开关、权限或其他会话，不提供任意对话 ID 参数；继续遵守当前对话互斥、去重、模型并发和有限预算。没有新增可压缩内容时返回无需压缩，不产生额外模型调用；重复消息不再次执行。
- `context_manage inspect` 区分 UI 外部维护与当前 Run 内提案，返回具体阻塞 Run 和原因；当前 Run 本身不是禁止其提出压缩的理由。
- 模型主动提出 compact/refresh/clear 仍需精确确认，包括 Full；它与用户已开启后按条件自动执行的压缩明确区分。其他 pending/dispatched/unknown 调用继续拦截，不能为改善提示而绕过未知结果。
- 本节必须完成跨 TG、GUI/公网、CLI 的功能回归和实际触发验收；不能以“内核已有”或旧版测试通过代替本版交付。

## 5. 提案生命周期精简

当前 `expires_at` 混合表达确认凭据和提案有效期，造成旧 user_direct 提案长期显示 pending。改为以下规则，复用原控制日志和 Run 卡片：

- 独立 `user_direct` 提案只服务于本次直接设置操作。确定取消或确定失败后收尾；未决定的操作超过 10 分钟有效期后终结，用户重新操作才能创建新提案。读取、确认和 Owner 恢复时都校验到期，不新增后台扫描；旧确认不能通过再次渲染自动延长过期的直接提案。
- 已经提交的变更、部分应用或结果不确定的操作不能当成普通过期请求丢弃，继续按实际记录恢复和报告。
- 模型提出的提案依附现有 Run 等待确认或取消；确认凭据过期不等于 Run 永久失效，用户重新查看原卡片时由后端验证当前资源版本和内容后获取新凭据。旧 Owner、旧会话或旧卡片不能应用变更。
- 返回给模型只保留提案状态、关联 Run、动作结果和恢复说明，不输出确认码、确认凭据的有效期，也不暴露其他对话的无关提案。UI/CLI 使用现有卡片或提示进行确认。
- 模型提案的拒绝、资源失效或任务取消必须同时收束对应 Attempt 与 Run，不能只改控制日志留下永久 waiting_confirmation。
- 不新增独立待处理控制面板或第二套确认状态。TG 接入申请列表属于第 2 节的渠道功能；本节设置提案在原 Run 卡片和已有 CLI 控制入口处理。需要保留的历史在既有控制记录中查看。

## 6. 文件交付与任务结束

- 用户确认的交付规则：提供可下载的附件即可，模型无需输出哈希值。回复简要说明文件内容并给出附件；只有文件路径或“已生成”的文字不算交付完成。
- `file_export` 的结果准确表示“下载快照已生成”。GUI/公网说明下载卡片已可用；TG 说明“附件将在本轮回答结束或达到限额时投递，无需重复导出或轮询等待”。该提示描述安排，不伪报已经发出；最终投递状态来自回执，不使用容易被当成最终失败的裸 `delivered=false`。
- GUI/公网显示认证下载卡片；TG 返回平台文件。HTTP 抓取工具关闭不影响这两条交付路径，不生成匿名公共下载 URL。
- 通过已有附件与投递记录查询 `pending/sent/failed/unknown`；仅在用户要求核查或已有失败时读取这些记录，不让模型在正在生成回答的同一 Run 中轮询尚待结束后投递的附件。
- 附件卡片显示文件名、大小和下载入口。哈希用于内部完整性校验，不作为模型回复或用户交付的必填内容；不为展示哈希额外调用工具，不把哈希或下载 ID 写回原文件再导出。
- 同一 Run、同一授权源文件的多次导出，在明确尚未开始渠道发送时只选最终成功版本投递；相同内容复用已有快照，不同内容生成新的不可变快照并替换待投递选择。按规范化源文件标识区分，不按文件名合并不同目录的文件。用户明确要求交付多个版本时保留这些选择。
- 旧快照、附件 ID 和执行 receipt 不被改写或删除；新导出失败时保留上一个成功选择。进入 dispatching/sent/unknown 的版本冻结，不能被静默替换、收回或自动重发；重启和并发投递下沿用同一判断。使用现有附件元数据和发送记录表达选择，不新增文件交付平台。
- 普通步骤/时间/输出限额触发时，如所有派发均已确定收束、没有待审批/未知调用或仍在运行的后台命令，就结算本轮并投递已有附件，保留 limited 原因与累计用量，不把未完成目标标成 completed。普通限额不要求用户先点击“结束”。
- 用户随后明确发送“继续”时，才为剩余工作开始下一轮；沿用同一对话和已确认结果，保留上一轮原发起人与当前权限约束，不把完成工具重新排队，也不在模型输出“继续”时自启动。新 Run 有自己的有限预算，上一轮用量不清零、不自动增加；同一请求重传不得创建多个后继 Run。复用现有 request key 和元数据建立关联。
- 仅在上一轮符合确定收束条件且目标唯一时，将用户整条“继续”、`/continue` 或对应按钮识别为下一轮入口。创建下一轮前复用现有终结路径释放上一轮占用，保留限额原因和原始消费；收尾、关联和新建需具备事务性或已有请求去重下的可恢复性，不留下永久占位，也不能误记为用户放弃未知作用。协作子任务不能借此脱离父任务累计预算。
- 如果限额时仍有 pending/dispatched/unknown、待确认或后台命令，先通过既有证据检查、停止或确认路径处理；禁止借“开始新一轮”绕过。保留用于这些真实未决状态的已有恢复操作，不增加新的暂停状态或通用结束按钮。
- 12 步默认暂不调整，先验证完成一份文件时不会因哈希回写、重复导出和投递轮询耗尽预算。

## 7. 实施顺序与交付范围

建议仍以一个 v7.12 版本交付，分四个可独立验收的阶段：

3. 替换 TG 通用配对码，完成带申请码的身份申请、管理员批准、统一名单、撤权、已有空间重新授权与 GUI/CLI/AI 接口。
4. 完成最终附件选择、准确投递反馈、普通限额结算与明确继续；做 Hytron 集成验收、便携包和发布记录。
