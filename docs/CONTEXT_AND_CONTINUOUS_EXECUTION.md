# v7.13 连续执行、上下文和对话接续

## 当前对话的上下文结构

以下为 v7.13.0-dev.2 的现有代码行为。经验总结扩展和新版“固定上下文”入口属于
[后续计划](FREEAGENT_NEXT_CORE_SETTINGS_RECOVERY_POSTGRESQL_PLAN_2026-11-05.md)，尚未实现。

一个对话持久保存完整消息和相关执行记录；每次模型调用另外组装一份有界请求。
网页可见的聊天记录、数据库中全部记录和本次发送给模型的内容不是同一个集合。

| 组成 | 现有来源与行为 |
| --- | --- |
| 运行规则和配置指令 | core 执行规则、`system_prompt`、明确选中的 `instructions/` 文件；必要时附带未决操作提示 |
| 已压缩的历史摘要 | 存在有效摘要时，以一条带来源说明的上下文消息加入，代表被覆盖的旧历史；原消息保留 |
| 显式选择的 Memory | 本对话选中的有效条目及范围说明；保存过的全部 Memory 不会自动加入，没有自动 RAG |
| 尚未被摘要覆盖的历史 | 按顺序包含用户/模型消息、完整工具调用与结果组，也包含本次输入及当前 Run 已产生的结果 |
| 本次选择的 Skills / 扩展 | 自动型 Skill 先给名称/描述索引，正文按需 `skill_load`；手动调用的 Skill 正文和获准扩展块加入指定位置 |
| 附件 | 选中且可访问的文本加入所属用户消息；受支持图片作为图像内容发送；大图/历史图的省略有明确标记 |
| 工具定义与输出预留 | 工具名称/参数 schema 是请求的独立字段；最大输出 token 及安全预留参与窗口核算，不是一段聊天正文 |

普通本机请求的基础消息顺序是：system → 可选历史摘要 → 显式 Memory → 未压缩历史。
当前用户输入原本就在历史尾部，随后可继续出现工具调用/结果和已采用的引导，不额外重复一份。
Skill/扩展是按权限与位置插入：手动 Skill 和本轮 tail 扩展位于最后一条用户消息之前，
已授权的 system 扩展紧随首个 system；每步 tail 扩展在派发前追加。附件最终展开后再核算。

排队但尚未采用的消息标记为 Deferred，不进入本轮模型请求，也不进入压缩源；点击引导
并被实际采用后，才作为当前 Run 的真实用户输入参与后续请求。

摘要、显式 Memory 和 Skill 的作用不同：摘要保存本对话进度，Memory 只带入明确选择
的参考内容，Skill 保存按需使用的方法。上下文压缩处理历史，不把整个请求的 system、
工具定义、Memory 或附件一并任意改写，也不把摘要自动变成长期经验。

**入口差异**：None 不提供工具，并跳过本机私有 Memory、Skill 和扩展；TG/Lark/QQ
无论工具权限如何，均跳过这些私有上下文，使用渠道规则、公开消息/确认回传和范围匹配
的摘要。获准工具仍可用于外部渠道当前 Run，其当前执行组按权限进入请求。
TG 不携带本机 `system_prompt` 或指令文件。公网 Web 的行为还取决于当前有效权限，
不能简单把“公网访问”和上述渠道公开上下文模式等同。

以上入口差异是当前实现限制。后续目标是 core 统一处理上下文，渠道只传递消息：
同一会话、身份授权和能力选择使用同一套 Memory/Skill/固定内容规则，内容可见性仍由
core 统一检查。不会另外建设 TG 固定经验系统，当前也尚未完成这项入口统一。

2026-11-05 修订计划将固定内容与入口统一安排在 v7.15，固定复用 Memory 属性、范围和
版本。Owner 私聊沿用其已有授权，群聊和其他人的空间仅默认使用本空间内容；GUI/Web
接续渠道会话也沿用该空间范围并回传原空间。经验总结以可选 Skill 加按钮交付，输入
与保存产物由 Core 通用流程检查密钥，确认后才能发布；这些均为后续能力，尚未实现。

v8.0 计划把运行状态和现有显式 Memory/知识能力统一改用 PG，具体约束见
[数据设计指南](FREEAGENT_PG_DATA_DESIGN_GUIDE_2026-11-06.md)。这不改变当前 v7.x 的
SQLite 实现，也不自动启用大型共享知识库；优先保证单 Core 的上下文、接续与恢复体验。

主要实现位置：`internal/harness/service.go` 的 `buildContextWithSummary`，
`context.go` 的能力装配，`context_prepare.go` 的附件/扩展后预算检查，
`context_summary.go` 的历史范围，`memory_context.go`、`skills.go` 和 `attachment_context.go`。

## 连续执行

普通任务没有总步数或累计执行秒数上限。步数与活动耗时仍保存在原 Run 中，
用于观察和排障。任务会在完成、用户停止、等待确认、明确失败或 UNKNOWN 时停下。
Provider、HTTP、单次命令以及可选协作子任务保留各自的超时或显式预算。
停止不撤销文件、命令或外部操作；UNKNOWN 必须核对，禁止自动重放。

后续 v7.14 的恢复规则以主计划为准：纯模型请求允许有界重试，额度不足不重试；工具
结果未知时当前 Run 进入只读核查，Full 也不能绕过。模型的“已发生”处置须绑定原
Attempt/参数/目标及 receipt 或核查结果，且原执行已终止、相关未决效果核清、权限有效，
才恢复工具；部分完成、旧执行存活、“未发生”或无法判断时暂停，由用户处理。结论
单独保存、原 UNKNOWN 不改，其他未决调用继续阻塞。MCP 复用显式只读信任及工具声明，
缺省/导入不授予信任；核查最多 2 轮，重启不重置。这些不是当前 v7.13 已支持的行为。

## 上下文窗口与压缩

对话顶部“上下文”提供同一核心查询，包括下一轮模型窗口、最近准备的请求、
估算的输入 tokens、序列化字节数、输出预留、分项占用和上次 Provider 实际用量。
最近准备的请求不包括之后产生的回复或尚未采用的输入，出现更新时会明确标注。
查询不会调用模型或执行扩展。

模型窗口只能根据可靠的服务商声明填写；模型列表只有名字不能推断容量。
点击“设置当前模型窗口”填写总 tokens，未知填 0。CLI 对应：

```text
freeagent config model --data-dir <data> --id <id> --provider openai-compatible --key <key-profile-id> --model <provider-model> --context-tokens 131072 --context-source manual --output-tokens 4096
```

这里的 `131072` 只是填写格式示例，不代表任何模型的实际能力。
模型配置操作会更新所给的 profile，请同时保留其原有协议、工具与其他能力声明。
AI 可通过已存在的 `model.set_profile` 提案修改能力，须由用户确认。

没有 token 声明时，以本地字节预算保守检查，并明确标记窗口未知。
本地 token 数是估算；Provider 实际返回的 usage 单独显示，不能当作总窗口。
固定提示、工具定义、扩展、历史、摘要、当前输入和附件都在派发前核算。
预算重算复用本次扩展与附件材料，不重复运行 hook。

自动压缩默认在可用输入预算的 80% 触发，覆盖已完成历史并保留最新输入与完整
工具组。输出预留已经从可用预算扣除。内部期望留出约 40% 余量；必须保留的
材料较大时可能达不到这个目标，最终请求仍必须能容纳。不会截断当前用户要求。

- 设置页：自动开关、摘要字节上限、50–95% 的触发占比。
- CLI：`config context --data-dir <data> --summary-bytes 4096 --auto-percent 80`。
- AI 提案：`runtime.set_limits` 的 `task_summary_bytes`、`auto_compact_percent`。
- 手动：GUI“压缩上下文”、CLI `/compact` 或 `context compact --session <id>`、TG `/compact`。

`task_summary_bytes=0` 关闭自动压缩，手动操作仍可用。原始消息和旧摘要在失败时
保留；摘要不是执行证据。已完成的大工具正文以不具执行能力的数据分块处理。
所有源分块共享一次空/超长摘要内容修复；429 等瞬时错误仍使用既有模型恢复与
Retry-After，两者分别计数。思考/输出额度耗尽且正文为空时，不按相同配置自动重发。
Provider 明确拒绝上下文且未生成任何内容或工具时，
最多压缩后重试一次，原失败 Attempt 仍保留；UNKNOWN、认证错误和限流不走此路径。
存在待确认、运行中的调用或 UNKNOWN 时，手动压缩会说明阻塞对象。

预防性压缩明确失败后，若重读插话、权限和摘要后的请求仍在硬预算内，本轮可沿用
原上下文继续。思考/输出额度导致的空摘要会在同会话、同有效配置下暂停后续预防性
压缩，只提示一次；界面/CLI 可查看暂停原因。相关压缩配置变化或手动压缩成功后恢复。
硬预算仍逐次检查，达到时明确停止；取消、配置变化、存储错误和摘要提交 UNKNOWN
不适用普通降级，不会因此重放工具或删除历史。

## 插话和 FIFO 队列

引导属于指定的当前 Run；排队属于后续新 Run。GUI/CLI 运行中发送普通文字，
默认进入待发列表。本轮完成后按顺序发送；GUI 每条待发消息旁的“引导当前任务”
可将同一条消息改为补充本轮要求，CLI 输入 `/guide` 选择首条，或 `/guide 2` 指定待发序号。
操作沿用原消息和请求标识，与取消和队列消费在同一事务边界竞争，不取消后重发。
目标已结束时保留待发项；已经发送或取消的消息不能被改回待发状态。
待发列表提供取消、暂停和恢复。每个对话最多
20 条待采用输入；接收后正文和请求标识持久保存，排队项不提前占一个 Run。

交互式 CLI 在真实终端里运行时，也能在生成过程中继续输入：普通文字先排队。
接收提示给出对应的 `/guide` 命令；`/steer <文本>` 可直接补充当前任务。
重定向脚本输入沿用顺序执行，以免把后续脚本控制命令误作插话。

| 操作 | CLI |
| --- | --- |
| 将待发消息用于本轮 | `/guide [待发序号或key]`；省略时采用首条 |
| 直接引导 | `/steer <文本>` |
| 排队 | `/queue <文本>` |
| 查看 | `/inputs` 或不带正文的 `/queue` |
| 取消未采用输入 | `/queue-cancel <输入key>` |
| 暂停 / 恢复 | `/queue-pause` / `/queue-resume` |
| 停止当前任务 | CLI `/stop`；TG `/stop`；GUI“停止任务” |

已派发的工具先保留实际结果。尚未派发且被插话替代的调用记为 NOT_RUN，并补齐
工具协议。插话不能批准旧参数，也不能越过 UNKNOWN。若指定 Run 已结束，输入
标记 `target_ended` 保留，不悄悄开始另一个任务。

仅当前任务正常结束后自动推进队列；停止、失败、待确认或 UNKNOWN 会暂停。
Owner 重启时保留采用关联，已关联的输入不会重新创建任务。因重启而停止的
Run 须明确处理后恢复队列。模型配置、准入或权限变化会阻止原条目派发，不能
通过重新排队扩大原授权。排队要求选定明确模型；Auto 用户需先选一个 profile。
接受的附件保留其已提交引用，显式删除附件仍会阻止后续派发。

TG 使用直接插话：同一发起人在运行中发送普通消息，作为本轮补充，不提供排队。
`/inputs` 查看已收到的补充，`/stop` 停止当前任务。Bot 只接收已获准、确实唤醒它
的输入；群背景文字不会触发执行，其他群成员不能接管当前 Run，需要等本轮结束
再发起新请求。Lark/QQ 未扩展真实平台验收。

## 工具过程与耗时

现有“运行活动”显示工具状态、目标、耗时和结果详情；模型延迟与 token usage
单独显示。执行中计时在客户端计算，不逐秒写库。没有可靠时间的旧记录显示
“耗时未记录”。等待确认与未派发不是执行耗时；取消和超时标志不证明没有副作用。
每轮快照只投影最近 128 个 Attempt，原始 Inspect 和按需详情仍保留完整记录。

## 从消息建立分支

用户消息旁“从这里重新执行”复制该消息之前的前缀，并以原文或修改后文本作为
新请求；模型已完成回复旁“从此回复继续”复制包含该回复的前缀。来源保留，文件
和外部副作用不回滚，旧工具也不会因为复制历史而重新运行。

CLI `/history` 显示消息 ID，随后使用 `/branch <消息ID> [替换文本]` 或
`/branch-reply <消息ID> [下一条要求]`。TG 对应 `/history`、`/branch`、
`/branch-reply`；外部空间须先显式 `/multi on`，且组织操作需要足够权限。

原摘要不复制，避免带入分支点之后的信息。附件在新会话重新绑定独立的不可变
副本，并检查配额和来源访问权。来源有活跃工作或 UNKNOWN 时不能执行新分支。
AI 可用 `conversation.branch` 提案，经确认只创建分支草稿，不自动执行。

## 当前 v7.12 数据副本升级检查

本版不提供旧平台兼容或自动迁移层，也不改写旧 Run 快照。升级前先处理当前
活跃/待确认任务、备份并验证恢复副本，再停止旧 Owner。

仅在准备交给 v7.13 的 `config.json` 副本中，删除普通任务的 `max_steps`、
`max_run_seconds`，把历史读取参数 `max_messages` 改名为 `history_page_size`，
设置 `auto_compact_percent`（默认 80）。这是本次明确的管理员配置编辑，不会
自动调整冻结 Run。用新程序执行 `config show`、`doctor` 并核对历史、摘要和附件。
旧未完成 Run 无法继续时，核对实际效果后明确放弃，再发送新请求。
切换失败时恢复原程序和原备份，禁止让两个 Owner 同时打开同一数据目录。
