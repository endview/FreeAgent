# FreeAgent 外部渠道与对话空间：两轮讨论整理

日期：2026-10-26。本文压缩整理指定范围内的用户需求与助手建议，尚未实施。
范围从“那，后续需要可以接入telegram,lark,qq”开始，到文末所引原回复结束。

## 第一轮：外部渠道接入

**用户需求**：FreeAgent 后续需要接入 Telegram、Lark 和 QQ。

**助手建议**：作为可选渠道连接器接入，共用现有 Owner、attach 接口和执行核心。

| 渠道 | 首期能力 |
|---|---|
| Telegram | 文字对话、流式回复、按钮确认、任务状态、停止 |
| Lark/飞书 | 机器人消息、交互卡片、审批确认 |
| QQ | 使用官方机器人开放平台，适配消息与确认入口 |

连接器只负责身份识别、消息收发、状态展示和确认传递；文件、命令、设置、权限和审批由现有核心处理。
按平台账号、会话和消息 ID 绑定与去重，处理重连和消息顺序。
远程接入使用配对或白名单、相应平台的鉴权校验及限流；Owner 未运行时不自动启动，断线不自动重放旧请求。

当时建议的版本顺序：v7.5 接入 Telegram，v7.5.1 接入 Lark，v7.6 接入 QQ；
附件、图片、文件回传和跨渠道会话查看后续补充。版本安排属于建议，尚未作为实施承诺。

## 第二轮：用户空间与多对话

**用户需求**：

- 用户 A 首次与 Bot 对话时，创建 A 的空间，空间可以容纳多个对话。
- 默认使用第一个对话。只有一个对话时持续复用，多对话功能默认关闭，需用户开启后再使用。
- 开启后可以调出对话列表并切换。
- 在 GUI 或 CLI 打开时，该空间对应对话的归类文件夹。

**助手建议**：命名为 `Conversation Space`，区分现有文件执行目录 `Workspace`。
空间负责归类、外部身份绑定和默认会话；Workspace 继续决定文件、命令和沙箱的执行范围。
归类文件夹是逻辑分组，独立物理目录留待实际需要时显式配置。

建议的最小结构：

```text
Space: id, title, source, external_identity,
       default_conversation_id, active_conversation_id,
       multi_conversation_enabled, created_at, updated_at
Conversation: 现有字段 + space_id
```

外部身份使用平台和 Bot/应用范围内的稳定账号、聊天标识，避免使用显示名造成混淆；
不同用户、Bot 或聊天场景不能错误共用空间。

首次创建空间时同时创建默认对话，默认项和当前项均指向它。
单对话阶段保持简单界面；开启多对话后提供新建、列表、切换和设置默认项。
原建议还包括：删除当前对话后切换到可用的默认对话，否则选择最近的可用对话。

| 入口 | 空间和对话操作 |
|---|---|
| GUI | 空间显示为归类文件夹，多对话时展开其中的会话 |
| CLI | `/spaces`、`/space`、`/sessions`、`/new`、`/use`，具体命令待实现确定 |
| Telegram / Lark / QQ | 消息命令、按钮或卡片调用同一套操作 |

处理流程：渠道消息 → 身份绑定 → 找到或创建空间 → 选定对话 → Owner / TaskService → 返回回复、审批和状态。
本地与渠道接续使用同一空间 ID 和对话 ID，避免重复创建记录；外部用户只能访问其已授权绑定的空间。
执行权限、审批、UNKNOWN 和 Owner 生命周期继续复用现有机制。

实施顺序：先完成空间归属及 GUI/CLI 展示，再依次接入 Telegram、Lark、QQ。

> 这样做以后，Telegram、Lark、QQ 都只是不同的消息入口，FreeAgent 的对话、权限和执行核心保持一套。
