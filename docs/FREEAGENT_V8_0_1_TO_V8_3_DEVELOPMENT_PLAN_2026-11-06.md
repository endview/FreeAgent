# FreeAgent v8.0.1—v8.3 后续版本实施计划

日期：2026-11-06（Asia/Shanghai）。状态：计划已编写，产品开发未开始。

本文件是 v8.0 之后的统一实施入口，整合前端框架评估、核心优化、AffectWeave 成品要求和经验总结安排。版本范围与实施顺序以本文件为准；专项设计继续引用配套文档。计划日期不等于发布日期，各版通过实际验收后发布。

## 1. 产品目标和当前基线

近期目标是一个日常使用顺畅、长期执行可靠、能按需扩展的单 Core Harness。

当前已交付 v8.0.0-dev.1：唯一 PostgreSQL Store、可选渠道进程、执行恢复、固定 Memory、统一设置及 Windows/Linux 便携包。Windows 和 Debian 12 全量/竞态、真实 DeepSeek、备份恢复等已有验收记录。Hytron 已更新，用户已确认 TG 私聊模型回复与公网原密码登录，服务端记录核对通过。

前端当前仍为 Vite + 原生 JavaScript。React/TypeScript/Tailwind/shadcn/Radix 的隔离小样已通过类型检查、生产构建和 12 项浏览器检查；这不代表产品迁移完成。AffectWeave 目前只完成外部源码与契约核查，尚未接入或运行其测试。

仍未验收的环境和场景包括：干净 Windows VM、管理员令牌启动、Windows 实际磁盘满、长时间持续负载、当前版本其他 Provider/Responses/搜索真实矩阵，以及 TG 多账号/群/回调/附件。Lark/QQ 继续按用户要求后测。

## 2. 全程约束

1. Core 继续负责会话、上下文、能力选择、模型/工具、权限、审批、输入采用、恢复和真实执行记录。GUI、CLI、Web 和渠道使用同一核心。
2. 渠道负责平台连接、来源身份与传输。默认一 Bot 一 Core；显式配置可让多个 Bot 接入一个 Core。
3. AffectWeave 和经验总结均为可选能力。未启用时无相关进程、分析请求和后台扫描；普通 Core 不依赖它们。
4. 产品只使用 PostgreSQL。保留当前 `Harness-pg-v1` 的原生数据连续性；不恢复 SQLite 后端、旧平台兼容或旧历史导入工具，也不每次发布都清库。
5. 模型提出的持久设置、角色/关系/Memory/Skill 修改绑定具体内容、范围和版本确认。实际执行/交付记录可以由运行时正常落库。文件、命令等操作继续走既有权限和工具审批，不能把 Full 模式改成所有工具都要控制面确认。
6. 普通任务继续没有累计总步数/总时长截断；单次调用、后台命令、子任务和显式授权的扩展调用保留各自边界。取消、等待确认和 UNKNOWN 的事实语义不变。
7. 保留原 UNKNOWN；不自动重放不确定副作用。只读核查、模型替代 Attempt 和渠道回执补齐分别处理。
8. 复用 Conversation、Run、Attempt、消息和 receipt；不增加独立 Task/Step/Evidence/Checkpoint 平台，不预建全局事件总线、插件市场或分布式调度。
9. 全局产品设置集中管理，并提供同一 Core 的 CLI/AI 操作；会话能力和选择在输入区。所有可调项都列出对话操作入口。纯界面布局偏好明确客户端归属，不伪装成执行权限；没有相应客户端时不能虚报已应用。
10. 发布提供可下载归档和使用说明；用户回复中无需列哈希。内部完整性校验和发行清单继续保留。

实现以这一个 Core 和本版实际流程为边界。优先补字段、校验、有限查询与测试；只有复现的缺口才引入新机制。接口“通用”指复用现有契约，不要求先交付通用回放、同步、备份协调或协议生成平台。

诊断复用既有 doctor、运行记录和日志，不增加长期驻留的遥测服务。默认本地导出，由用户决定是否分享；所有记录均应先脱敏。

v8.0.1 新增的诊断导出和更新前检查，优先通过 CLI 与 Core 接口提供。旧界面只加入必要的最少入口，完整界面在 v8.1 实现，避免同一功能做两遍。

### 4.2 持续负载和发布条件

至少执行一轮 8 小时隔离混合负载：聊天、工具、人工审批模拟、连接重建、短暂 Provider 故障和备份；以可控 Provider 为主，真实 Provider 样本单列。检查未完成任务、重复副作用、连接泄漏、孤儿进程和内存趋势。

退出条件：

- 没有未解决的数据损坏、错误授权或重复副作用问题。
- 启动失败能归因，失败不留下“初始化成功”的配置或无主 PG。
- 已有 Windows/Debian 相关回归通过；新增排障流程可重复运行。
- 干净环境/管理员/磁盘满/持续负载实际执行情况逐项记录。缺条件时可以发布有明确范围的开发候选，不把它标成完整稳定环境验收。
- GitHub 发布说明与包内容、源码版本一致；实际推送/Release 以独立操作结果为准。

## 5. v8.1：FreeAgent 前端框架与完整界面

### 5.1 技术基线

采用 **React + TypeScript + Vite + Tailwind CSS 4 + shadcn/ui（Radix Primitives）**，继续输出 Go 随包静态资源，用户运行时不需要 Node。

| 事项 | 规则 |
| --- | --- |
| 版本 | React 主版本固定。F2 在 Vite 8 及配套 React 插件下验证构建、CSP 和可重复构建，通过即采用；不通过则固定 Vite 7 与兼容插件，并记录原因和升级条件 |
| shadcn/ui | 固定 CLI 版本并提交 `components.json`；按需引入组件，保留来源、许可证和本项目修改记录；基础交互控件统一使用 Radix |
| 路由 | 使用根路径加查询参数的小型路由，不引入 React Router；改用 pathname 路由时须连同 Go fallback 一起实现 |
| 状态 | F2 在自建小型 store（`useSyncExternalStore`）和 Zustand 中二选一；不叠加 TanStack Query 等第二套缓存 |
| 表单与组件展示 | 设置表单先不引入表单库；不使用 Storybook，改用开发构建专用的状态页（见 5.5） |
| 新增依赖 | 运行时依赖须说明用途、体积和许可证，并在生产 CSP 下通过检查 |
| Tailwind | 明确扫描 `src`，不依赖对整个仓库的自动扫描 |

产品使用 FreeAgent 自己的 token、组件和视觉规范。unslop 用于真实画面的分层审阅，参考来源为 Damir Sokolovsky 的 [unslop](https://github.com/heydamir/unslop)，不作为运行时依赖。

已有 [框架评估](FREEAGENT_V8_1_UI_FRAMEWORK_EVALUATION_2026-11-06.md) 的 Vite 7 小样是历史可行性证据，不替代 F2 的 Vite 8 验证。

### 5.2 设计系统

视觉方向在 F1 用可交互样例确定，**经用户确认后再冻结 token**；确认前不大规模铺开页面。此次计划修订不等于用户已经确认未来样例的视觉方向。

| 方面 | 规则 |
| --- | --- |
| 中文排版 | 使用系统字体栈（PingFang SC、Microsoft YaHei UI 等），不打包中文字体；阅读区正文约 15px、行高约 1.7；中文不使用负字距（如 `tracking-tight`）；长路径、URL、哈希可断行；页面设置 `lang="zh-CN"` |
| 语义状态 | 定义运行中、排队、等待确认、UNKNOWN、失败、取消、完成的 token；同时用颜色、图标和文字表达，UNKNOWN 与失败明显区分 |
| 风险与变更 | 定义读、写、命令、网络四类风险标识和 diff 增删颜色；标识不替代 Core 的具体风险与审批判断，Full 模式在输入区持续可见 |
| token 约束 | lint 禁止组件直接使用调色板颜色（如 `bg-red-500`）；禁止 `dangerouslySetInnerHTML`，经审阅的 Markdown 渲染组件除外 |
| 外壳与滚动 | 应用外壳自建，不采用 shadcn Sidebar，以统一管理状态、可拖拽宽度和恢复；消息区使用原生滚动容器；Radix ScrollArea 只用于弹层内的短列表 |
| 拖拽尺寸 | 侧栏宽度、阅读宽度、输入区高度按像素设计并设上下限；核实 react-resizable-panels 能否按像素约束，不能则自写分隔条；分隔条支持键盘调整和双击恢复默认 |
| 输入区高度 | 输入框随内容自动增高，拖拽设定的是最大高度 |
| 焦点 | 运行中出现的审批卡片不抢输入框焦点，也不放入模态 Dialog；模态只用于用户主动发起的危险操作；焦点样式补 outline，保证 Windows 高对比度模式下可见 |
| 窄屏 | 侧栏改为抽屉；设置改为“列表 → 详情”；手机上输入框字号不小于 16px；处理 `dvh`、`visualViewport` 和安全区；触控目标不小于 44px |
| 主题 | 浅色、深色、跟随系统；首屏不闪现错误主题；桌面版深色时原生标题栏同步变深 |

长正文中的路径可断行；代码块、表格和公式保留局部滚动及原文复制。模态限制针对业务审批/危险操作；窄屏抽屉仍按导航组件的焦点和背景交互规则实现。

### 5.3 页面和功能范围

| 区域 | v8.1 交付 |
| --- | --- |
| 对话主界面 | 空间/会话导航、阅读区、输入器；当前执行详情按需展开，保持回答为主 |
| 会话与历史 | 置顶、分组、服务端分页、搜索、完整轮次分页、从消息重新开始；不能因列表上限让旧会话不可发现。分组即空间：GUI/CLI 中显示为会话归类文件夹，列表内再按置顶和时间分段，不新增独立分组对象 |

| 上下文与后台命令 | 上下文窗口占用、自动/手动压缩状态；后台命令会话的状态、输出和停止（按现有入口迁移） |

| 能力管理 | 内置工具、MCP、Skill、扩展；启用后显示配置和状态，输入区保留会话选择；为扩展详情页预留位置（见 5.6） |

| 首次启动与空状态 | 未配置 Provider、尚无会话时的引导 |
| 全局状态与提示 | Owner 断开/重连、PG 不可用、版本更新后提示刷新；普通提示 2 秒后自动收起 |
| 布局和主题 | 侧栏宽度、阅读宽度、输入器最大高度可调整；键盘替代、恢复默认、深浅主题和窄窗口 |

全部已有功能建立“当前入口 → 新组件/页面 → 验收用例”映射。映射清单从旧界面实际调用的接口和处理的事件类型整理而来。不得为了界面完成度隐藏未迁移的核心功能，也不靠长期保留两套正式前端交付。可选项中的“增强提示”不降级已经存在的标题/关注提示；需要用户处理的错误与审批不因普通提示到时而消失。

同时建立“可调字段 → 保存位置/作用范围 → GUI → CLI/AI 操作 → 生效时机”清单，并以 Core 控制面的可调项清单做覆盖检查：新增可调项没有界面映射时测试失败。现有 `/api/control/catalog` 可枚举操作；F2 核实字段级覆盖是否足够，必要时补最小字段映射，不另建设置平台。AI 提出的持久修改继续确认；只在当前客户端生效的视图操作明确显示目标客户端，不向其他窗口广播。

### 5.4 数据流和状态规则

| 方面 | 规则 |
| --- | --- |
| 权威来源 | 以 Core 快照为准，事件流只表示进展；React 不自行裁决审批或运行成功。只有用户自己输入的消息可以先行显示（带临时 ID 和原请求键），审批和运行状态不做乐观更新；回执按请求键合并，避免双份消息 |
| 快照与事件 | 复用现有 `generation/seq`，序号在同一 Owner 代次内单调；快照加载期间有界缓存事件，重复事件幂等。跳号、换代、缓冲溢出或游标过期时默认重新读取授权快照，确有必要才用现成的有限事件补读，不新建持久事件库或回放协议。F2 核实快照覆盖水位及过滤语义，不能把查询结束时的最大序号直接视为快照已覆盖；有缺口只补必要字段/响应 |
| 本地与公网接口 | F2 列明两入口的路由/字段范围；复用现有 `/api/chats`、`/api/events` 等受限查询及服务端投影，缺字段优先补现有响应。公网继续拒绝 `/api/attach/*`，不为统一前端放开本地管理接口或建立第二套公网执行核心 |
| 连接生命周期 | 一个页面实例只保持一条全局事件流；切换会话不重连；StrictMode、切页和组件卸载不导致重复连接或重复发送。核实刷新、开发热更新和睡眠唤醒期间 Owner 的在线判定宽限，不能误判最后一个客户端已离开；已被正常回收时能明确重新连接或启动，不谎称无限存活 |
| 渲染批处理 | 流式更新按帧合并；浏览器后台标签页暂停 `requestAnimationFrame` 时，用有界定时器兜底。定时器也可能被节流，恢复前台或唤醒后重新校对快照，不依赖后台计时器保证任务存活 |
| 事件类型 | 实际发送入口使用一份轻量事件常量清单，覆盖 Harness 事件和必要传输控制帧；用覆盖测试核对前端每种类型的处理、刷新或明确忽略策略。JSON 样本只负责字段校验，不能单靠样本证明穷举。清单新增而前端遗漏时测试失败；运行时未知版本类型保留诊断并提示刷新。不建设全量 Go/TS 协议生成框架 |
| 草稿与秘密 | 草稿保存在组件外的 store，按表单/会话区分；注意 Radix Tabs 默认卸载非当前页，Dialog 关闭时也会卸载内容。会话滚动位置按会话保存。Provider 草稿在切页和失焦后保留；秘密只存专用内存。界面偏好、输入草稿和请求幂等键分别管理 |
| 客户端存储 | localStorage 按来源隔离，端口也算在内。F2 核实桌面端口回退和 WebView2 数据目录，按真实连续性缺口选择稳定来源或补最小的受限客户端偏好/获准草稿字段，不预建跨设备同步服务。绑定实例、身份、具体设备/客户端与会话，不能只按“桌面/Web”类型合并。Provider Key/token 不进入该存储；公网主动退出登录清除该身份草稿 |
| 消息模型 | F2 根据现有“从消息重新开始”的记录方式，确定分支如何显示（在原位置切换版本，或分叉为新会话），并据此确定前端数据结构，不凭 UI 假设改写历史语义 |
| 认证和路由 | 本地启动 capability 在 React 挂载前一次性读取，并从地址栏清除；公网保留 Cookie/CSRF；使用查询参数路由 |
| 安全渲染 | 保持原有 Markdown、公式、链接规则和原文复制；只有经审阅的 Markdown 渲染组件可以插入 HTML；每条消息有独立错误边界，单条消息出错不影响整页 |
| 流式渲染 | 只更新当前消息；已完成段落和正在生成的尾部分开处理；未闭合的代码块和公式先按纯文本显示，闭合后再高亮或排版；KaTeX 和代码高亮按需加载 |
| 长列表 | 会话列表使用虚拟列表；消息区使用分页加 `content-visibility: auto`，不支持时回退普通布局。v8.1 不做消息区虚拟化，以保留已加载消息的 Ctrl+F、跨消息选中复制和滚动锚点；尚未加载的历史不冒称已被浏览器查找覆盖 |
| 版本更新 | 仅带内容哈希的公开静态资源长期缓存，`index.html`、API、认证、草稿和私有附件不缓存；处理 `vite:preloadError`，通过连接/快照版本提示刷新。存在未保存秘密草稿时不自动刷新，提示先正常保存或明确放弃并重新输入；用户也可暂不刷新。非秘密草稿按既有持久规则恢复，不为保留 Key 新建秘密草稿库。核对旧 chunk 失效处理，不循环刷新或重发请求 |
| 多标签页 | 实测本地多个标签页及各自 SSE；HTTP/1.1 浏览器常见每源约 6 个连接的限制以实际环境为准。出现请求挂起时，在 F3 确定处理方式，并确认不影响 Owner 在线判定；不预设共享连接平台 |

### 5.5 开发环境、CSP 和状态页

- **开发模式**：Vite 开发服务器代理到 Core。F2 核实 Core 的 Origin/Host 及认证检查；现有代码已有来源检查。若需要额外支持，只能使用本机、开发构建限定的窄入口，保持身份认证；或者改用 `vite build --watch`，由开发 Core 从磁盘读取产物。发行构建中不存在任何放宽检查或任意目录挂载入口。
- **CSP**：验收以“生产构建 + Go 服务”为准，Vite 开发服务器或独立小样服务的表现不代表生产 CSP。每新增一个运行时依赖都要实测；运行时插入 `<style>` 的库（如 Sonner 提示组件）重点检查，不因此放宽生产策略。
- **新旧对照**：从 F3 开始，开发构建中的新界面可以和旧界面同时连接同一个隔离测试 Core，对照同一会话的状态和操作结果。使用不同客户端标识；对照以同一权威状态为准，不把一个操作自动重放到另一界面。
- **状态页**：开发构建提供 `?view=gallery`，用来自真实契约的合成/脱敏样本展示各组件和状态（含长中文、错误、空状态、窄屏），用于 unslop 审阅和固定环境下的截图比对；构建检查确认发行产物不包含页面、fixture 或对应路由模块。

### 5.6 为 v8.3 预留的扩展位置

能力管理页为扩展详情页预留路由和导航位置。扩展页面作为 FreeAgent 前端自己的代码按需加载；输入区的本轮能力列表按 Core 返回的数据渲染。v8.3 接入 AffectWeave 时复用这些位置，不需要插件 UI 运行时或重新设计前端外壳。

## 6. v8.2：单 Core 效率、上下文与长任务质量

### 6.1 原则和基准

先测量再改动；优化以实际用户等待和资源消耗为依据。保留 PG 的同步持久化、当前审批和 UNKNOWN 事实，不靠放松这些边界制造性能数字。

| 场景 | 固定负载 | 记录 |
| --- | --- | --- |
| 启动/闲置 | 首次初始化、再次启动、最后客户端离开 | 各启动阶段耗时、Core/PG/渠道/浏览器分别占用、退出结果 |
| 多会话 | 1 万会话、置顶与搜索/分页 | 查询 p50/p95、响应字节、前端处理与可操作时间 |
| 长对话 | 5000 轮合成对话、代码/公式/工具/附件引用 | 当前页打开、加载旧页、滚动/选中/展开、内存 |
| 执行存储 | 沿用 10 万 Run/40 万消息/30 万 Attempt 数据集 | TaskService/Echo、SQL 计划、池等待、重开和事务耗时 |
| 流式交互 | 固定消息内容，模拟每秒 30 个片段持续 10 分钟 | 输入响应、批次渲染、取消响应、内存和订阅数 |
| 长期运行 | 至少 8 小时隔离混合负载 | 错误分类、未决任务、重复作用、连接/进程泄漏和资源趋势 |

上述是计划负载，尚未运行。每组保存提交、环境、种子、样本数和原始结果。耗时统计至少 200 个有效样本或注明不足；真实模型等待单独统计。不能用 Echo 核心 p95 约 100ms 推导真实对话或 UI 同样快。

对比采用相同环境，定位到的慢路径需要可重复改善；无关关键路径若 p95 回退超过 20%，调查并记录原因，不能机械地把噪声或模型延时判为回归。内存检查关注稳态和资源释放，不能只选一次低值。

### 6.2 性能实施范围

1. 按阶段记录可复用的耗时：上下文准备、数据库/连接等待、模型首字/总时长、工具和投递。使用现有记录的投影，不引入观测平台。
2. 对实测慢 SQL、重复上下文读取、重复序列化和过宽列表请求做定向优化。
3. 扩展/Skill 扫描或解析只有存在重复成本时才缓存；缓存包含内容/配置版本及权限作用域，变更及时失效。
4. v8.1 已建立前端性能预算、分页、流式批量渲染和按需加载；v8.2 只处理基准中发现的长尾问题，例如超长会话加载旧页、长时间高频流式更新。KaTeX/高亮延迟加载必须保持原文与内容位置。
5. 不默认增大连接池或并发。工具并行只作为有充分读写/取消/顺序证据时的单独工作项，不是本版默认优化手段。

### 6.3 上下文和压缩质量

- 统一检查模型窗口、输出预留、工具 schema、固定内容、附件与扩展片段的实际请求预算。
- 压缩之前先区分历史可压缩部分和不可分割的当前输入/工具组；明确提示无法继续的具体占用来源。
- 自动和手动压缩共用一个核心过程；查看/预估不创建任务或推进插件状态。
- 连续压缩保留目标、用户约束、已验证结果、未决事项、重要路径与来源。摘要不把工具输出变成授权，不把 UNKNOWN 总结成成功。
- 压缩失败、取消或无明显缩减时保留上一份可用摘要；避免反复压缩同一范围造成额外花费。
- 验证压缩期间新消息、插话、附件、权限降低和会话分支，提交时重新核对范围/版本。
- 构造至少 3 类长任务，各经历至少 5 次压缩。检查早期约束保留、实际任务结果和追加 token/模型调用；真实模型与确定性测试分开记录。

### 6.4 恢复与错误处理

保持现有有限模型恢复及不确定工具的有界只读核查，补齐用户能执行的下一步：

| 情况 | 产品行为 |
| --- | --- |
| 认证/配置/余额不足 | 明确定位对应配置，不自动循环请求 |
| 瞬时限流/网络错误 | 有界等待和恢复，显示次数/原因；停止可取消等待 |
| 输出长度截断 | 保留已有确定结果，说明输出边界；完整且确认的工具才可能执行 |
| 上下文不足 | 提供占用事实与合适的压缩/移除选择；不冒称模型不支持全部任务 |
| 工具结果 UNKNOWN | 展示原 Attempt/receipt 与核查结果；不重放原副作用 |
| TG 投递失败/UNKNOWN | 保留已完成 Run，显示渠道结果；核查/补回执不再调用模型或工具 |

v8.2 的优化以减少无效重试和用户困惑为目标，不把所有失败改成无限自动继续。

### 6.5 Provider 验收

按协议族覆盖 Chat Completions、Responses 和 Anthropic；复用现有实现，先补契约/故障测试。获得有效服务条件时再执行真实 JSON/SSE、工具、usage、取消、中断、长度/上下文错误等代表性用例。

Responses 搜索针对真实 `web_search_call`、事件和来源解析验收；不因为兼容 `/responses` 就推断服务支持托管搜索。未具备搜索服务的配置明确标不支持或未验，不能伪造搜索结果。

DeepSeek 继续作为主要真实使用基线。其他品牌不逐个重复建设执行逻辑；真实条件不足单列未运行，不把整个单 Core 优化伪装为阻塞。

### 6.6 退出条件

性能基准、已定位慢路径的改动前后数据和回归结果齐全；压缩质量、恢复、副作用计数、取消和接续通过。相关全量/竞态按改动范围运行，最终发布再做完整回归。真实 Provider 未验范围准确保留。

## 7. v8.3：AffectWeave FreeAgent 版 1.0 完整成品

### 7.1 定位和实现方式

AffectWeave 整体以 Go 重写，并主动按 FreeAgent 的扩展契约适配。采用独立可执行进程、现有版本化协议、Core 授权的输入/上下文/交付接口及 PG；人物业务保持独立，不进入默认 Core。

**Go 是 AffectWeave 唯一生产实现，由 AffectWeave 仓库负责整体重写与成品化。** 固定 [AffectWeave](https://github.com/endview/affectweave) Python Demo 参考提交，保留规则说明、源码出处、许可证和合成 fixture；迁写人物基线、情绪/中期状态、关系、经历、未决事项及上下文编译，并重构状态推进、流式回答/提案分离、PG 和交付恢复。旧 Python 仅供离线行为对照，不做生产回退、不继续同步功能开发；FreeAgent 不复制人物业务代码，不维护双引擎，不恢复旧 SQLite/API 兼容。

A1 验证最小 Go 协议入口及 Windows/Debian 样包，采用与 FreeAgent 对齐的 Go 工具链、固定依赖，优先无需 CGO 的实现；最终包实际核对系统库需求。发行只含可执行文件、manifest 和必要资源，用户无需安装 Go/Python/Node，未启用时无人物进程。现有导入上限为 8 MiB/256 文件，Go 二进制同样可能超限，优先验证用户扩展目录离线安装；需要脚本时只做该扩展的安装/卸载，不建设插件平台。选择依据是长期维护和发行统一，性能收益以实测为准；前期重写成本和规则偏差纳入验收。比较与责任划分见[适配决策](AFFECTWEAVE_FREEAGENT_ADAPTATION_DECISION_2026-11-06.md)。

扩展自身版本为 **AffectWeave FreeAgent 1.0**。开发允许分里程碑，成品验收覆盖下列全部范围，不能只交付上下文注入的小样。

### 7.2 成品功能

| 功能 | 产品要求 |

| 情绪和中期状态 | 明确事件来源、时间、幅度、衰减与未决状态；临时推导与长期写回区别展示 |
| 关系 | 绑定真实交互者与空间，查看来源/历史，支持经确认的修改 |

### 7.3 状态与授权

| 内容 | 处理方式 |
| --- | --- |
| Core 已采用输入、生成结果、实际发送 receipt | 按真实身份和稳定操作键登记，可自动记录事实 |
| 固定规则计算的衰减/临时状态 | 按已配置规则处理，注明推导来源；不构造用户新偏好或人格变化 |
| 模型建议的长期角色/关系/记忆修改 | 保存为待确认提案；具体内容、作用范围、版本确认后才生效 |
| 用户直接编辑/重置/删除 | 经 GUI/CLI 或 AI 提案确认的同一操作执行，支持查看影响范围 |

启用扩展不是授权隐式人格学习。可以把若干明确提案放在一次预览中批量确认；任一内容/版本变化重新核对，部分成功逐项记录。未确认的模型判断不能变成长期人物事实。

人物态度不修改工具权限、Provider 选择或执行限制；亲密度等数值不授予信任。群空间仍不带入私人经历，用户昵称/模型文本不能替代 Core 提供的身份。

### 7.4 Core 与扩展交界

只补这次实际需要的通用能力，具体 wire 字段在 A1 冻结：

- 已采用输入的标识及其 Run/会话/空间关联；排队未采用内容不传入推进过程。
- 当前授权上下文片段预算和有界输入。人物片段不重复加入原始聊天历史和 Core 摘要。
- 已有生成/投递结果的按范围读取或通知，支持从有限游标补读；通过现有消息/receipt 投影提供。
- 扩展配置与持久状态提案的统一确认入口，支持 revision、幂等和逐项结果。当前 extension settings 仍是 user-only；新增普通非秘密配置须有类型和作用域约束，使 GUI/CLI/AI 使用同一确认操作，不直接向模型开放任意 settings/env_from。
- 独立 PG 数据域的初始化/备份/恢复所需的窄接口或维护命令。

这些接口复用既有扩展协议和记录；不建设通用消息总线、任意插件 UI 执行器或新的管理平台。扩展身份不得获得 Core 数据库和模型凭据。

[扩展开发指南](EXTENSION_DEVELOPMENT_GUIDE.md)列出现行接口和未实现部分。A1 增加实测的 Go 最小入口/manifest/fixture 样例，冻结本次确需的新字段/方法和兼容方式；A4 将构建、双端契约测试、安装/故障步骤同步为实装版本。不提前建设通用 Go SDK，也不发布仅写在计划里的可调用 API；现有 Python/Node 文档仍供其他扩展使用。

跨库确认复用现有 `ControlOperation.ID`、内容摘要、期望版本和结果字段。扩展在自己的单个 PG 事务中同时更新状态并保存该操作的最小结果记录；同 ID/同内容返回原结果，同 ID/不同内容拒绝。若提交后回执丢失，Core 保留该操作待核对，通过受限查询读取原结果，不换新 ID 重做，也不直接判为未生效。未查到结果还须确认原调用已结束；无法确认则保留 UNKNOWN，禁止盲目重发。查询结果不产生新审批，用户授权仍绑定原内容与范围。

这只补扩展本地的事务内去重与结果查询，复用已有控制日志，不增加另一套审批对象、跨库事务、补偿工作流或后台协调服务。操作结果随扩展备份保留，不能比可恢复的原控制记录更早清除。

### 7.5 每轮处理流程

1. 用户启用角色与指定范围。Core 接收、去重并采用输入，提供稳定消息身份。
2. 扩展对同一输入只登记一次；上下文查询、模型重试、同轮工具后调用均复用已冻结的人物版本，不再次推进状态。
3. 扩展编译片段；Core 重新核算全部上下文后按正常流程调用模型/工具。
4. 可见回答按原方式流式交付。人物状态分析与状态提案不混入回答正文；额外模型调用须明确启用、记入同轮用量并有界执行。
5. 保存候选回答和真实交付结果：`turn.finished` 仅是执行结束；TG 回执、GUI/CLI 的实际呈现确认分别表达各自能证明的事实，不把发送成功当作用户已读。
6. 后续反馈绑定原行为；模型自己的评价不能当独立结果。长期变更经确认后，以 CAS 更新对应人物状态。

流式取消、部分发送和 UNKNOWN 不能统一记为失败或成功。GUI/Web 断连后缺少呈现确认时保留不确定，不为了补人物证据自动重发回答。

### 7.6 PG 和备份

扩展用自己的逻辑数据库和受限角色，可共用当前 PG 实例。仅显式启用持久化时创建。业务键至少包含 Core 身份、空间、角色、参与者及事件/操作身份，更新使用事务、期望版本和幂等键。

避免把 Demo 的整个人物生命周期无限追加在一个不断增长的 JSON 大对象里。先保留清楚的当前状态、已有事实引用、必要历史与幂等记录；具体表按真实访问模式设计，不提前引入知识图谱或向量服务。

成品首版的配套备份复用已有 Core backup 与扩展 `pg_dump`，只增加 AffectWeave 的有界写回暂停：暂停新扩展写回，等待在途写回和原控制回执核对完成，再生成两份备份及同一清单。Core 普通任务派发不暂停，新事实继续进入 Core 原有记录。等待超时或存在未核清写入时不产出“完整配套备份”；以受控清理释放暂停，不能强制把 UNKNOWN 当成功。

清单记录 Core 身份、扩展版本、各快照及扩展已消费的持久来源边界，不用内存 SSE 序号充当恢复游标。恢复后扩展落后时只补读/采用已有事实与原操作结果，不重跑模型/工具；扩展领先且缺源、备份混搭或来源已不可恢复时拒绝启用扩展，要求匹配的配套备份，Core 可单独恢复。若备份中存在未结算的跨边界修改，按原操作 ID 核查，不盲目重放。

这里只组合两份备份和一项有限写回暂停，不建设通用备份协调器、分布式快照或自动跨库回滚。A1 验证暂停期间事实保留与恢复边界；不足则补必要读取，不靠增加通用历史平台解决。

若当前只读接口不能恢复所需事实，应先补可靠的窄读取能力；不得用重新执行模型/工具弥补。旧实例确认停止后才恢复同一身份副本，生产启用前核对渠道唯一性。

### 7.7 管理与故障体验

设置 → 能力管理 → 扩展 → AffectWeave 提供完整管理页，包含启用状态、角色、作用范围、人物状态、待确认提案、存储/备份和错误处理。输入区只放当前会话/本轮选择与简要状态。管理页作为 FreeAgent 前端自己的代码，使用 v8.1 预留的扩展详情页位置按需加载；输入区的角色选择使用 Core 返回的本轮能力列表。

扩展超时、崩溃或状态版本冲突时，显示原因和恢复选项。普通执行可以按已选策略继续，但不能假装人物状态已应用；未决写入保留待核对。停用停止新注入和分析，不擅自删除用户数据。

## 8. 经验总结 0.1：独立可选扩展批次

保持既有方向：**复杂可重复流程 → Skill；简单稳定约定 → 可固定 Memory**。它是可选 Skill 加“总结经验”入口，不需要独立常驻服务或另一套数据库。

完整流程：

1. 用户选择 Run、消息范围或已确认产物，Core 核对可见范围和来源。
2. 提供有界、脱敏输入，由该 Skill 生成草稿；失败和未解决 UNKNOWN 必须保留局限说明。
3. 预览类型、标题、正文、适用条件、来源和范围。Skill 展示步骤/输入/验收；Memory 展示固定位置与预算影响。
4. 通过既有持久确认保存具体内容。保存与启用/固定分别表达，也可在同次明确确认中“保存并固定”。
5. 使用稳定请求键和期望版本避免重复发布；修改、停用、取消固定和删除沿用已有管理。

不在每轮自动总结；不把压缩摘要直接当永久经验；不自动把 AffectWeave 人物经历写入全局知识。停用总结功能不删除已确认产物。

退出条件：来源越权拒绝、秘密过滤、UNKNOWN 正确保留、确认内容准确、重复确认不重复创建，产物在 GUI/CLI/TG 的已授权范围内实际可用。

## 9. 数据更新、发布与 Hytron 验收

### 9.1 数据连续性

v8.0 切 PG 时已按用户选择全新开始，这不意味着今后每个版本都重建用户对话库。后续普通发布使用当前原生 PG 格式；必要的 schema 前向变更有版本检查、备份和失败处理，不维护旧 SQLite 读取、双写或跨版本回退层。

只换前端时不变动数据库。schema 变化只做明确必要的最小变更，未知/更新 schema 拒绝写入。程序回退若不兼容新 schema，先保留当前数据并报告，不能悄悄把有新写入的库覆盖回旧备份。

### 9.2 每版发布步骤

1. 核对工作区、既有改动、实际完成项和未验项目。
2. 完成相应的逻辑/组件/API/竞态/真实环境检查，先调查失败并定向修复，再运行最终相关全量回归。
3. 固定源码与依赖、更新实际使用文档和发布说明；用最终源码生成 Windows/Linux 归档，验证重复构建和最终包。

### 9.3 生产隔离

## 10. 完成状态与测试报告格式

每版报告分开记录：

| 状态 | 含义 |
| --- | --- |
| 已实现 | 当前源码存在对应行为，但可能尚缺真实环境验收 |
| PASS | 指定版本/环境的检查实际运行并符合预期 |
| FAIL | 实际运行不符合预期，需调查修复；修复复测与原失败都保留 |
| NOT_RUN | 尚未执行或缺凭据/环境，不能用编译或 mock 代替 |
| UNKNOWN | 实际派发后结果不确定的执行/交付事实；不能泛指没做测试 |
| BLOCKED | 缺必须的用户决定、权限或外部条件，明确解除条件 |

验收保留实际命令、源码版本、环境、原始结果位置、局限和复测说明。核心正确性/数据/权限问题不带病标完成；非本版承诺的外部平台缺口可延期并明确披露。

文档编辑检查链接和一致性即可，不为文字修改重跑完整 Go 套件。实现阶段按真实影响选择测试；完成后不为增加数量反复跑已充分通过的检查。

## 11. 暂缓的方向

大型共享知识库、自动知识治理、跨 Core 自主协作、任务抢占/认领和全局拓扑继续保留为未来候选。启动前需要一个明确、可验收的用户工作流；PG 的存在不是实现它们的充分理由。

Lark/QQ 按用户后续真实测试再排期；多租户、组织权限、插件市场和通用进程编排不在本计划。
